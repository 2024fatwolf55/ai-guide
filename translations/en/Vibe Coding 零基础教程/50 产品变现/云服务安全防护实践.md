## How to Use Cloud Services Safely

#### 1. If You Don’t Need It, Don’t Use It!

Always choose cloud services based on your actual needs. Don’t use technology just for the sake of using technology.

For example, if you’re building a practice project or a free website, then be cautious with usage-based services like object storage and CDN.

Yes, object storage is convenient, and CDN can accelerate your website—but are they really necessary? Is your server bandwidth really unable to support that tiny amount of traffic? Without CDN, will your website truly violate the 8-second rule?

> The 8-second rule is a famous internet principle: when visiting a webpage, if users wait longer than 8 seconds, they become impatient; if downloading takes too long, they may give up entirely.

In fact, just spending a little more money to increase your server bandwidth can also improve loading speed.

I used to love using CDN. If I didn’t put a CDN in front of a website, I felt uncomfortable. But in reality, most websites don’t have much concurrent traffic, so CDN doesn’t make them noticeably faster. Instead, it increases both cost and attack risk. And don’t even get me started on Cloudflare CDN. In China, the free version can practically act as a “website slowdown tool.”

I’ve also recommended some free deployment services before, such as Vercel, GitHub Pages, Railway, and so on. They’re all great ways to save money, so feel free to try them. But once a site deployed on those platforms gets attacked, the platform will most likely just ban your account. After all, they don’t really need to care who the attacker is. As long as your service is generating problematic traffic, blocking your service and account is their idea of solving the issue.



#### 2. Protect Your Unique Identifiers!

“Unique identifier” is a broad concept, and it means different things for different cloud services.

- Cloud server: the server IP
- Object storage: the bucket name
- CDN: the CDN domain name
- Developer account: `accessKey`
- Application: `appId`



This is extremely important, because for most cloud services, the unique identifier is **not changeable**. Once it is exposed to attackers, they can keep hitting you forever.

For example, if someone knows your server IP, they can launch a DDoS attack on it. If they know your object storage bucket name, they can derive the storage domain and start draining your traffic.

![](https://pic.yupi.icu/1/image-20240319155850380.png)

Some people may ask: isn’t the server IP visible through website requests or DNS resolution?

![](https://pic.yupi.icu/1/image-20240319155924361.png)

If your site is deployed on a single server, then yes, that’s true. But if you place a load balancer or a CDN in front of it, the visible IP may be dynamic, and attackers can no longer directly hit a specific backend server.

So be sure to protect your service’s unique identifiers and never expose them proactively!



#### 3. Control Permissions Strictly

Try to follow the principle of least privilege: close everything by default, then open permissions one by one only when needed.

For example, when using object storage, ways to control permissions include bucket access settings, anti-leech protection, and granting access only as needed.

1) When creating a bucket, set the permission to “private read/write.” If you need to grant access to team members, use sub-accounts whenever possible instead of sharing your primary account directly.

![](https://pic.yupi.icu/1/1705978130876-edf05ae2-93b9-401d-83fe-909594685066.png)



2) Configure anti-leech protection by rejecting empty `Referer` values and only adding your own site’s domain to the whitelist.

![](https://pic.yupi.icu/1/1705972980906-712c8bb3-fe95-4115-a683-3e7ef9f53a07.png)



3) Configure permissions on demand. For example, if there are many directories inside a bucket, you can allow specific users to publicly read only a subset of them, such as public images.

![](https://pic.yupi.icu/1/1704184426557-2fd77f75-8e0a-4644-b63a-1e0f4ec48302.png)



#### 4. Set Up Monitoring and Alerts

The strategies above are meant to prevent attacks. But if an attack does happen, you must be able to receive a “you are being attacked” notification immediately—not a “your account is overdue” notification.

So every cloud service must have monitoring and alerts configured, and you need to consider multiple dimensions and alert strategies together. Don’t just casually add one alert and call it done.

For example, you can configure combinations of multiple indicators, so alerts trigger when there are service errors, traffic spikes, or too many client-side error requests.

![](https://pic.yupi.icu/1/image-20240319161121251.png)

After the traffic-draining incident happened to me, I gave Tencent Cloud a lot of suggestions for improvement. To their credit, they did improve things. Now they even remind you to configure alerts when creating a bucket, which I think is very nice~

It’s also worth mentioning that they later added an announcement saying that object storage already supports automatic anti-traffic-abuse features:

![](https://pic.yupi.icu/1/image-20240319160736142.png)

Emmm... whether that is fully true or not, I still recommend configuring permissions and alerts manually yourself. Double protection is better.



#### 5. Emergency Control Measures

If alerts tell you that a cloud service is under attack, there are actually some emergency steps you can take to stop the loss from growing.

For example... shut the service down!

Don’t laugh. If the benefit of keeping the service running is lower than the loss caused by the attack, temporarily shutting it down may be the best option. If you can’t win, retreat strategically~

Most cloud platforms provide ways to limit or block attacks, such as IP allowlists and blocklists, IP rate limiting, blocking access from certain regions, or forbidding certain requests.

![](https://pic.yupi.icu/1/image-20240319161622687.png)

If you use object storage, never access the bucket directly through the object storage domain. Use a CDN domain instead. That’s because CDN not only provides more capabilities, but can also protect the object storage origin address.

Of course, CDN itself can also be attacked, so you still need all the protection measures above. Among them, IP rate limiting is absolutely mandatory. And if your project mainly serves users in China, I recommend directly blocking access from overseas regions.



#### 6. Storage Migration

I believe more than 90% of people have no experience with this.

Let me share a situation I encountered before. An attacker kept requesting a certain object storage bucket to drain traffic. Once I noticed it, I quickly blocked access, and all of the attacker’s requests started returning `403 Forbidden`.

But guess what? The attacker kept sending requests anyway.

The nasty part is that object storage billing is not only based on traffic—it can also charge by request count! In other words, even if every malicious request is rejected, as long as the attacker keeps requesting, I still keep losing money!

Oh, and here’s another fun experience worth sharing. To find the attacker’s IP, I needed to enable logging for object storage. But guess what? The log files are stored in your own object storage bucket. That means every attacker request is effectively causing files to be written into your bucket! Incredible. If they keep attacking for a few days, the number of log files can exceed the number of your normal files. And yes, log storage costs money too~

I even asked customer support what to do in this case. Just let them keep draining me forever?

The solution from support was: migrate the storage.

In other words, switch to a new bucket name and don’t let the attacker know it.

Well... yes, that technically is a solution, though the cost is pretty high.

So once again: never leak your object storage bucket name! Protect your service’s unique identifiers!



#### 7. Recharge Only as Needed

In plain language: don’t top up your cloud account with too much money at once!

Because network attacks are impossible to defend against perfectly. Even if you configure alerts, they’re not fully controllable. If I get a warning text at 3 a.m., I probably won’t see it until the next day, and by then it may already be too late.

At that point, if your account still has balance, the system will continue deducting money. But if it runs out of balance and becomes overdue, it won’t keep charging, which lets you discover the issue faster and stop the bleeding sooner.



## Final Thoughts

Those are the 7 cloud security lessons I’ve summarized. Let me emphasize again: never assume cyberattacks won’t happen to you. Attackers don’t need a reason to target you.

AI is making product-building easier and easier, but that should never weaken your security awareness. Spending 10 minutes on protection might save you tens of thousands of yuan.
