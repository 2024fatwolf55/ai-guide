## What Are Dynamic Workflows?

Dynamic workflows are the ability for AI to write its own orchestration scripts, split a large task into multiple subtasks, distribute them to dozens or even hundreds of parallel sub-agents, and finally aggregate and verify the results.

![](https://pic.yupi.icu/1/01_%E5%8A%A8%E6%80%81%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%A6%82%E5%BF%B5%E5%9B%BE-AI%E8%87%AA%E5%B7%B1%E7%BC%96%E6%8E%92%E5%AD%90Agent_compressed_v3.png)

Note that the key phrase here is **AI writes it itself**.

In the past, when we built multi-agent collaboration—whether with a framework like LangGraph or our own orchestration code—the logic of how to split tasks, coordinate sub-agents, and merge results was all manually defined by the developer. You had to think in advance about how many agents there would be, what each one would do, and how the upstream and downstream flow would connect.

Dynamic workflows are different. You only need to tell AI what you want done—for example, “Help me migrate this project from Python 2 to Python 3.” It will analyze the structure of the codebase by itself, decide how many sub-agents are needed, determine which files each sub-agent should migrate, figure out how to run them in parallel, and decide how to verify whether the migrated code is correct.

The whole orchestration plan is generated by AI in real time based on your specific task. It is not a predefined template.

To use an analogy, traditional multi-agent orchestration is like being the project manager yourself: you draw the Gantt chart, assign tasks, and run status meetings.

Dynamic workflows are more like handing the requirement to a reliable technical director who goes off, assembles a team, splits the work, tracks progress, handles acceptance, and finally gives you the result.

## How Agent Systems Are Classified

To understand the technical positioning of dynamic workflows, we first need to look at how Anthropic officially classifies agent systems.

Back in December 2024, Anthropic published a very classic engineering blog post called *Building Effective Agents*.

![](https://pic.yupi.icu/1/image-20260706185611910.png)

That article divides all agentic systems into two major categories.

The first category is **Workflow**. Its defining characteristic is that the collaboration path between the LLM and tools is orchestrated through predefined code. You write the process, and AI follows it.

The second category is **Agent**. Its defining characteristic is that the LLM dynamically decides what to do next, which tools to use, and how to move the task forward. Control rests with the model.

Within the Workflow category, Anthropic further breaks things down into five specific patterns:

1. **Prompt Chaining**

The task is split into a fixed sequence of steps, where the output of the previous step becomes the input of the next. For example, first generate copy, then translate it into English. The order is fixed.

2. **Routing**

Requests are sent to different processing flows based on input type. For example, in a customer support system, refund issues go through the refund flow while technical issues go through technical support.

3. **Parallelization**

One task is split into multiple independent subtasks that run in parallel, and then the results are combined. For example, having multiple agents review the same piece of code from different angles.

4. **Orchestrator-Workers**

A central LLM acts as the orchestrator, dynamically breaks the task down, assigns subtasks to multiple worker LLMs, and then synthesizes their results. The key point here is “dynamic”: the orchestrator is not assigning work based on predefined rules, but deciding on the number of workers and their responsibilities according to the actual input.

5. **Evaluator-Optimizer**

One LLM generates a result, while another LLM evaluates it and provides feedback, forming an iterative loop until the quality meets the standard.

![](https://pic.yupi.icu/1/03_Anthropic%E4%BA%94%E7%A7%8DAgent%E7%B3%BB%E7%BB%9F%E6%A8%A1%E5%BC%8F%E6%A6%82%E8%A7%88-%E5%90%AB%E4%B8%AD%E6%96%87%E5%90%8D_compressed_v3.png)

See it now? Dynamic workflows are essentially a productized implementation of the fourth pattern: **Orchestrator-Workers**.

Note that this is not a new pattern, but a different implementation of the same pattern. The real difference is **who builds the orchestration system**.

In the traditional approach, you implement the Orchestrator-Workers pattern yourself in code. For example, if you want to perform a full-codebase security audit, you might build the orchestration logic with LangGraph or plain Python like this:

```python
# 这是开发者自己写的编排器
files = scan_all_files(project_path)
risk_groups = classify_by_risk(files)
agents = []
for group in risk_groups.high:
    agents.append(Agent(task="deep_audit", targets=group))
for group in risk_groups.low:
    agents.append(Agent(task="quick_scan", targets=group))
results = run_parallel(agents)
report = merge_results(results)
```

That code is indeed “dynamic” at runtime, because it distributes work according to the actual file situation. But the problem is that **you wrote the orchestrator itself**. How files are scanned, how risk is classified, how many agents are launched, and what strategy each agent uses—every one of those decision rules has to be designed by you.

Dynamic Workflows are different because Claude Code handles all of that for you. You only need to say, “Help me audit this project for security vulnerabilities,” and Claude will generate and execute orchestration logic like the code above by itself. File scanning, risk assessment, task assignment, and result aggregation are all completed autonomously by the model at runtime.

To summarize in one sentence: **in the traditional approach, you are the developer of the Orchestrator-Workers pattern; in Dynamic Workflows, you are the user of that pattern.**



## How Dynamic Workflows Operate

The execution process of a dynamic workflow can roughly be divided into several stages.

1) First comes task intake and planning.

Claude analyzes your input, understands the scale and complexity of the task, and dynamically generates an orchestration plan that decides how many sub-agents to launch and what each one is responsible for. This is like a technical lead receiving a big project, first estimating the workload, and then drafting a staffing and responsibility plan.

2) Once the plan is set, it moves into the distribution and execution phase.

Sub-agents are launched in parallel, each processing its assigned subtasks. The system currently supports up to 16 concurrent sub-agents at the same time, with a total upper limit of 1000!

3) Then comes cross-validation, which is one of the highlights of dynamic workflows.

It doesn’t simply stitch subtasks together. Instead, it arranges independent verification agents to check the output of other agents. For high-risk tasks, it can even launch **adversarial agents**, whose only job is to look for weaknesses and break the results produced by earlier agents.

If verification fails, the relevant sub-agents are asked to make corrections. **This loop continues until all results meet the consistency standard.**

Does that sound familiar?

Exactly—it’s Loop Engineering again. If you want to know more about Claude Code’s official Loop Engineering design philosophy, you can read *A Beginner-Friendly Guide to Loop Engineering* in this tutorial’s experience-and-tips section. The core idea is to let AI run again and again, fix again and again, until the goal is achieved. Dynamic workflows push this idea to the extreme. Instead of a single agent looping by itself, a whole group of agents loops by validating and correcting one another.

4) Finally, all verified results are aggregated into one complete deliverable and returned to the user.

Progress is continuously saved throughout the whole process. If the task is interrupted midway, it can resume from the breakpoint instead of starting from zero.

![](https://pic.yupi.icu/1/04_%E5%8A%A8%E6%80%81%E5%B7%A5%E4%BD%9C%E6%B5%81%E8%BF%90%E4%BD%9C%E6%9C%BA%E5%88%B6%E5%9B%9B%E9%98%B6%E6%AE%B5%E6%B5%81%E7%A8%8B_compressed_v3.png)

There is also another key design: **the orchestration runs outside the main conversation context**.

You can think of it this way: the main chat window is the meeting room where you talk to the technical director, while those sub-agents are working independently at separate desks. No matter how many people are working in parallel outside, they do not take up space in your meeting room. So no matter how large the task is or how many sub-agents it involves, it won’t blow up Claude’s main context window. That is the key reason it can handle large tasks spanning hundreds of files.

![](https://pic.yupi.icu/1/05_%E4%B8%8A%E4%B8%8B%E6%96%87%E9%9A%94%E7%A6%BB-%E4%BC%9A%E8%AE%AE%E5%AE%A4vs%E7%8B%AC%E7%AB%8B%E5%B7%A5%E4%BD%8D%E6%AF%94%E5%96%BB_compressed_v1.png)



## A Real Dynamic Workflow Case

The most jaw-dropping example of dynamic workflows comes from Jarred Sumner, the developer of the JavaScript runtime Bun.

He used dynamic workflows to port Bun from Zig to Rust. The whole process took 11 days, produced about 750,000 lines of Rust code, and preserved a 99.8% pass rate on the original test suite.

How was that migration completed with dynamic workflows?

Anthropic’s official blog revealed the rough process.

First, one workflow traversed the entire Zig codebase and mapped the Rust lifetime annotations required for every field of every struct. That step required analyzing a huge number of type relationships and ownership semantics.

Then, another workflow distributed hundreds of `.zig` files to parallel agents, with each agent translating its assigned `.zig` files into behaviorally equivalent `.rs` files. And each file had two review agents assigned to check the translation results.

Next came the repair loop. A workflow repeatedly ran builds and tests, then distributed compiler errors and test failures to the relevant agents for fixes, until the entire project compiled successfully and passed the test suite.

Finally, an overnight workflow eliminated unnecessary data copies and created a separate Pull Request for each optimization so humans could review them.

Throughout the whole process, the human developer only defined the goal, confirmed the plan, and reviewed PRs at the end. All concrete implementation in the middle was handled autonomously by the dynamic workflow.

## Is Dynamic Workflow a Model Capability or a Tool Capability?

This is a sharp interview question: is dynamic workflow something the model itself is capable of, or something provided by the platform tooling?

The answer is **you need both, but they play different roles**.

**At the model layer, what you get is intelligence.**

For example:

- Task planning ability: being able to decompose one vague high-level goal into concrete, executable subtasks
- Context understanding ability: being able to analyze codebase structure and understand dependencies between files
- Tool use ability: being able to correctly generate and execute orchestration scripts
- Self-correction ability: being able to judge whether subtask outputs are correct and determine how to fix them

This is why dynamic workflows were released together with Opus 4.8. Opus 4.8 made clear improvements in task planning and judgment. Its defect-detection rate on its own code is four times higher than the previous generation. That self-checking ability is the foundation that makes “cross-validation” and “adversarial checking” possible in dynamic workflows.

**At the platform layer, what you get is infrastructure.**

For example:

- Lifecycle management of sub-agents: creating, scheduling, and destroying them
- Concurrency control: limiting simultaneous execution to at most 16 agents
- Progress persistence: allowing interrupted tasks to resume
- Context isolation: making orchestration logic not consume the main conversation context window
- Final aggregation and delivery of results

Here’s an analogy: model capability is like the brain of an excellent technical director. It knows how to break down work, assign people, and validate outcomes.

Platform capability is like the company’s project management system and infrastructure, providing meeting rooms, collaboration tools, version control, continuous integration, and so on.

A smart brain without an execution system is not enough. And infrastructure without anyone capable of planning is not enough either.

So if an interviewer asks this question, the most accurate answer is that dynamic workflow is **a platform product feature built on top of strong model capability**. The model provides the intelligence for planning and decision-making, while the platform provides the infrastructure for parallel execution and lifecycle management. Only the combination of the two forms a complete dynamic workflow.

## How It Differs from Multi-Agent Frameworks

Once you understand the architectural layering above, the difference between dynamic workflows and multi-agent frameworks like LangGraph and CrewAI becomes very clear.

The traditional multi-agent framework approach is that the developer defines the roles and capabilities of agents, writes the orchestration logic manually to decide who runs first, who runs next, how results are passed, and how exceptional cases are handled. The framework gives you many ready-made modules and connection methods, but assembling them is still your job.

Dynamic workflows take the exact opposite approach. The developer only describes the final goal, and the model automatically completes role definition, task decomposition, orchestration logic generation, exception handling, and result verification. You don’t even need to write the orchestration code, because Claude writes it itself.

**Neither approach is absolutely better or worse. They are suited to different scenarios.**

If your task is highly standardized and follows a fixed flow—for example, running a daily data analysis report on schedule—then hardcoding the workflow in a traditional framework will be more stable, more controllable, and cheaper.

If your task is one-off, large-scale, and has unpredictable subtasks—such as codebase migration, security auditing, or large-scale refactoring—then the advantages of dynamic workflows become obvious, because there is simply no way to define all the subtasks and execution paths in advance.



## How Do You Use It?

Dynamic workflows can currently be used in Claude Code’s CLI, desktop app, VS Code extension, and also through the API.

Other AI coding tools are also exploring similar parallel multi-agent patterns. For example, Cursor has launched Cloud Agents and background agent parallelism. But as of now, when it comes to the model **writing its own orchestration scripts**, Claude Code’s dynamic workflows are the most complete and the most highly productized.

There are two very simple ways to start a dynamic workflow.

The first is to directly tell Claude to create a workflow, for example:

```markdown
创建一个工作流，帮我审计整个代码库的安全漏洞
```

The second is to enable the `ultracode` setting in Claude Code’s effort menu. That setting turns reasoning effort up to the maximum and also lets Claude automatically judge whether the current task is suitable for a workflow. If it is, Claude automatically switches into workflow mode.

The first time a workflow is triggered, Claude Code displays the plan it is about to execute and asks for your confirmation instead of immediately running.

One thing to keep in mind is that dynamic workflows consume far more tokens than ordinary Claude Code sessions. The reason is simple: if you hire dozens or hundreds of workers at the same time, the payroll is obviously much more expensive than hiring just one.

So I recommend using it as needed. Start with a small-scoped task first, get a feel for the scale of the consumption, and only then gradually expand. Don’t point it at the entire codebase in one shot right away.



## Final Thoughts

After reading this article, you’ll probably notice that AI application development is evolving from “developers orchestrate agents” to “agents orchestrate agents.” The role of the developer is moving upward, from the executor who writes orchestration code to the manager who defines goals and reviews outcomes.

This trend means that in the future, just knowing how to use a framework to build agents may no longer be enough. You’ll also need a deep understanding of the entire agent architecture system. The five patterns proposed in Anthropic’s *Building Effective Agents* are basically required knowledge in this field, and I strongly recommend rereading them.

I hope this article truly helps you understand dynamic workflows, so whether you face them in interviews or in real usage, you’ll feel confident. The world of AI coding changes fast—keep learning, and you’ll definitely keep up!
