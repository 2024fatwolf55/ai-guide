# Claude Code 驗證迴圈實戰教程

> 讓 AI 寫完程式碼後自己驗收，驗證迴圈的原理和實戰

大家好，我是程式設計師魚皮。

最近 Claude 官方發了一篇部落格，專門講怎麼讓 Claude Code 自己檢查自己寫的程式碼，官方管這個叫 Verification Loop 驗證迴圈。

簡單來說，就是 AI 寫完程式碼以後不急著交差，而是先自己跑一遍檢查。有問題就繼續改，改完再檢查，形成一個迴圈，直到全部檢查透過以後才交付給你。

> 原文指路：[https://claude.com/blog/building-verification-loops-in-claude-code-with-skills](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)

![](https://pic.yupi.icu/chengfang/1786413234706-10e92ec5-2867-4fc4-bdc7-207583033002.png?imageSlim)

不過話說回來，現在 AI 寫程式碼是真的快，可是每次它自信地跟我說「搞定了」，我還是得自己開啟頁面、一個功能一個功能試、切換到手機端再測、最後開啟瀏覽器控制檯看有沒有報錯。

程式碼是它寫的，怎麼最後驗收還是我的活？

所以我倒要試試，Claude 官方的這套驗證迴圈，到底能不能真讓我少乾點活。

![](https://pic.yupi.icu/chengfang/2.jpeg?imageSlim)



## 什麼是驗證迴圈？

Claude Code 在開發過程中本來就會做一些基礎檢查，比如：

- 型別檢查，確認變數型別有沒有寫錯
- 程式碼規範檢查，有沒有少寫分號之類的低階問題
- 自動化測試，跑一遍預設的測試用例
- 還有執行時報錯，程式碼能不能穩定執行

這些檢查都能給出明確的對錯結果，AI 可以根據結果繼續修改程式碼。

但是，這些基礎檢查覆蓋不了所有最終效果。像手機端有沒有佈局錯亂、按鈕到底能不能點、頁面有沒有嚴重遮擋，這些問題光靠跑程式碼檢查工具是發現不了的，最後還是得自己開啟頁面親眼確認。

所以我平時用 AI 開發的流程一般是這樣的：先讓 AI 把程式碼寫完、跑一些基礎檢查，然後我再實際操作一遍。發現問題以後告訴 AI 哪裡不對，讓它繼續改。

但是換成 Verification Loop 以後，後面人工驗收的部分也可以交給 AI 來幹了。讓 AI 自己驗證、自己修改，全部透過以後再交付給我。

![](https://pic.yupi.icu/chengfang/01-AI.png?imageSlim)

當然，光跟 AI 說一句「你自己檢查一下」肯定不夠。它得知道具體該檢查什麼，也得拿到一個能夠判斷「到底過沒過」的明確結果。

在這方面，Claude 官方提到了好幾種內建的驗證方式：

+ `/verify` 技能，讓 AI 自己構建專案、執行起來、然後觀察改動有沒有問題
+ Toolchain，也就是利用專案裡已有的工具鏈（比如程式碼檢查工具），讓 AI 直接讀取工具返回的錯誤和警告來判斷
+ Code Review，一個自動審查程式碼改動的多 Agent 服務，可以在 PR（程式碼合併請求）上自動跑一遍審查
+ GitHub Actions，在程式碼提交時自動觸發檢查流程
+ Spec validation，按照專案裡的需求規格文件來驗證改動
+ Rubrics，按照評分標準來打分，不及格就打回去重做

這些名字不用記住，核心思路都是一樣的：**給 AI 一個明確的檢查結果，讓它能判斷這次到底是透過還是失敗。** 程式能不能正常執行、測試有沒有透過、程式碼提交有沒有問題，都屬於這種能夠明確判斷對錯的結果。

甚至專案自己定的特殊規則，也可以變成驗收條件。

那麼你可能要問了：什麼是專案自己定的特殊規則？

舉個例子，假如資料庫遷移要刪掉一列資料，但是沒有事先把資料備份保留下來，那這次修改就直接判定不透過。

這種規則是你的專案自己定的，通用的程式碼檢查工具根本不知道這回事，但同樣可以寫進驗證流程，讓 AI 每次都按照這個標準來驗。

![](https://pic.yupi.icu/chengfang/02-AI.png?imageSlim)



## 用 Skill 把驗證迴圈固定下來

如果你每次要重複的不只是一兩條規則，而是一整套檢查動作，那就可以把它們整理成 Skill 技能。

Skill 的本質就是一個 Markdown 檔案，裡面用自然語言寫清楚檢查步驟，放到專案的 `.claude/skills/` 目錄下。以後再遇到類似的任務，AI 直接按照這套流程執行，不需要你每次重新教一遍。

官方推薦的上手路徑是這樣的：

1. 先從一項最常重複的人工檢查開始，比如試試 Claude Code 裡內建的 `/verify` 技能，輸入這個命令以後，AI 就會自己構建專案、執行起來、然後檢查改動有沒有問題。
2. 覺得不夠用的話再自己寫。你可以把檢查流程用自然語言描述出來，交給 `skill-creator` 外掛幫你生成，它會理解你的工作流程然後自動生成對應的 Skill 檔案。當然也可以自己手寫一個 Markdown 檔案，放到技能目錄下就行。
3. 拿新任務跑一遍，看看哪裡不好用就繼續迭代。等單個檢查穩定了，再嘗試把多個檢查串起來。

![](https://pic.yupi.icu/chengfang/03-AI.png?imageSlim)

一個簡單的 Skill 檔案長這樣：

```yaml
# .claude/skills/verify-log-hygiene/SKILL.md
---
name: verify-log-hygiene
description: 檢查錯誤日誌是否包含請求 ID，並且不能洩露請求體內容。
---
讀取當前程式碼改動中的錯誤處理路徑。

對於每一個錯誤路徑上的日誌呼叫，確認它包含了請求 ID，
並且沒有把請求體、請求頭、或使用者提交的任何資料寫進日誌。

逐條報告違規項（標註檔名:行號），然後修復它。
```

上面這個 Skill 的作用是檢查日誌規範。你可以看到，它就是一段 YAML 格式的頭資訊（名字和簡介）加上幾段自然語言寫的檢查指令，告訴 AI 該看什麼、怎麼判斷、發現問題怎麼處理。沒有想象中那麼複雜，本質上就是把你平時腦子裡的檢查流程用文字寫下來。

像我平時檢查前端頁面，就會反覆檢查頁面載入、核心互動、移動端適配、瀏覽器控制檯這些東西，每次都是同樣的流程。所以這次我乾脆把它們寫成了一個 `verify-frontend` Skill，讓 AI 自己對照著驗收。

![](https://pic.yupi.icu/chengfang/6.png?imageSlim)

不過要注意，**Verification Loop 是核心思路，Skill 只是實現它的一種方式**。你也可以用 Hooks 鉤子（在特定時機自動觸發的指令碼）來實現類似的效果，甚至可以用 `/goal` 命令定義一個目標條件，讓 AI 自己迴圈直到條件滿足為止。



## 實戰驗證 - 迴圈到底有沒有用？

嗶嗶了一大堆，這玩意到底有沒有用呢？

我決定設計一個對比實驗來試試看。

同一個專案、同樣的需求，第一輪正常讓 AI 開發然後我人工驗收，第二輪讓 AI 開發完以後自己執行 Verification Loop 來驗收。看看這套驗證迴圈在實際開發中，到底能不能幫我省事。

本來我想直接在 Claude Code 裡用 Claude 自家的模型來跑這個實驗，但是我的 Claude 賬號早就喜提封號了。。。

<img src="https://pic.yupi.icu/chengfang/1786431474389-948c82a1-921e-44b1-8e42-54b26a412b93.jpeg?imageSlim" style="zoom:50%;" />

沒辦法，這次只能讓 Claude Code 接 DeepSeek 模型給大家實測。具體怎麼接入，可以閱讀本教程程式設計工具板塊 Claude Code 目錄中的《Claude Code 和 Codex 對接國內模型教程》，這裡就不展開講了。

至於拿什麼專案來測試，我選了最近挺火的竹知了~

我直接給了 AI 幾張參考圖，讓它搓一隻 3D 賽博風格的竹知了出來。

初始版本的頁面只有竹知了主體、緩慢自轉和一個標題。

![竹知了初始版本](https://pic.yupi.icu/chengfang/%E7%AB%B9%E7%9F%A5%E4%BA%86%E5%88%9D%E5%A7%8B%E7%89%88%E6%9C%AC.png?imageSlim)

然後我給 AI 下了 5 條需求：

```plain
1. 滑鼠拖動控制竹知了的旋轉和朝向

3. 狂暴粒子光效
4. 375px 移動端適配
```

為了儘量公平，兩輪實驗都從同一個初始版本開始，用的是相同的 DeepSeek 模型和同一套工具環境，而且每輪都重新開一個全新的 Claude Code 會話。

同時為了保證公平，我在第一輪開始之前就把第二輪要用的 6 類驗收檢查全部定好了，避免我看完第一輪結果以後再臨時往規則裡塞東西。

### 第二輪、驗收也交給 AI

第二輪我把程式碼回退到了竹知了最初的樣子，也就是隻有主體模型和緩慢自轉的那個版本，確保兩輪測試的起點完全一樣。

前面那 5 條功能需求一字不改，只額外增加了一句話：

```plain
開發完成後必須執行 verify-frontend Skill，全部透過後才能宣佈完成。
```

這次 AI 不光要寫程式碼，還得把我平時會做的那些驗收工作自己跑完。

還記得前面提到，我在實驗開始前就定好的那 6 類檢查嗎？

+ 專案能不能正常構建
+ 頁面能不能正常開啟
+ 核心互動有沒有生效
+ 375px 手機端有沒有問題
+ 瀏覽器控制檯有沒有報錯
+ 頁面有沒有明顯錯位、遮擋或者裁切

![](https://pic.yupi.icu/chengfang/16.png?imageSlim)

為了讓 AI 真正能操作頁面，這次我給它配了兩個工具。

1. Playwright 是一個瀏覽器自動化測試框架，相當於 AI 的「手」，能幫它開啟網頁、拖動模型、點選按鈕這些真實操作。
2. Vision 視覺能力相當於 AI 的「眼睛」，讓它能夠截圖並看懂頁面長什麼樣，檢查有沒有明顯的錯位、遮擋或者裁切。可以用 GitHub 上開源的 [多模態視覺識別 Skill](https://github.com/asuojun/claude-vision-skill)

![](https://pic.yupi.icu/1/image-20260803155552049.png)

AI 寫完程式碼之後，會自動執行驗收流程。

中間還出了個小插曲，Playwright 一開始因為依賴沒裝好所以沒跑起來。不過這點小問題根本不需要人工處理，AI 自己排查出了原因、修好了依賴、然後繼續往下驗收。

![](https://pic.yupi.icu/chengfang/17.png?imageSlim)

最終，按照實驗前定好的規則，6 類檢查全部透過了。

![](https://pic.yupi.icu/chengfang/18.png?imageSlim)

這一輪任務總耗時 9 分 48 秒。而且從效果上來看，第二輪狂暴模式的粒子效果，比第一輪確實炫酷多了。

這也提醒了我，如果真要把驗收交給 AI，光告訴它該驗什麼還不夠。AI 具體用什麼方式去檢查（比如是看截圖還是讀控制檯日誌）、檢查到異常以後怎麼分類記錄、最後怎麼在報告裡完整匯報出來，這些同樣得在 Skill 裡寫清楚。中間任何一環有疏漏，都可能出現有問題卻沒有報告的盲區。



## 兩輪實驗的對比結果

按照實驗前定好的規則，兩輪都透過了驗收，也都沒有發現影響功能的業務 Bug。

真正發生變化的，是驗收這件事由誰來做。

第一輪 AI 寫完以後，我自己點、自己看、自己測。

第二輪在 AI 宣佈完成之前，我完全沒有插手驗收過程，它自己把整套流程跑完了。

代價就是，第二輪總耗時多了 4 分多鐘。但這段時間不需要我守在旁邊一個個手動點選螢幕，我可以去喝杯水、摸摸魚、做一組提肛，回來直接看結果。這才是我覺得 Verification Loop 真正有價值的地方。

當然，「透過驗收」和「效果完全符合預期」還是兩回事。就像第一輪的狂暴模式，功能確實做出來了，但到底夠不夠狂暴、視覺效果滿不滿意，還是得人工來判斷。

所以我覺得，真正適合先交給 AI 驗收的，是那些能夠明確判斷對錯、而且每次都要重複做的事情。比如專案能不能構建、核心互動有沒有生效、手機端有沒有適配問題、瀏覽器控制檯有沒有報錯。

至於動畫是不是太快、頁面夠不夠好看、竹知了到底有沒有小時候甩起來那個味兒，這些涉及主觀審美和產品感覺的事情，最後還是得人來拍板。

在 AI 時代，審美和判斷力才是人類最稀缺的能力。



## 驗證迴圈還能怎麼玩？

我這次只是在 AI 開發完成以後，單獨跑了一遍驗收。但 Verification Loop 並不只能放在最後一步。

等這套驗收方式拿真實任務跑過幾次、確定比較可靠以後，還可以把它嵌進日常開發流程，甚至跟其他檢查串起來形成一條流水線。

Claude 官方把這些用法總結成了 4 種執行方式：

![](https://pic.yupi.icu/chengfang/04-AI.png?imageSlim)

1）Standalone 獨立執行

需要的時候手動觸發一次，比如提交程式碼前臨時跑個安全掃描。

2）Embedded 嵌入到其他 Skill 裡

把驗證步驟直接寫進生產 Skill 的末尾。比如你有一個自動建立 React 元件的 Skill，就可以在最後加一行「建立完成後跑一遍 eslint 檢查」，這樣每次用這個 Skill 的時候都會自動驗證。

3）Chained 鏈式串聯

多個 Skill 首尾相連，一個跑完自動觸發下一個。

Anthropic 自己的 Claude Code 團隊日常就是這麼用的。先用 `/code-review` 命令找 Bug，再用 `/simplify` 命令精簡程式碼，然後用 `/verify` 命令確認功能正常，如果改動涉及 UI 的話，最後還會用一個自定義的 `/design` Skill 比對設計規範。

這四步跑完，就是一整套全自動的程式碼質量保障流程，開發者只有在某一步出了問題、需要人工介入時才會收到通知。

![](https://pic.yupi.icu/chengfang/05-AI.png?imageSlim)

4）On every PR 每次提交程式碼時自動執行

等鏈式流程在你自己的開發中跑穩以後，就可以把它掛到 GitHub Actions 上。這是 GitHub 提供的自動化流水線服務。

這樣一來，團隊裡任何人提交程式碼合併請求，都會自動觸發同一套驗證檢查，不需要靠每個人自覺去手動執行，程式碼質量有了統一的底線保障。

順帶一提，Claude Code 的創造者 Boris Cherny 在今年 6 月說過一句話：我已經不再手動給 AI 寫提示詞了，我現在的工作是設計迴圈，讓迴圈去指揮 AI 該做什麼。

![](https://pic.yupi.icu/1/loop%20engineering.png)

這個理念在開發者社群裡被叫做 Loop Engineering 迴圈工程，核心思想就是人類從「逐條指揮 AI」轉變為「設計一套系統讓 AI 自己運轉」，而 Verification Loop 就是其中最關鍵的一環。

![](https://pic.yupi.icu/1/01_Loop_Engineering%E6%A0%B8%E5%BF%83%E6%A6%82%E5%BF%B5%EF%BC%9A%E4%BD%A0%E8%AE%BE%E8%AE%A1%E7%B3%BB%E7%BB%9F%E8%AE%A9%E5%AE%83%E4%BB%A3%E6%9B%BF%E4%BD%A0%E7%BB%99AI%E4%B8%8B%E6%8C%87%E4%BB%A4_compressed_v1.png)

關於 Loop Engineering 的更多內容，可以閱讀本教程經驗技巧板塊中的《Loop Engineering 保姆級教程》。



## 寫在最後

看到這裡，你應該感受到了 Verification Loop 的作用。

如果你要用 AI 做完整的大專案，我建議你除了給 AI 需求清單之外，再給 AI 一張驗收清單。

像那些每次都要重複做的檢查，能讓 AI 先跑一遍，就沒必要再從頭手動驗一遍了。

得益於這套方法，最近我用 AI 輕輕鬆鬆搞了不少完整的作品，並且已經推廣給不少人用了~

比如下面這個遊戲記錄工具：

![](https://pic.yupi.icu/1/image-20260812144301650.png)

如果你也有一套寫完程式碼後每次都會重複的檢查流程，可以試著整理成 Skill。懶得從零寫的話，可以用官方的 `skill-creator` 外掛，它會像面試一樣問你平時的工作流程，然後幫你自動生成。

話說回來，AI 能自己檢查程式碼了，那還要程式設計師幹嘛？

答案很簡單：**背鍋**（bushi）

AI 驗收透過不代表萬事 OK，它只能覆蓋那些能明確判斷對錯的部分。真要上線出了問題，需求是誰定的、驗收標準是誰寫的、最終拍板上線的是誰，這些責任 AI 可背不了。

AI 是很好的執行者和檢查員，但它不是決策者，更不是責任人。

所以別覺得什麼「一人公司」就很輕鬆。你只是沒看到人類背後被 AI 反覆折磨、對著螢幕狂罵的樣子罷了。

一個能做判斷、敢扛責任的人，加上一個不知疲倦、執行力拉滿的 AI，這才是當前最靠譜的組合。
