# 用好 CLAUDE.md，讓你的 AI 程式設計效率翻倍！

> 一份 Markdown 檔案，讓 AI 自動了解你的專案

大家好，我是程式設計師魚皮。

最近我發現一個現象，很多同學開始用 Claude Code、Cursor 這些 AI 程式設計工具了，但用了一陣子之後就開始抱怨：AI 怎麼總是不聽話？讓它改個 Bug 反而引入三個新 Bug，讓它加個功能結果技術棧都給換了。

![](https://pic.yupi.icu/1/image-20260622164228939.png)

這些問題的根源，往往不是 AI 笨，而是你沒有給它足夠的上下文。

AI 每次開始新會話，都是一張白紙。它不知道你的專案用的是什麼技術棧，不知道你們團隊的程式碼規範，不知道你之前做了什麼決策。

你不說，它就猜。猜對了算你運氣好，猜錯了你就得返工，把你的 tokens 全拿走，把回憶化成空~

那有沒有一種方法，讓 AI 每次開始工作前就自動了解你的專案？

必須有啊！就是今天要聊的 **CLAUDE.md**。

![](https://pic.yupi.icu/1/image-20260320152009626.png)



## 一、CLAUDE.md 是什麼？

CLAUDE.md 是 Claude Code 裡的一個 Markdown 檔案，放在專案根目錄下。

Claude Code 每次啟動會話時，都會自動讀取這個檔案，把裡面的內容當作專案的背景知識。

你可以把它理解為 **給 AI 寫的「入職手冊」**。就像新員工入職第一天，你會給他一份文件，介紹公司用什麼技術、程式碼怎麼寫、測試怎麼跑、有什麼坑要注意。CLAUDE.md 乾的就是這個事。

![](https://pic.yupi.icu/1/01_CLAUDE.md%E6%98%AFAI%E7%9A%84%E5%85%A5%E8%81%8C%E6%89%8B%E5%86%8C_compressed_v1.png)

比如一個最簡單的 CLAUDE.md 長這樣：

```markdown
# 我的部落格系統

Next.js 16 + TypeScript + Tailwind CSS + Supabase

## 常用命令
- npm run dev        # 啟動開發伺服器
- npm run test       # 跑測試
- npm run build      # 生產構建

## 程式碼規範
- 使用函式式元件，不用 class 元件
- 樣式只用 Tailwind CSS，不寫自定義 CSS
- 所有元件必須有 TypeScript 型別定義
```

AI 每次開始工作前都會先讀一遍，然後所有生成的程式碼都會自動遵循這些規範，不用你每次都重複交代。

不過有一點需要注意，CLAUDE.md 對 AI 來說 **是建議** 而 **不是強制執行** 的配置。它的效果取決於你寫得有多具體、多簡潔。越精確的指令 AI 遵循得越好，寫了一大堆模糊的要求反而可能被選擇性忽略。



## 二、更通用的 AGENTS.md

你可能會想，這是 Claude Code 的專屬功能嗎？我用 Cursor 怎麼辦？

其實幾乎所有主流 AI 程式設計工具都有類似的機制。比如 Cursor 也支援 `.cursor/rules/` 和 AGENTS.md 來做同樣的事。

必須要知道的是 AGENTS.md，它是一個跨工具的開放標準，由 OpenAI、Google、Cursor 等多家公司聯合推出，目前已經有好萬個開源專案在用，支援 30 多種 AI 程式設計工具。

![](https://pic.yupi.icu/1/image-20260622190311465.png)

Claude Code 雖然預設只讀 CLAUDE.md，但你可以在 CLAUDE.md 裡用一行 `@AGENTS.md` 把它匯入進來，兩邊就打通了。

這些 Markdown 檔案本質上都是一回事，就是 **給 AI 寫一份專案說明書**。你學會寫好這份說明書，換任何 AI 程式設計工具都能用。

而且 AGENTS.md 的用途不只是專案開發指導，它同樣可以作為指導 AI 做事的工作流文件。比如我自己就用 AGENTS.md 來定義各種工作流，像圖文創作、產品客服、資料分析這些場景，都可以用一份 Markdown 檔案把 AI 的工作方式固定下來，每次啟動自動載入，省得重複交代。

後面我會統一用 CLAUDE.md 來講解，但裡面的技巧對所有工具都適用。



## 三、為什麼一定要寫好這個檔案？

你可能覺得，不就是個配置檔案嗎，隨便寫寫不就行了？

大錯特錯！CLAUDE.md 的質量直接決定了 AI 幫你幹活的效率和準確度。

以我自己天天用 AI 程式設計的體驗來看，一個好的 CLAUDE.md 至少能解決 3 個問題：

**第一，減少重複溝通。** 

沒有 CLAUDE.md 的時候，每次新會話我都得重複交代一遍技術棧、程式碼規範、專案結構。有了它，這些資訊 AI 自動就知道了。

**第二，提升程式碼一致性。**

之前 AI 有時候用 React 函式元件，有時候給我整個 class 元件出來；有時候用 CSS Modules，有時候給我寫內聯樣式。規範寫進 CLAUDE.md 後，這種問題基本消失了。

**第三，降低出錯率。**

比如我的專案裡有個特殊的 API 響應格式 `{ success, data, error }`，不寫進規則的話，AI 每次都按自己的習慣來。寫進去之後，Claude 就會自動遵循，不用我每次糾正。

![](https://pic.yupi.icu/1/03_%E6%B2%A1%E6%9C%89vs%E6%9C%89CLAUDE.md%E7%9A%84%E5%AF%B9%E6%AF%94_compressed_v1.png)

之前我在另一篇文章裡提到過，規則檔案在 50 行左右時遵循率可以達到 94%，但如果一股腦堆到 400 行，遵循率就掉到了 71%。

**所以 CLAUDE.md 不是越多越好，而是要精準。**

這就引出了最核心的問題，也是本文的重點，怎麼寫好 CLAUDE.md 文件？



## 四、怎麼寫好 CLAUDE.md？

下面這些技巧，很多是經過社群大量實踐和我個人驗證的經驗，建議仔細閱讀，細細品味。



### 1、控制在 200 行以內

這是 Claude Code 官方文件給出的建議。

CLAUDE.md 的內容會在每次會話開始時載入到 AI 的上下文視窗中。這個視窗是有限的，你的規則檔案越長，留給實際工作內容的空間就越少。

而且 AI 對指令的遵循能力跟指令數量負相關。社群有人引用過一項研究，AI 大概能合理遵循 150 到 200 條指令，超過這個數之後，遵循質量會均勻下降，不僅僅是忽略新加的，而且全部都開始變差。

**所以寫 CLAUDE.md 要像寫簡歷一樣，精煉再精煉。**

![](https://pic.yupi.icu/1/08_%E6%8C%87%E4%BB%A4%E6%95%B0%E9%87%8Fvs%E9%81%B5%E5%BE%AA%E7%8E%87%E6%9B%B2%E7%BA%BF_compressed_v3.png)

對於每一行，問自己一個問題：刪掉它 AI 會犯錯嗎？

如果答案是不會，就果斷刪掉。



### 2、只寫 AI 猜不到的東西

官方文件專門列了一個 CLAUDE.md 中應該寫和不該寫的清單，非常值得參考。

應該寫進去的：

- AI 不可能猜到的構建命令和測試命令
- 跟預設不同的程式碼風格規則
- 團隊的 Git 規範（分支命名、PR 格式）
- 專案特有的架構決策
- 開發環境的特殊要求（必需的環境變數之類）
- 容易踩坑的地方

不該寫進去的：
- AI 讀程式碼就能知道的東西
- 通用的語言規範（AI 本來就會）
- 詳細的 API 文件（放別的地方，CLAUDE.md 裡放連結就行）
- 寫乾淨的程式碼、注意效能這種廢話

![](https://pic.yupi.icu/1/09_%E8%AF%A5%E5%86%99vs%E4%B8%8D%E8%AF%A5%E5%86%99%E5%88%86%E7%B1%BB%E7%AD%9B%E9%80%89%E5%9B%BE_compressed_v2.png)

像我做程式設計導航專案時，就把一些即使讀程式碼也容易忽略的約定寫進了 CLAUDE.md，比如 API 響應統一使用 `BaseResponse` 包裝類、異常統一用 `BusinessException` 丟擲。雖然 AI 深入分析程式碼也能發現這些模式，但寫進規則之後能省掉它每次重新推斷的過程，效率高很多。



### 3、用正面指令代替否定指令

這個技巧其實有點兒反直覺。。

有篇論文研究發現，87.5% 的 AI 規則違反都來自同一個原因，就是否定句反而把被禁止的概念給啟用了。你寫「不要使用分號」，AI 看到分號這兩個字，反而更容易在後續生成中產出分號。

這跟心理學裡的白熊效應一模一樣。叫你不要想白熊，你腦子裡馬上就全是白熊。

所以正確的做法是用正面表述替代：
- ❌ 不要使用 class 元件 → ✅ 使用函式式元件和 Hooks
- ❌ 不要用 any 型別 → ✅ 所有變數必須有明確的 TypeScript 型別定義
- ❌ 不要在主分支直接提交 → ✅ 所有變更透過 feature 分支提交 PR

![](https://pic.yupi.icu/1/04_%E7%99%BD%E7%86%8A%E6%95%88%E5%BA%94%E4%B8%8E%E6%AD%A3%E9%9D%A2%E6%8C%87%E4%BB%A4_compressed_v2.png)



### 4、指令要具體可驗證

模糊的指令等於沒有指令。AI 很擅長處理具體的規則，但對抽象的要求就會自行發揮。

舉些例子：

- ❌ 正確格式化程式碼 → ✅ 使用 2 空格縮排
- ❌ 測試你的更改 → ✅ 提交前執行 `npm test`
- ❌ 保持檔案有序 → ✅ API handlers 放在 `src/api/handlers/`

越具體的指令，AI 越容易判斷自己有沒有遵循，違反了也更容易被發現。



### 5、用 Hooks 來強制執行

CLAUDE.md 本質上只是建議，不是 100% 生效的禁令。

像程式碼格式化、提交前跑測試、危險命令攔截這些任務，應該用確定性的自動化指令碼來執行。

Claude Code 提供了 Hooks 機制，可以在 AI 操作的關鍵節點自動執行你預設的指令碼。

比如你想讓每次檔案編輯後自動跑 ESLint，寫一個 Hooks 配置就搞定了，AI 根本不介入，100% 會執行。

**一句話總結就是，CLAUDE.md 負責建議，Hooks 負責強制操作。**

![](https://pic.yupi.icu/1/05_CLAUDE.md%E5%BB%BA%E8%AE%AEvs_Hooks%E5%BC%BA%E5%88%B6%E6%89%A7%E8%A1%8C_compressed_v3.png)



### 6、大專案用路徑規則按需載入

如果你的專案比較大，200 行根本裝不下所有規範。這時候不要硬往 CLAUDE.md 裡塞，而是用 `.claude/rules/` 目錄來拆分。

每個規則檔案可以用 YAML frontmatter 指定只對特定路徑的檔案生效：

```yaml
---
paths:
  - "src/api/**/*.ts"
---

# API 開發規範
- 所有 API 端點必須包含輸入驗證
- 使用標準的錯誤響應格式
- 新增 OpenAPI 文件註釋
```

這樣只有當 Claude 操作 `src/api/` 下面的 TypeScript 檔案時，這些規則才會載入到上下文中，既省了上下文空間，又不會用不相關的規則干擾 AI。



### 7、用 @import 做漸進式披露

社群裡最受推崇的高階技巧叫漸進式披露，核心思想就是不要把所有東西塞進 CLAUDE.md，而是告訴 AI 去哪裡找它需要的資訊。

做法很簡單。在專案中建立一個 `docs/` 目錄，放各類專題文件，然後在 CLAUDE.md 中用簡短描述加觸發條件來引用：

```markdown
## 參考文件

### API 架構 — @docs/api-architecture.md
何時閱讀：新增或修改 API 端點時

### 資料庫設計 — @docs/database-design.md
何時閱讀：建立或修改資料模型時
```

這樣 Claude 只在真正需要的時候才會去讀取對應的文件，平時不佔用上下文空間。

![](https://pic.yupi.icu/1/06_%E6%B8%90%E8%BF%9B%E5%BC%8F%E6%8A%AB%E9%9C%B2%E6%8C%89%E9%9C%80%E5%8A%A0%E8%BD%BD_compressed_v2.png)

CLAUDE.md 的 `@path` 匯入語法支援相對路徑和絕對路徑，最多可以巢狀 4 層。

這個思路其實跟我之前講的上下文工程和 Agent Skills 是類似的。AI 程式設計工具的上下文視窗是有限的，你不能一股腦把所有資訊都塞進去。Anthropic 官方把這個策略叫 just-in-time，就是讓 AI 按需獲取資訊，而不是全量載入。



### 8、讓 AI 幫你維護

CLAUDE.md 不是寫好了就不管了，它應該是一份隨著專案成長不斷完善的 "活" 文件。

Claude Code 的創始人推薦了一個習慣：**每次 Claude 犯錯，不要只修正錯誤，還要順手讓它把糾正寫進 CLAUDE.md。**

我自己也是這麼做的，比如 Claude 用了錯誤的匯入路徑，糾正完之後跟它說一句：把這條規則更新到 CLAUDE.md 裡，下次別再犯。

Claude 特別擅長給自己寫規則，時間久了，你的 CLAUDE.md 就變成了一份完整的專案知識庫，出錯率會明顯下降。

另外 Claude Code 現在還有一個 Auto Memory 自動記憶功能，Claude 會自動記錄它在工作中發現的模式和偏好，存到 `~/.claude/projects/<專案>/memory/` 目錄下。這些筆記每次會話都會自動載入，相當於 AI 給自己做了一份備忘錄。

你隨時可以用 `/memory` 命令檢視和編輯這些記憶。

## 五、如何快速建立？

看到這裡你可能會想，這些技巧我都記住了，但從零開始寫一份完整的 CLAUDE.md 還是有點頭疼。

別擔心，有幾個快速起步的方法。



### 用 /init 命令自動生成

在 Claude Code 中輸入 `/init`，Claude 會自動分析你的程式碼庫，生成一份包含構建命令、測試指令和專案規範的 CLAUDE.md。如果檔案已經存在，它會建議改進而不是覆蓋。

![](https://pic.yupi.icu/1/image-20260622182756786.png)

不過需要注意，自動生成的內容可能不夠精確，畢竟 AI 只能看到你的程式碼成果，不理解背後的過程。

社群有人說過，CLAUDE.md 影響你工作流的每個階段和產出的每個檔案，一條不好的指令產生的破壞力遠超一行壞程式碼。所以自動生成之後，一定要自己過一遍，該刪的刪、該補的補。



### 讓 AI 從對話中沉澱

我自己經常用的一種方法是，先不急著寫 CLAUDE.md，正常跟 AI 協作完成一兩個任務。做完之後，讓 AI 回顧整個對話過程，幫你總結出需要記住的專案規範和注意事項，直接寫成 CLAUDE.md。

這樣得到的規則檔案是從實戰中提煉出來的，比憑空想象要精準得多。

像我自己帶團隊做專案時，每次 Code Review 中發現 AI 犯的錯誤，都會讓 Claude 把修正追加到 CLAUDE.md 裡。做了一個月之後，這份檔案已經沉澱了幾十條非常有針對性的規則，新同事用 Claude Code 的時候上手也快了很多。

![](https://pic.yupi.icu/1/10_AI%E7%BA%A0%E9%94%99%E6%B2%89%E6%B7%80%E6%AD%A3%E5%90%91%E5%BE%AA%E7%8E%AF_compressed_v2.png)



### 參考優秀的開源專案

GitHub 上有個 awesome-claude-md 倉庫，收錄了 100 多個真實專案的 CLAUDE.md 示例，覆蓋各種技術棧和專案型別，包括 Anthropic 官方的、Cloudflare 的 monorepo 專案等等。

另外還有個 awesome-claude-code 倉庫，整理了 Skills、Hooks、斜槓命令等 Claude Code 生態工具，也值得收藏。

![](https://pic.yupi.icu/1/image-20260622184038586.png)

有時間的話，可以讓 AI 幫你分析一下這些案例，找個跟你專案技術棧接近的參考著寫，比從零開始快多了。

**記住，CLAUDE.md 的內容寧缺毋濫。**

先從最關鍵的 20 行開始，在實際使用中再慢慢補充。



## 六、多層級配置和團隊協作

如果你在團隊中使用 Claude Code，或者同時做多個專案，有一些進階玩法值得了解。



### 四層作用域

CLAUDE.md 不只能放在專案根目錄，它支援四個層級，按載入順序從先到後排列：

1）組織級，公司 IT 統一部署的規範，所有人強制生效

2）使用者級 `~/.claude/CLAUDE.md`，對你本機的所有專案生效

3）專案級 `./CLAUDE.md`，只對當前專案生效，可提交到 Git

4）本地級 `./CLAUDE.local.md`，只對當前專案生效，不提交到 Git

載入越靠後的內容，AI 越傾向於優先遵循，所以優先順序是 本地級 > 專案級 > 使用者級。但組織級比較特殊，它雖然載入最早，卻 **不可被個人或專案設定排除**，屬於公司強制執行的底線規範。

建議團隊共享的規範寫在專案級，個人偏好寫在本地級，兩邊互不干擾。



### 團隊共建 CLAUDE.md

Claude Code 的創始人推薦把 CLAUDE.md 用 Git 來管理，讓團隊成員共同維護。

每當有人在 Code Review 中發現 AI 犯了什麼錯誤，就把修正追加到 CLAUDE.md 裡。時間久了，這個檔案就沉澱了團隊的開發經驗和規範，變成了整個團隊的 AI 使用手冊。

我們自己團隊也是這麼做的。像面試鴨後端專案的 AGENTS.md，裡面沉澱了技術棧選型、Spring Boot 分層規範、統一響應格式、異常處理方式、資料庫命名規則等約定。新同事入職直接看這份檔案就能上手，Claude 也能自動遵循這些規範生成程式碼，省了大量溝通成本。

### 重要規則一定要存檔案

當你在對話中用 `/compact` 壓縮上下文時，專案根目錄的 CLAUDE.md 會被重新讀取和注入。但你在對話中口頭說的指令，比如後面的程式碼都用 async/await，壓縮後就沒了。

所以，凡是重要的規則，一定要寫進 CLAUDE.md，不要只在對話裡說。這一點跟我之前講的上下文工程也是相通的，持久化的資訊要落到檔案裡，別光靠 AI 的短期記憶。



## 七、排查不生效的問題

如果你發現 AI 好像沒在遵守 CLAUDE.md 裡的規則，可以按這個順序排查：

1）執行 `/memory` 命令，看看你的 CLAUDE.md 有沒有被正確載入

2）檢查指令是不是太模糊了。比如格式化好程式碼這種 AI 沒法執行，改成使用 2 空格縮排、單行不超過 80 字元

3）檢查不同檔案之間有沒有矛盾的指令。如果 CLAUDE.md 裡說用 MyBatis Plus，某個 rules 檔案裡又說用 MyBatis Flex，AI 可能隨便選一個

4）如果某個操作必須在特定時機執行，比如每次提交前跑 lint，就不要靠 CLAUDE.md 了，改用 Hooks

## 寫在最後

沒想到吧，就這麼一個 Markdown 檔案，其實是 AI 程式設計時代最重要的基礎設施之一。

以前我們寫 README.md 是給人看的，現在寫 CLAUDE.md 是給 AI 看的。但本質都一樣，就是把專案的重要資訊組織好、傳達清楚。區別在於，給 AI 寫的說明書要更精煉、更具體、更可執行。

另外補充一個好訊息，前面講的「刪掉它 AI 會犯錯嗎」這個判斷標準，現在有工具幫你做了。Claude Code 內建了一個 `/doctor` 命令，可以自動掃描你的 CLAUDE.md 和 Skills，把冗餘內容和矛盾指令都揪出來。想了解這個命令的用法，可以閱讀本目錄中的《Claude Code 常用斜槓命令大全》。

如果你還沒有為自己的專案寫一份 CLAUDE.md，馬上就可以試試。從最簡單的 20 行開始，把技術棧、構建命令、和 AI 總是犯錯的幾個規則寫進去，你會立刻感受到它的強大。
