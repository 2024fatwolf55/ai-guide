# Cursor Debug 模式詳解

> Cursor 獨家的 AI 除錯功能，用執行時資料幫你精準定位那些靠猜解決不了的 Bug

大家好，我是程式設計師魚皮。

有人說 Codex 香、Claude Code 夯，但是 Cursor 這個曾經的王者似乎已經過時了？

其實不然，Cursor 作為有圖形介面的 AI 程式設計工具，更專注程式設計開發的體驗，不僅內建了程式碼編輯器，還針對程式設計場景提供了一些特色功能。

![](https://pic.yupi.icu/1/image-20260707173645762.png)

今天要分享的 Debug 模式就是 Cursor 的獨家功能，我敢說大多數玩 AI 程式設計的人都不知道。

我一開始也沒在意，但體驗之後只想說一句：夯爆了！



## 為什麼需要 Debug 模式？

用 AI 程式設計修 Bug，大部分時候的流程是這樣的：你把報錯資訊發給 AI → AI 分析程式碼 → 給出修復方案 → 人工驗證一下 → 搞定。

這套流程足夠對付大多數小 Bug 了。

![](https://pic.yupi.icu/1/01_%E5%B8%B8%E8%A7%84AI%E8%B0%83%E8%AF%95%E6%B5%81%E7%A8%8B_compressed_v3.png)

但有些狗 Bug 比較刁鑽，你按照常規方法排查，發現請求正常、日誌也沒報錯、程式碼邏輯看起來也對，但執行結果就是不符合預期。

舉個例子，假設你做了個「AI 每日熱點」應用，熱點列表本來應該按釋出時間從新到舊排列，但實際展示出來的順序時對時錯，重新整理一下又變了。

![](https://pic.yupi.icu/1/image-20260707174025120.png)

你看了下程式碼，發現明明寫了按時間倒序排列，沒毛病啊？？？

![](https://pic.yupi.icu/1/image-20260707174149733.png)

這種 Bug 就很適合用 Cursor 的 Debug 模式來排查。



## Debug 模式實戰

在 Cursor 的對話方塊裡，把模式切換到 Debug，然後描述你遇到的 Bug。

![](https://pic.yupi.icu/1/image-20260707183325681.png)

和普通的 Agent 模式不同，AI 不會一上來就改程式碼。

它會先閱讀你的專案程式碼，針對可能出問題的地方**生成多個假設**。

![](https://pic.yupi.icu/1/image-20260707183429043.png)

然後 AI 自動在程式碼的關鍵位置插入日誌探針。這些日誌資料會傳送到 Cursor 內建的本地除錯伺服器，用來採集執行時的真實資料，比如變數值、執行路徑、時序資訊等。

![](https://pic.yupi.icu/1/image-20260707183500109.png)

接下來 AI 會給你具體的復現步驟，讓你去操作應用，把 Bug 觸發出來。

![](https://pic.yupi.icu/1/image-20260707183608207.png)

你按步驟操作的同時，Cursor 在後臺收集執行時的日誌資料，看到變數的實際值、程式碼的執行路徑等等。

復現 Bug 之後，讓 AI 繼續執行。

AI 透過執行時日誌發現了 Bug 的導火索。部分熱點資料的 time 欄位是字串型別，另一部分是數字時間戳。排序程式碼用的是 `b.time - a.time`，字串減字串得到的是 `NaN`，導致排序結果不確定。

![](https://pic.yupi.icu/1/image-20260707183744622.png)

如果沒有執行時日誌，光看排序程式碼，你很難注意到是資料型別不一致導致的。

定位到原因後，AI 給出了修復方案並自動改好了程式碼，統一把 time 轉為時間戳再比較。

![](https://pic.yupi.icu/1/image-20260707183850585.png)

修好 Bug 之後，AI 會讓你再復現一次來驗證修復效果。

如果你覺得還沒修好，AI 就會加上更多日誌探針，你再復現一次，它再分析，一直迴圈直到問題真正解決。

![](https://pic.yupi.icu/1/image-20260707183947841.png)

確認修復後，AI 會自動把之前插入的所有除錯日誌清理乾淨，只留下那幾行真正的修復改動，非常精準。

![](https://pic.yupi.icu/1/image-20260707184020203.png)

最後，AI 還會給出一段簡潔的問題總結，便於你瞭解 Bug 根因和修復方案。

![](https://pic.yupi.icu/1/image-20260707184103058.png)

總結一下，這套 Debug 模式的工作流程是：假設 → 埋點 → 復現 → 用資料驗證 → 修復 → 再驗證 → 清理。

![Debug 模式完整工作流迴圈](https://pic.yupi.icu/1/02_Debug%E6%A8%A1%E5%BC%8F%E5%AE%8C%E6%95%B4%E5%B7%A5%E4%BD%9C%E6%B5%81%E5%BE%AA%E7%8E%AF_compressed_v3.png)

Cursor 官方在設計這個功能時，研究了團隊中最優秀的除錯工程師的實踐，把他們的工作方法封裝成了這套模式。

整個過程中，AI 負責繁瑣的資料收集和分析工作，你只需要按步驟復現 Bug、確認修復效果就好。

這也是 Debug 模式能搞定那些普通 Agent 模式解決不了的 Bug 的原因，它拿到了程式執行時的真實資料來做判斷，而不是憑藉著訓練資料的經驗值盲目猜測。

![Agent 模式和 Debug 模式對比](https://pic.yupi.icu/1/03_Agent%E6%A8%A1%E5%BC%8Fvs_Debug%E6%A8%A1%E5%BC%8F%E5%AF%B9%E6%AF%94_compressed_v3.png)



## Debug 模式的適用場景

並不是所有 Bug 都需要 Debug 模式。一般的報錯或者邏輯問題，用普通 Agent 模式發一段描述就夠了。

Debug 模式最適合的是那種**執行時才暴露**的問題：

1）競態條件和時序問題。比如兩個請求幾乎同時寫入資料庫導致資料被覆蓋，這種問題只有在併發的時候才會出現，看程式碼根本看不出來。

2）資料時對時錯的問題。就像前面那個排序 Bug，有時候結果對有時候又不對，AI 需要執行時資料才能發現規律。

3）效能問題和記憶體洩漏。頁面用著用著變卡、記憶體佔用一直漲，需要執行時資料才能定位瓶頸在哪。

4）迴歸問題。功能之前好好的，突然就不行了，程式碼改動又多，光靠程式碼變更根本看不出哪一行引入了問題。

這些問題光靠看程式碼很難發現，只有跑起來、拿到執行時的真實資料，才能找到根因。所以遇到這類 Bug 的時候，果斷切換到 Debug 模式試試，會比在 Agent 模式裡反覆讓 AI 猜高效很多。

![](https://pic.yupi.icu/1/04_%E5%9B%9B%E7%B1%BB%E9%80%82%E7%94%A8%E8%BF%90%E8%A1%8C%E6%97%B6Bug%E5%9C%BA%E6%99%AF_compressed_v1.png)

再分享幾個使用 Debug 模式的技巧。

1）描述 Bug 的時候儘量詳細，把錯誤資訊、堆疊跟蹤、操作步驟、預期行為和實際行為都說清楚，AI 的除錯效果會好很多。

2）復現 Bug 的時候嚴格按照 AI 給的步驟去操作，因為 AI 插入的日誌是有針對性的。

3）如果 Bug 不是每次都出現，那就多復現幾次，競態條件這類問題可能要觸發好幾次才會暴露。



## 寫在最後

很多人覺得沒有程式設計基礎，就不能靠 AI 程式設計做出完整專案，因為一旦遇到 Bug 就束手無策了。

別擔心，AI 程式設計工具和模型是在不斷進化的，像 Cursor 的 Debug 模式就把專業工程師的方法論變成了一個開箱即用的功能，你不需要自己來寫日誌、會分析堆疊，AI 都幫你搞定了。學會利用好 AI 程式設計工具的功能，哪怕你不懂技術，一樣可以做出複雜的專案。

目前 Debug 模式是 Cursor 獨有的功能，Claude Code 和 Codex 還沒有類似的能力。畢竟每個工具都有自己擅長的地方，根據自己的情況選擇就好，也希望它們能進一步提升 AI 程式設計的工程能力和開發體驗。
