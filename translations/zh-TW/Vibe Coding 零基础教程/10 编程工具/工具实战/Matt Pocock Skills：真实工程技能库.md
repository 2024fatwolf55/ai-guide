# Matt Pocock Skills：真實工程技能庫

> 18 萬 Star 的開源 Skills 倉庫，把軟體工程方法論裝進 AI

你好，我是程式設計師魚皮。

如今的 GitHub 真是太魔幻了，有個 AI 相關的專案，幾乎全是 Markdown 文字檔案，但是不到半年就拿到了 **18 萬 Star**。

這個倉庫叫 [skills](https://github.com/mattpocock/skills)，作者 Matt Pocock 是前端 TypeScript 領域很有名的教育者，在 YouTube 上有大幾十萬粉絲。他把自己日常用 AI 程式設計的工作方法總結成了一套技能，也就是一組可以直接裝進 Claude Code、Codex 等 AI 程式設計工具裡的指令集，然後開源了出來。

![](https://pic.yupi.icu/1/image-20260721175958152.png)

那麼這套 Skills 到底有什麼？為什麼能受到這麼大的歡迎？

這篇文章我就帶你揭秘這個倉庫，看看怎麼安裝使用、裡面有哪些值得學習的 AI 程式設計技巧。



## 一、這個倉庫有什麼特別

這個倉庫的 Slogan 是「Skills for Real Engineers」，意思是這套東西不是給氛圍程式設計用的，而是給真正要做工程的人用的。

簡單來說，它提供了一套 AI 程式設計的 **標準操作流程**。

用過 Claude Code 的同學應該知道，你可以透過寫 `CLAUDE.md` 檔案來告訴 AI 該怎麼做事。但大多數人寫的要麼是一些零碎的注意事項，要麼就是從網上抄來的通用提示詞，效果一般。

Matt Pocock 做的事情是把真實的軟體工程方法論，比如測試驅動開發、程式碼評審、領域建模這些，濃縮成一個個 Skill 檔案。裝到自己的電腦上後，在 AI 程式設計工具裡輸入類似 `/grill-me`、`/tdd` 這樣的斜槓命令，AI 就會按照對應的工程方法來工作，而不是像平時那樣想到哪寫到哪。

![概念對比 CLAUDE.md 和 Skills](https://pic.yupi.icu/1/01_Skills%E6%A6%82%E5%BF%B5%E5%AF%B9%E6%AF%94%EF%BC%9A%E6%99%AE%E9%80%9ACLAUDE.md_vs_Skills%E7%B3%BB%E7%BB%9F_compressed_v1.png)

截止到我寫這篇文章時，整個倉庫裡有大幾十個 Skill 檔案，其中正式推薦使用的有 22 個，剩下的是一些還在開發中的、作者個人專用的、以及已經廢棄的。

![](https://pic.yupi.icu/1/image-20260721213003965.png)

這 22 個正式 Skill 分成兩大類。一類是工程類，包括測試驅動開發、程式碼評審、Bug 診斷這些跟寫程式碼直接相關的；另一類是生產力類，比如頭腦風暴、上下文交接，甚至還有一個讓 AI 教你學東西的。

如果你還不瞭解 Skills 到底是什麼、內部是怎麼運作的，建議先閱讀本目錄中的《Agent Skills：通用 AI 技能庫》。



## 二、30 秒安裝使用

這個倉庫的安裝很簡單，開啟終端，輸入一行命令就能搞定：

```bash
npx skills@latest add mattpocock/skills
```

![](https://pic.yupi.icu/1/image-20260721181513539.png)

執行之後它會讓你選想要哪些 Skill，以及裝到哪個 AI 程式設計工具裡。選完之後，對應的 Skill 檔案會被複制到你的專案目錄或者 AI 工具的本地配置目錄（比如 `~/.claude/skills/`）。

![](https://pic.yupi.icu/1/image-20260721181722123.png)

建議選上 `/setup-matt-pocock-skills` 這個初始化 Skill，裝完後在 AI 程式設計工具裡執行一次，比如我在 Claude Code 中執行：

![](https://pic.yupi.icu/1/image-20260721181838820.png)

AI 會問你幾個問題來適配你的專案，比如用什麼工具來管理 Issue、專案文件儲存在哪個目錄。

我這裡為了簡單，選擇了用本地 Markdown 檔案來管理 Issue，文件儲存在預設的 `docs/` 目錄下，規則儲存到 `CLAUDE.md` 檔案中。

![](https://pic.yupi.icu/1/image-20260721182034789.png)

如果你不想手動管理這些安裝到專案裡的 Skill 檔案，也可以用 Claude Code 的外掛方式來安裝，這樣它會自動保持最新版本，不過就不能自己修改了。

![](https://pic.yupi.icu/1/image-20260721190007313.png)

裝好之後，接下來我帶你看看這個倉庫裡最實用的幾個 Skill。



## 三、grill-me 需求拷問

這是整個倉庫最火的一個 Skill，也是 Matt Pocock 本人反覆推薦的，作用是讓 AI 反過來對你進行「靈魂拷問」，幫你在讓 AI 寫程式碼之前把需求和設計想清楚。

**但是，它的核心內容加起來竟然只有 3 句話！**

翻譯過來大概是這樣的：

> 針對我的計劃或設計，一個問題一個問題地追問我，直到我們達成共識。沿著決策樹的每個分支走下去，逐個解決分支之間的依賴關係。每個問題要給出你的推薦答案。
>
> 每次只問一個問題，等我回答完再問下一個。一次丟擲一堆問題會讓人不知所措。
>
> 能透過檢視環境（檔案系統、工具等）找到的事實，直接去查，不用問我。但決策是我來做的，每個決策都要等我拍板。

![](https://pic.yupi.icu/1/image-20260721182742452.png)

就是這麼簡單粗暴，但實際用起來後，你會發現效果確實很好。

有使用者分享說，他第一次用 `/grill-me` 的時候，AI 一口氣問了 38 個問題。等問完之後，他發現很多自己之前根本沒想到的設計細節都被 AI 逼著想清楚了。

![](https://pic.yupi.icu/1/image-20260721183248245.png)

這個 Skill 我專門寫了一篇完整的實戰體驗和原理拆解，可以閱讀本教程經驗技巧板塊中的《用 grill-me 讓 AI 拷問你的需求》。

如果你在做的是一個有程式碼倉庫的專案，還可以用升級版的 `/grill-with-docs` 技能。它在拷問你的同時，還會把討論過程中確定下來的術語和決策記錄到 `CONTEXT.md` 和架構決策記錄檔案裡，給你的專案建一份專屬術語表。

這個術語表有什麼用呢？

大家應該都有過這種經歷，每次跟 AI 描述專案裡某個操作的時候，都要寫一大段話來解釋，因為 AI 並不瞭解你們專案內部的叫法。

Matt Pocock 的做法是在 `CONTEXT.md` 裡提前定義好這些術語。比如他自己有個課程管理專案，針對「把課程章節中的某節課建立到檔案系統」這個操作，他定義了一個術語叫「物化級聯」，之後跟 AI 溝通的時候只需要說這個詞，AI 就知道他在說什麼了。

因為 AI 每次對話都會讀 `CONTEXT.md`，所以這些術語積累得越多，AI 對專案的理解就越精準，溝通也越來越高效。

![CONTEXT.md 共享語言讓溝通越來越高效](https://pic.yupi.icu/1/03_CONTEXT.md%E5%85%B1%E4%BA%AB%E8%AF%AD%E8%A8%80%E8%AE%A9%E6%B2%9F%E9%80%9A%E8%B6%8A%E6%9D%A5%E8%B6%8A%E9%AB%98%E6%95%88_compressed_v3.png)



## 四、tdd 測試驅動開發

大家有沒有遇到過這種情況？當你要求 AI 用測試驅動的方式來開發時，它會一口氣先把所有測試寫完，然後再寫所有程式碼。

這種方式看起來效率很高，但實際上有個很坑的問題。AI 在寫測試的時候，程式碼還不存在，所以它只能靠想象來設計測試的結構。等真正開始寫程式碼的時候，實際的 API 可能跟它想象的完全不一樣，結果就是一堆測試要推倒重寫。

`/tdd` 這個 Skill 就是來解決這個問題的。它強制 AI 用「垂直切片」的方式來工作，也就是先寫一個測試讓它失敗，然後只寫剛好能讓這個測試透過的程式碼，透過之後再寫下一個測試。這就是經典的 Red-Green-Refactor 迴圈，一次只走一小步，每一步都是實打實驗證過的。

![TDD 垂直切片和批次方式對比](https://pic.yupi.icu/1/04_TDD%E5%9E%82%E7%9B%B4%E5%88%87%E7%89%87vs%E6%89%B9%E9%87%8F%E6%96%B9%E5%BC%8F%E5%AF%B9%E6%AF%94_compressed_v1.png)

除了迴圈本身，這個 Skill 裡還有幾條值得注意的規則。

比如它要求 **只在預先商定的接縫處測試**。所謂接縫（Seam）就是程式碼的公開介面，比如一個函式的入參和返回值。在寫任何測試之前，AI 會先跟你確認在哪些接縫處寫測試，而不是到處亂寫，這樣測試的覆蓋重點才能落在真正重要的地方。

![](https://pic.yupi.icu/1/image-20260721190924720.png)

另外這個 Skill 還列出了幾種 AI 寫測試時容易犯的反模式，相當於給 AI 定了規矩，一旦發現自己寫出了這類測試就必須改掉。

最典型的一種叫「同義反復測試」，就是把被測程式碼的邏輯在測試裡重新寫一遍，比如 `expect(add(a, b)).toBe(a + b)`，這樣的測試永遠都能透過，毫無意義。正確的做法是用獨立的資料來源來做期望值，比如一個確定的字面量、一個手工算好的例子。

對於團隊專案來說，讓 AI 按照 TDD 的方式來寫程式碼，程式碼質量會有明顯的提升。



## 五、diagnosing-bugs Bug 診斷

遇到 Bug 的時候，很多人的第一反應都是先看程式碼，猜一個可能的原因然後試著改。AI 也是這樣的，大家應該有過這種經歷，讓 AI 修 Bug，結果它改了半天越改越亂。

Matt Pocock 認為問題的根源在於 AI 跳過了最關鍵的一步，就是先建立一個 **能穩定重現 Bug 的反饋迴圈**。

什麼叫反饋迴圈呢？簡單來說就是一條能穩定重現 Bug 的命令。可以是一個會失敗的測試用例、一個 curl 請求、甚至一個 Playwright 瀏覽器自動化指令碼，只要能一鍵執行並且明確告訴你 Bug 到底有沒有觸發就好。

`/diagnosing-bugs` 這個 Skill 把 Debug 過程拆成了 6 個階段，其中「建立反饋迴圈」是第一步，也是整個流程的核心。

![](https://pic.yupi.icu/1/image-20260721191701894-20260721191719297-20260721191756770.png)

**在這步完成之前，AI 不允許跳到「猜原因」的階段。** 如果 AI 在還沒有一條能重現 Bug 的命令的時候就開始分析程式碼，Skill 會直接打斷它。

等有了一條穩定重現的命令之後，接下來的步驟就比較常規了：最小化重現場景、提出假設並逐一驗證、修復並寫回歸測試。

![Bug 診斷 6 階段流程圖](https://pic.yupi.icu/1/05_Bug%E8%AF%8A%E6%96%AD6%E9%98%B6%E6%AE%B5%E6%B5%81%E7%A8%8B%E5%9B%BE%EF%BC%88%E5%8F%8D%E9%A6%88%E5%BE%AA%E7%8E%AF%E4%BC%98%E5%85%88%EF%BC%89_compressed_v2.png)

這個思路跟 Cursor 內建的 Debug 模式有點異曲同工，都是先透過自動檢測和分析錯誤來定位問題，而不是讓 AI 上來就瞎猜和亂改（可以閱讀本教程程式設計工具板塊「Cursor」目錄中的《Cursor Debug 模式詳解》）。

不過 `/diagnosing-bugs` 更偏向於流程規範，它用一套嚴格的分階段方法來約束 AI 的除錯行為。



## 六、teach AI 輔助學習

前面幾個 Skill 都跟寫程式碼有關，但這個倉庫裡還有一些通用的生產力工具，比如 `/teach` 技能，作用是讓 AI 變成你的私人教師。

按照作者寫 `/grill-me` 的尿性，我以為這個 Skill 也就幾句話，結果它背後有一套相當完整的教學方法論。

當你執行 `/teach` 並告訴 AI 你想學什麼之後，AI 會先問你為什麼想學這個東西，然後把你的學習目標記錄到一個叫 `MISSION.md` 的檔案裡。

![](https://pic.yupi.icu/1/image-20260721202928545.png)

接著它會去搜尋高質量的學習資源，整理成 `RESOURCES.md` 資原始檔。

![](https://pic.yupi.icu/1/image-20260721203009683.png)

最後基於收集到的資源給你設計課程，每堂課是一個精美的 HTML 檔案，儲存在 `lessons/` 目錄下。

![](https://pic.yupi.icu/1/image-20260721203410326.png)

值得一提的是，AI 會區分「流暢度」和「儲存強度」這兩種學習效果。流暢度就是你當場能回憶起來的感覺，但這不代表你真的記住了，儲存強度才是真正的長期記憶。所以它會刻意設計有一定難度的練習，用間隔重複和交錯練習等方法來幫你加深記憶，而不是讓你產生「我已經學會了」的錯覺。

還有個很妙的設計是「最近發展區」，這是教育學裡的經典理論。AI 會根據你之前的學習記錄來判斷你現在的水平，然後設計剛好超出你能力一點點的課程內容，不會太簡單讓你感到無聊，也不會太難讓你放棄。

而且你的所有學習過程都儲存在當前目錄下，下次開啟同一個目錄繼續學的時候，AI 就能接著上次的進度來。



## 七、wayfinder 大專案規劃

這個 Skill 專門解決一個問題：當專案大到一個 AI 對話裝不下的時候，該怎麼辦？

用過 AI 程式設計的同學應該都有感受，如果你強行在一個很長的對話裡完成所有事情，AI 的思考質量會隨著上下文變長而明顯下降。Matt Pocock 把 AI 表現最好的上下文範圍叫做「智慧區間」，大概在 120K tokens 以內。

`/wayfinder` 的做法是把一個大需求拆成一張「決策地圖」。當你面對一個大而模糊的需求時，AI 會先跟你一起把最終目標定義清楚，然後在 Issue 管理工具裡建立一張地圖，上面列出需要做的一系列決策，每個決策是一個獨立的 Issue。

![](https://pic.yupi.icu/1/image-20260721204043039.png)

這些決策之間有依賴關係，所以它會自動標註哪些可以先做、哪些要等前置決策完成才能開始。每次你開啟一個新的 AI 對話來處理一個決策的時候，上下文都是乾淨的，不會被之前的內容汙染。

![](https://pic.yupi.icu/1/image-20260721204132899.png)

這裡面還有一個很有趣的設計叫「戰爭迷霧」，就像遊戲裡沒探索過的地圖區域一樣。你現在能看到的決策只是一部分，隨著前面的決策逐步完成，後面的決策才會逐漸清晰起來。這樣可以避免一開始就過度規劃那些還想不清楚的事情。

![Wayfinder 戰爭迷霧決策地圖](https://pic.yupi.icu/1/06_Wayfinder%E6%88%98%E4%BA%89%E8%BF%B7%E9%9B%BE%E5%86%B3%E7%AD%96%E5%9C%B0%E5%9B%BE_compressed_v1.png)

不過這個 Skill 的門檻相對比較高，更適合有一定工程經驗的開發者。如果你的專案規模不大，前面提到的 `/grill-me` 就夠用了。



## 八、其他實用技能

除了上面這些，還有兩個我覺得很值得一提的。

1）`/improve-codebase-architecture` 程式碼架構改進

Matt Pocock 建議每隔幾天就跑一次這個技能，相當於定期給程式碼做一次體檢。它會深度掃描你的程式碼庫，找出那些結構上可以最佳化的地方，然後生成一個視覺化的 HTML 報告，用 Tailwind 美化樣式、用 Mermaid 畫架構圖，每個最佳化建議都是一張卡片，寫著涉及的檔案、當前的問題、建議的改進方案。

![](https://pic.yupi.icu/1/image-20260721204942049.png)

這個 Skill 背後的核心理念來自《A Philosophy of Software Design》這本書。打個比方，一個好的模組就像微波爐，你只需要按幾個按鈕就能加熱食物，內部的電磁波原理完全不用管，這種叫做「深」模組，介面簡單、實現複雜。但如果一個模組用起來跟自己寫一個差不多費勁，那就是「淺」模組了。這個 Skill 要找的就是程式碼庫裡那些淺模組，幫你把它們變成深模組。

![深模組和淺模組的區別](https://pic.yupi.icu/1/07_%E6%B7%B1%E6%A8%A1%E5%9D%97vs%E6%B5%85%E6%A8%A1%E5%9D%97%EF%BC%88%E5%BE%AE%E6%B3%A2%E7%82%89%E6%AF%94%E5%96%BB%EF%BC%89_compressed_v1.png)

2）`/handoff` 上下文交接

大家用 AI 程式設計的時候應該都遇到過這個問題：在一個對話裡討論了很多內容，積累了大量上下文，但是要開一個新對話的時候，之前的所有討論就全丟了。雖然可以手動複製貼上，但是比較麻煩，還容易遺漏關鍵資訊。

`/handoff` 就是來解決這個問題的。在你當前對話結束前，它會讓 AI 把整個對話的核心內容壓縮成一份交接文件，儲存成一個 Markdown 檔案。下次開新對話的時候，只要讓 AI 讀一下這個檔案，它就能接著上次的進度繼續工作。

![](https://pic.yupi.icu/1/image-20260721205244844.png)

這個交接文件還會標註建議在新對話中使用哪些 Skill，並且會自動去除 API 金鑰之類的敏感資訊。



## 寫在最後

學習完這個倉庫後，我感受最深的一點是，這些 Skill 本質上不是提示詞技巧，而是把經典的軟體工程方法論封裝成了 AI 能執行的格式。

像測試驅動開發、領域建模、架構評審，這些理念在軟體工程領域已經存在了二十多年，但以前你得靠團隊協作和程式碼評審來落地，現在透過 Skill 檔案就能讓 AI 自動按照這些方法來工作。

而且透過這個倉庫，你會發現 AI 時代做開源從未如此簡單。Matt Pocock 本質上就是把自己電腦裡 `.agents` 目錄下的工作方法分享了出來，然後持續迭代打磨，就成了十幾萬 Star 的專案。

也許你也可以把自己積累的 AI 程式設計工作流或提示詞模板整理一下開源出來，持續最佳化，說不定也能幫到很多人。**行動才是第一生產力。**
