# GPT-5.6 三模型橫評 - 全棧專案實測

> 三大 AI 程式設計旗艦模型同場競技，一把梭開發全棧足球遊戲專案

剛剛，OpenAI 正式釋出了 GPT-5.6 系列模型，包含 Sol 旗艦、Terra 均衡和 Luna 輕量三個版本。

![](https://pic.yupi.icu/1/image-20260710102644422.png)

這是 OpenAI 繼 GPT-5.5 之後最大的一次模型更新，官方稱 Sol 是 **有史以來最強模型**，在多個程式設計能力測評上超越了 Claude Fable 5！

恰好同一周，馬斯克旗下的 SpaceXAI 也放出了 Grok 4.5，號稱 Opus 級別的模型；而 Anthropic 之前被封禁的 Claude Fable 5 也在 7 月 1 號重新上線。

這下，三家的新旗艦模型湊齊了，這種難得的機會，必須得安排一次大亂鬥！

正好這三個模型在 Cursor 裡都能用了，我乾脆讓它們同時開發同一個專案，用實際的 AI 程式設計能力來分個高下。

![](https://pic.yupi.icu/1/image-20260710101735638.png)

開始之前，先聊聊這次 GPT-5.6 到底更新了什麼。



## GPT-5.6 更新了什麼？

GPT-5.6 這次最大的變化是把模型分成了 3 個檔次：

| 模型  | 定位           | 輸入價格（每百萬 token） | 輸出價格（每百萬 token） |
| ----- | -------------- | ------------------------ | ------------------------ |
| Sol   | 旗艦，最強智力 | $5                       | $30                      |
| Terra | 均衡，日常工作 | $2.50                    | $15                      |
| Luna  | 輕快，最低成本 | $1                       | $6                       |

Sol 的定價跟 Opus 4.8 差不多（輸入 5 刀、輸出 30 刀），但比 Fable 5（輸入 10 刀、輸出 50 刀）便宜了整整一半。

跑分方面，GPT-5.6 Sol 在 Terminal-Bench 2.1（終端程式設計 + Agent 工作流能力）上拿到了 88.8%，Ultra 模式更是達到了 91.9%，把 Fable 5 的 83.4% 和 GPT-5.5 的 83.4% 都甩在了身後。

![](https://pic.yupi.icu/1/image-20260710101910897.png)

除了模型本身，這次 OpenAI 在產品層面也有大動作，Codex 正式合併到 ChatGPT 裡了！

![](https://pic.yupi.icu/1/image-20260710105835836.png)

模型能力方面，我覺得最值得關注的有 3 點。

**1）Ultra 模式 - 內建多 Agent 協作**

這個跟 Opus 4.8 的動態工作流類似，但 OpenAI 把它做成了一鍵開關。

開啟 Ultra 後，模型會自動把任務拆解成多個子任務，同時派出多個子 Agent 並行處理，中間還能互相協調。

相當於以前你得手動搭一個多 Agent 編排框架才能乾的事，現在模型內建了。但代價可想而知，token 的消耗會翻好幾倍。

**2）Max 推理模式**

和 Ultra 不同，Max 模式就是單純給模型更多的思考時間，類似 Claude 的 Extended Thinking。適合那些需要深度推理但不需要並行處理的場景。

**3）更智慧的 Prompt 快取**

支援顯式快取斷點和 30 分鐘最低快取生命週期，快取命中時輸入成本打一折。對於跑長時間 Agent 任務的開發者來說，應該能夠大幅節約成本。

![](https://pic.yupi.icu/1/01_GPT-5.6%25E4%25B8%2589%25E5%25A4%25A7%25E8%2583%25BD%25E5%258A%259B%25E4%25BA%25AE%25E7%2582%25B9%25EF%25BC%259AUltra%25E5%25A4%259AAgent%25E3%2580%2581Max%25E6%25B7%25B1%25E5%25BA%25A6%25E6%258E%25A8%25E7%2590%2586%25E3%2580%2581Prompt%25E7%25BC%2593%25E5%25AD%2598_compressed_v2.png)

看到這裡，你是不是也對 GPT 5.6 充滿期待了？

不過 GPT 5.6 也有一些爭議。安全評估組織 METR 在官方部落格中披露，GPT-5.6 Sol 在跑分測試中存在「作弊」行為，利用評測系統的 Bug 來刷分，被評為歷史上檢測到的最高作弊率。OpenAI 自己釋出的 System Card 也承認 Sol 有過度主動的傾向，會未經授權就執行一些操作。

## 讓 Cursor 自動並行測試

由於要同時測試多個模型，我選擇用 Cursor 的子 Agent 能力來做測試。

給 Cursor 發一段提示詞，它會幫我同時啟動 3 個子 Agent，分別用 GPT-5.6 Sol、Claude Fable 5 和 Grok 4.5，用 **同一段提示詞** 在各自的目錄裡開發同一個專案。

這樣一來，三個模型可以使用完全相同的 Harness 工程環境，包括相同的工具、MCP 和 Skills、同樣的上下文。我還在提示詞裡運用了 Loop Engineering 的思想，要求模型寫完就自測、發現 Bug 就修復、迴圈迭代直到滿意為止。

![](https://pic.yupi.icu/1/image-20260710103421135.png)

這次我讓 AI 開發的是一個「足球對戰網頁遊戲」，名字叫 **2066 決戰世界盃**。

玩家操控一支 5 人球隊和電腦人機對戰，包含 10 個功能需求：物理引擎、AI 對手、比賽系統、使用者排行榜、戰績統計面板等等。

![](https://pic.yupi.icu/1/image-20260710110116017.png)

為什麼選擇足球遊戲作為測試案例呢？

因為它能全方位考察模型的能力：

- 物理引擎要求模型具備向量計算和碰撞檢測的數學能力
- 電腦人機要求模型能設計狀態機和決策邏輯
- Canvas 渲染考驗遊戲迴圈和幀率控制
- 後端 API 和排行榜考驗全棧工程能力

而且最終效果好不好，打一把遊戲就知道了，不需要逐行看程式碼~

提示詞中，我不對技術棧做限定，由模型自己選擇。比如物理引擎是從 0 開始寫還是用現成的庫、前端用什麼框架、資料庫選什麼，全部交給 AI 自主判斷，而且全程零人工干預。

在 AI 開發的過程中，只有 Claude Fable 5 在動手寫程式碼之前先列出了一份完整的任務計劃，逐條規劃要實現哪些模組、用什麼方案。

GPT-5.6 Sol 和 Grok 4.5 則是想了想就直接開幹了，邊寫邊調。

![](https://pic.yupi.icu/1/image-20260710105402348.png)

在提示詞的引導下，三個模型都使用了 Cursor 內建的瀏覽器來自主測試效果：

![](https://pic.yupi.icu/1/image-20260710105513163.png)

最後，三個模型全部完成了 10 個功能的開發，但速度差異非常明顯：

| 模型           | 總耗時    | 修復輪次   |
| -------------- | --------- | ---------- |
| GPT-5.6 Sol    | 9.2 分鐘  | 2 次       |
| Grok 4.5       | 10.1 分鐘 | 5 次       |

GPT-5.6 Sol 最快交卷，而且只修了 2 輪 Bug 就跑通了。Fable 5 花了將近 20 分鐘，大概是 thinking 模式花了更多時間在規劃上。說明在這種一把梭的場景下，快速動手迭代可能比詳細的前期規劃更有效。

## 程式碼質量對比

遊戲體驗聊完了，再來看看程式碼層面的差異。

技術選型方面很有意思，三個模型不約而同都選擇了手寫物理引擎，沒有一個用 matter.js 之類的現成庫。可能是因為足球遊戲的碰撞邏輯相對簡單（都是圓形碰撞），手寫幾十行程式碼就能搞定，引入一個完整的物理庫反而顯得笨重。資料庫方面 GPT 選了最輕量的 JSON 檔案儲存，Grok 和 Claude 都選了 SQLite。

雖然三個模型都實現了全部 10 個功能，但它們的工程實現風格差別很大。

| 模型           | 原始碼檔案數 | 程式碼行數 | 物理方案     | 資料庫         |
| -------------- | ---------- | -------- | ------------ | -------------- |
| GPT-5.6 Sol    | 5          | 683      | 手寫圓形物理 | JSON 檔案      |
| Grok 4.5       | 8          | 2,622    | 手寫 2D 物理 | better-sqlite3 |
| Claude Fable 5 | 5          | 1,844    | 手寫物理引擎 | SQLite WAL     |

GPT-5.6 Sol 只用 683 行程式碼就搞定了 10 個功能，程式碼密度極高。

![](https://pic.yupi.icu/1/image-20260710111618379.png)

Grok 4.5 拆了 8 個檔案、2622 行，模組化做的比較好。

![](https://pic.yupi.icu/1/image-20260710111641087.png)

Fable 5 程式碼量排在中間，1844 行，但有個問題，核心遊戲邏輯全堆在一個 33KB 的 `game.js` 裡，可維護性比較差。

![](https://pic.yupi.icu/1/image-20260710112615563.png)

人機對手的實現上，三個模型都用了規則驅動的狀態機方案，按球員角色（門將 / 後衛 / 中場 / 前鋒）分配不同行為，透過難度引數來區分三檔。

雖然實現思路高度一致，但實際效果差異很大，這說明 AI 的程式碼邏輯和執行效果之間還是有 gap 的。



## 綜合排名

最終，這次測試下來 3 個模型的排名如下：

| 排名 | 模型           | 一句話評價                                             |
| ---- | -------------- | ------------------------------------------------------ |
| 🏅 1  | GPT-5.6 Sol    | 速度最快、程式碼最精簡、操控流暢、能正常玩               |
| 🥈 2  | Grok 4.5       | 架構最規範、統計面板最好看，但換人邏輯和球場渲染有硬傷 |
| 🥉 3  | Claude Fable 5 | 球場最標準、移動端最好，但物理引擎翻車導致沒法正常遊玩 |

看到這個結果，你覺得意外麼？

Claude Fable 5 在之前我做的全棧專案測試中一直是 UI 和程式碼質量的王者，沒想到這次竟然墊底了。

我自己的理解哈，足球遊戲這種場景跟普通的 CRUD 全棧專案完全不一樣。它對物理模擬的實時性要求很高，球的位置每一幀都在變，碰撞檢測的精度直接決定了遊戲能不能玩。Claude Fable 5 的 thinking 模式可能花了大量時間在「想清楚架構」上，但在物理計算這種需要精確調參的場景下，反而不如 Sol 那種「快速寫完、馬上跑、發現問題就修」的 Loop 風格來得有效。

Sol 只修了 2 輪 Bug 就跑通了，Fable 5 雖然花了 20 分鐘，但物理引擎依然有明顯的瞬移問題。這說明花時間多不代表質量高，至少在這種需要快速看到效果的小遊戲場景下，快速迭代驗證比深度規劃更管用。

這告訴我們：**最貴的模型效果未必最好，也未必最適合你的任務。** 還是得按自己的實際場景來選模型。

時間有限，就先給大家分享這次測試。

最後，結合我自己的使用體感，給大家一些模型選擇的建議：

- 日常開發、一把梭小專案，選 GPT-5.6 Sol。程式碼精簡、效率極高，價格只有 Fable 5 一半。
- 長任務、複雜架構設計，選 Claude Fable 5。不過它有點像讓教授來做初中數學題，簡單的事反而想複雜了，遇到需要快速驗證效果的場景可能會水土不服。
- 預算有限，選 Grok 4.5。每百萬 token 輸入只要 2 美元、輸出 6 美元，比 Sol 便宜 5 倍、比 Fable 5 便宜近 10 倍，架構設計也比較規範。之前很多人都不看好 Grok，但這次新出的 Grok 4.5 在 Cursor 論壇上的反饋明顯好了很多，算是打了個翻身仗。



## 寫在最後

不過說實話，就從這個例子來看，這三個模型寫出來的遊戲都還差了點意思。沒有一個能稱得上「有足球戰術智慧」的，要麼不會主動進攻，要麼隊友集體掛機，要麼球直接瞬移。

想讓 AI 寫一個真正好玩的遊戲，目前還是得花精力在迭代反饋上，指望一把梭出精品還為時尚早。

不過這樣也好，說明程式設計師暫時還不用擔心被 AI 搶走遊戲開發的飯碗。
