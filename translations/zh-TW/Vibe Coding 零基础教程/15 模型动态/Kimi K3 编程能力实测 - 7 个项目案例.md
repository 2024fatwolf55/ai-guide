不過在 DeepSWE 和 FrontierSWE 這類更復雜的工程基準上還跟 Fable 5 和 Sol 有差距。

## 安裝 Kimi Code

先到 [Kimi Code 官網](https://www.kimi.com/code) 複製一行安裝命令，在終端執行就好：

![](https://pic.yupi.icu/1/1784171620008-ffaf4ccb-8b91-4559-94e7-b8bf142c3a0f-20260717144613039.png)

安裝完成後，在終端輸入 `kimi` 進入 Kimi Code，然後輸入 `/login` 命令透過網頁登入：

![](https://pic.yupi.icu/1/1784211829361-e461a0d2-76c7-4033-b417-3d201343ac94-20260717144613127.png)

登入成功後，輸入 `/model` 切換模型為 K3。目前 K3 的 thinking 僅支援 `max` 模式，後續會開放 `low` 和 `high`：

![](https://pic.yupi.icu/1/1784211934461-a4897b78-aa9a-423c-b461-c2177b7bff4c-20260717144613240.png)

切換成功，可以在下方看到當前模型已經是 K3，上下文視窗顯示 1M，這下可以狠狠造了~

![](https://pic.yupi.icu/1/1784211973313-458de0b1-1f05-41d7-b0b3-6c99f5a66811-20260717144613435.png)

Kimi Code 跟 Claude Code 一樣，支援 Skills 技能擴充套件。由於我之前很多技能都裝在了 AI 程式設計工具通用的 `~/.agents/skills/` 目錄下，Kimi Code 會自動掃描載入，不用再重新安裝了。

在 Kimi Code 中輸入 `/skill` 可以檢視已安裝的技能：

![](https://pic.yupi.icu/1/1784172987287-9e55701a-3045-467e-b093-02a4a98db463-20260717144613497.png)

接下來的測評中，我會用到 Context7 的文件搜尋技能、Firecrawl 的聯網搜尋和網頁抓取技能、browser-use 瀏覽器操控技能等等。

環境準備完畢，下面開始實戰。



## 專案實戰測評

這次，我準備了 **7 個專案** 來測試 K3 的程式設計能力，從簡單的前端頁面逐步升級到複雜的全棧產品：

1. 互動式動畫講解網站
2. 3D 版動畫知識講解
3. 文案拆解為網頁 PPT
4. 網頁 PPT 生成工具（內建 AI 大模型）
5. 足球對戰網頁遊戲（橫評對比）
6. 以撒的結合肉鴿遊戲
7. 全棧 AI 程式設計工具（復刻 Cursor）

下面挨個兒來看。



### 1、互動式動畫講解網站

第一個專案，讓 K3 生成一個用互動式動畫講解知識的網站。

以講解 K3 模型引入的「注意力殘差」機制為例，讓模型自己用動畫解釋自己的核心技術。

提示詞中，我告訴 AI 先用 Firecrawl 技能聯網搜尋注意力殘差的技術細節，確保講解內容準確，不會因為訓練資料的時效性而瞎編：

![](https://pic.yupi.icu/1/image-20260717111349321-20260717144613538.png)

K3 完成任務後，可以看到它確實呼叫了 Firecrawl 聯網搜尋了相關論文和解讀，還透過截圖驗證了桌面端和移動端的渲染效果，發現問題後自主修復了佈局細節。

這其實就是 K3 的多模態工程能力在發揮作用，官方部落格裡管這個叫「vision in the loop」，開發完截圖看一眼效果對不對，不對就改，相當於 AI 自帶了一雙眼睛來檢查自己的作品。

![](https://pic.yupi.icu/1/1784182068361-f421d08f-a157-42f0-8cc3-606e69afa6f7-20260717144613862.png)

來看看成品效果，K3 把注意力殘差的原理拆分成了幾個階段來講解，每個階段配有互動式動畫。

第一部分用了「煮湯」的類比來解釋問題。標準 Transformer 的殘差連線會把每一層的輸出都等權加到資訊流裡，層數一多，早期層的訊號就被後面的資訊淹沒了。網站把這個過程類比成 100 位廚師接力往一個大鍋里加調料，到最後第一位廚師加的高湯原味幾乎嘗不到了。

使用者可以透過滑塊控制加料速度，實時看到資訊如何被稀釋：

![](https://pic.yupi.icu/1/1784181755536-d293e9bf-8eb5-4ad8-af7f-4eef6da47067-20260717144614356.png)

第二部分進入核心機制的互動演示。使用者可以拖動滑塊給不同層分配注意力權重，實時看到 softmax 歸一化後的注意力分佈變化：

![](https://pic.yupi.icu/1/1784181771104-8becb2f1-a011-4d45-9741-3daf5bc35a50-20260717144614853.png)

最後還有分塊注意力殘差的工程落地方案視覺化，使用者可以調節總層數和塊數，直觀感受分塊策略對視訊記憶體的影響：

![](https://pic.yupi.icu/1/1784181796772-02fc0cdb-545f-431b-a2c7-f64a0db97847-20260717144614997.png)

一個提示詞就搞定了，前後不到 5 分鐘。

我對這個效果是很滿意的，點和線之間的連線很準確，動畫過渡也很流暢，審美線上。

之前我都是用 Claude 做這種互動式動畫網站，還經常會有元素錯位的情況。K3 在前端這塊確實有兩把刷子，難怪能在 Arena 前端榜拿第一，之後這種動畫完全可以放心交給它來做了。



### 2、3D 版動畫知識講解

還是用跟第一個測試同樣的知識點，這次換成 3D 場景來呈現。

提示詞中除了讓 AI 聯網搜尋，還要求用 Context7 查詢所用 3D 庫的最新文件，避免用過時的 API：

![](https://pic.yupi.icu/1/image-20260717111408539-20260717144615047.png)

這次執行前，我先開啟了 `/yolo` 模式。

開啟後，AI 會自動批准安全的工具呼叫，不用我一個個手動點確認了，適合跑這種已知安全的開發任務：

![](https://pic.yupi.icu/1/1784212052027-a60efe1d-787b-4e1c-9ff3-3f6618947f21-20260717144615340.png)

來看看成品效果。介面沒有多餘的元素，重點全在 3D 動畫演示上。左下角有步驟控制面板，可以逐步推進講解：

![](https://pic.yupi.icu/1/1784181948833-d092b7b8-abc2-42c4-9c8c-bfcd38cef470-20260717144616007.png)

我可以透過滑鼠拖拽自由調整視角，3D 空間中的節點和連線把 Transformer 各層的資訊流動展示得很清晰：

![](https://pic.yupi.icu/1/1784181917700-09e53717-bbf1-42c1-9f4e-c17413ace9f1-20260717144616347.png)

兩個動畫講解網站都是單次提示詞就搞定的，速度很快，效果也不錯。

這類前端創意專案本來就是 AI 程式設計最擅長的場景，Kimi 在前端生成方面的口碑一直不錯，K3 延續了這個優勢。



### 3、文案拆解為網頁 PPT

我做影片教程時，偶爾會需要把文章內容做成演示畫面。

但手動做 PPT 太慢了……

這次，我乾脆直接把技術文章丟給 K3，讓它按照文章講解順序，拆解成一個可以全屏演示的網頁 PPT，後續可以當做影片錄製的畫面素材。

提示詞很簡單：

![](https://pic.yupi.icu/1/image-20260717111421384-20260717144616722.png)

很快 AI 就搞定了，成品效果很有科技感。你會發現，K3 自動識別了文章的結構層次，每頁 PPT 都標記出了重點內容，程式碼塊也用了高亮顯示：

![](https://pic.yupi.icu/1/1784182284219-2a17237b-b739-4def-ac14-4361bc39fd3d-20260717144617743.png)

以後要給別人講東西的時候，比起甩一篇密密麻麻的文章過去，用這種 PPT 來輔助表達清晰多了。

此外，翻頁動畫比較絲滑，支援鍵盤左右鍵和空格翻頁。移動端的佈局也很合理：

![](https://pic.yupi.icu/1/1784182350543-fb631ebf-e7aa-4bdc-9d69-4988b5869e1b-20260717144617905.png)

如果你希望 PPT 中有圖片，跟 AI 說一下把文章中的圖片新增到合適的位置就好。



### 4、網頁 PPT 生成工具（內建 AI）

前面 3 個都是開胃小菜，更看重的是 K3 的前端創意和資訊拆解能力。

接下來要測測它的全棧工程能力了，讓 AI 開發一個整合大模型的完整應用。

上一個案例是給定一篇文章生成 PPT，那能不能把這個能力做成一個通用工具呢？

使用者貼上任意文案，後端呼叫 AI 大模型拆解內容，前端渲染成可演示的網頁 PPT，還支援切換主題和匯出 HTML。

這次使用 Kimi Code 內建的 `/goal` 命令來執行，完整提示詞如下：

![](https://pic.yupi.icu/1/image-20260717111459584-20260717144618089.png)

這個命令會讓 AI 進入自主目標模式，跨多輪持續工作直到任務完成，不需要人工干預，很適合這種複雜的長程開發任務。

注意，提示詞裡我直接把 Kimi Code 的 API Key 寫進去了，這樣 AI 能自主調通大模型介面完成測試：

![](https://pic.yupi.icu/1/1784212180951-43c52af1-007f-4f1b-8582-78edd9c7defc-20260717144618309.png)

K3 完成後，從日誌中可以看到它做了兩組端到端的 Playwright 測試，桌面端和移動端都驗證透過了。API Key 也很貼心地寫入了 `.env` 並加入了 `.gitignore`，不會洩露到版本控制裡：

![](https://pic.yupi.icu/1/1784182502815-67d51dcf-29fc-438a-a725-88357a126380-20260717144618858.png)

看下成品介面。非常精簡，核心就是一個貼上文案的輸入框。我把之前寫過的 Loop Engineering 教程粘進去，點選生成 PPT：

![](https://pic.yupi.icu/1/1784182758933-6b75a1c9-f922-437b-8c85-0115cdea665e-20260717144619030.png)

AI 把文案拆成了 11 頁 PPT，每頁都有標題和要點：

![](https://pic.yupi.icu/1/1784182820142-e3568d65-e8d9-4f9d-80a6-e35fb240f07e-20260717144619691.png)

可以隨時切換內建的主題配色，全屏演示和匯出 HTML 功能也都能正常執行：

![](https://pic.yupi.icu/1/1784182924437-2dfeda13-6f0f-4979-85ca-515c6286a63f-20260717144620501.png)

美中不足的是，開發出來的應用比較簡單，沒有給大模型加工具呼叫等 Agent 能力，所以得到的 PPT 有點過於精簡了。

不過至少核心業務流程是完全跑通的，從貼上文案到生成、預覽、切換主題、匯出，每個環節都能正常工作。作為初版 demo 已經夠用了，後面再讓 AI 迭代最佳化就好。



### 5、足球對戰網頁遊戲

之前 GPT-5.6 釋出的時候，我寫過一篇《頂級國外模型橫評對比》的文章，用同樣的提示詞讓 GPT-5.6 Sol、Claude Fable 5、Grok 4.5 三個模型同時開發了一個「2066 決戰世界盃」足球遊戲。

這次用完全一致的提示詞讓 K3 來做，來一波橫向對比，看看國產模型能不能問鼎巔峰？

同樣用 `/goal` 模式執行，提示詞要求用 Loop Engineering 的方式推進，先搭最小可玩版本，每完成一個功能就自測，發現問題就修，交付前做完整驗收。

![](https://pic.yupi.icu/1/1784212215001-dd8b856c-c210-458a-9028-fbab5050ace4-20260717144620566.png)

過了大約 17 分鐘，K3 完成了目標。

技術選型上選了 Node.js + Express + SQLite 做後端，前端用 Canvas 手寫了物理引擎，這個選擇跟之前 GPT-5.6 Sol 的思路一致，對於這種量級的遊戲來說是合理的：

![](https://pic.yupi.icu/1/1784182979895-6c1425b5-1b1e-49a8-8e7a-cd4e25cbd3d7-20260717144620711.png)

來試玩一下，西班牙大戰阿根廷！

賽前設定介面做得中規中矩，能選擇比賽難度、時長、隊名和顏色：

![](https://pic.yupi.icu/1/1784183295400-9db9775e-5666-400f-994e-0eeb6b77b4f8-20260717144620787.png)

進入比賽，球場佈局還算標準，也能夠正常切換球員和踢球。

不過人機的演算法有點簡單，我方只有當前控制的球員單槍匹馬往前衝，其他隊友全在後方觀戰吃瓜。而人機對手的策略就是造人牆堵著我：

![](https://pic.yupi.icu/1/1784183345124-cfa1e19d-6ee3-4487-b31b-c164d1f53d00-20260717144621824.png)

守門員的防守可以說是滴水不漏，總是能卡在我射門的方向。結果我玩了好幾局中等難度，都是 0 比 0 平局：

![](https://pic.yupi.icu/1/1784183683653-faafeeba-b8fd-46df-8182-fee7303188c2-20260717144622038.png)

跟之前測的其他模型對比一下。

先說好的方面。K3 的操控和物理引擎沒有明顯 Bug，球不會瞬移也不會穿模。對比一下 Claude Fable 5，物理引擎翻車了，球經常會瞬移，根本沒法正常玩耍。

![](https://pic.yupi.icu/1/1783648857986-4d1edca9-1496-494c-80b1-096690b34bc4-20260717144622560.png)

對比 Grok 4.5，存在球場渲染的硬傷，而且換人邏輯不順暢，經常切換到離球最遠的隊友身上：

![](https://pic.yupi.icu/1/1783648020795-d1809bda-6c3c-4e36-babf-a3f6e9e494e1-20260717144623018.png)

K3 在「能不能正常玩」這一點上是穩穩過關的，體驗比 Fable 5 和 Grok 4.5 都好。

不過跟 GPT-5.6 Sol 比，還是有差距的。GPT-5.6 Sol 只用了 9 分鐘就完成了開發，人機雖然也不太聰明，但至少有些進球的機會。

![](https://pic.yupi.icu/1/1783647330206-bb64786d-95d9-41e5-9d53-4fb42ffdd9da-20260717144623818.png)

K3 的人機對手戰術智慧明顯不如 Sol，從遊戲性角度來說離「好玩」還有距離。

整體來看，K3 在這個專案上處於中上游的水平，一個國產模型能做到這樣，已經是超出我的預期了。



### 6、以撒的結合肉鴿遊戲

接下來是一個更有挑戰性的遊戲專案。

以撒的結合是我小孩兒時代很愛玩的一款肉鴿遊戲，這次讓 K3 來複刻它的核心玩法，包括隨機地牢生成、射擊戰鬥、道具系統、多種敵人和 Boss。

提示詞中要求先用 Firecrawl 搜尋以撒的結合的遊戲機制和美術風格資料，用 Context7 查詢所用遊戲框架的文件：

![](https://pic.yupi.icu/1/1784212259593-16d5f314-9b40-4651-851b-c61dcf8d8c7c-20260717144625002.png)

K3 完成目標後，反饋說它用了 Firecrawl 研究了遊戲機制與美術風格，用 Context7 查了所選遊戲引擎的最新文件，並且透過 Playwright 在每一步完成後自動試玩、截圖驗證，修復了好幾個問題。最終測試已實現從開局到擊敗三層 Boss 通關的完整流程：

![](https://pic.yupi.icu/1/1784185068039-17f4980f-618e-46eb-a1c2-68f752637f5f-20260717144627576.png)

來試玩一下。

雖然介面看起來簡陋，但基本玩法是完全跑通的，可以發射子彈打擊怪物：

![](https://pic.yupi.icu/1/1784190076766-03662fe2-7400-4938-87d1-422f3d992bd7-20260717144628318.png)

玩過原版的朋友應該會注意到一個小細節，AI 生成的人物形象是有眼淚的，致敬了原版以撒的角色設計：

![](https://pic.yupi.icu/1/1784184670536-65377053-11ea-4c54-b0f6-e48318b1d955-20260717144629472.png)

遊戲中可以殺怪、吃道具、開寶箱，拾取道具后角色的攻擊力、射速等屬性會實時變化，螢幕上方還會顯示當前狀態：

![](https://pic.yupi.icu/1/1784184864353-d099812b-21e7-4cdc-a0e6-43fe80b45a24-20260717144630414.png)

敵人方面做了多種不同型別，有追著你跑的、有遠端射擊的、有對著你橫衝直撞的，甚至還有會放彈幕和召喚小怪的 Boss！

![](https://pic.yupi.icu/1/1784184823083-d46122a9-8b45-4719-a69d-c8eeda7906aa-20260717144631052.png)

總的來說，整個遊戲的玩法鏈路已經跑通了，從開局到清房間、撿道具、打 Boss 都沒問題。

**別忘了，我們現在只用了一輪提示詞，沒有做任何後續迭代。**

如果後面想正兒八經地做這個遊戲，只需要再多提供一些美術素材，增加更多道具、怪物和關卡的設計就行了。



### 7、全棧 AI 程式設計工具

最後一個專案，直接把難度拉滿！

我讓 K3 基於 VS Code 的開原始碼，開發一個類似 Cursor 的 Web AI 程式設計工具，支援 Editor Window 程式碼編輯器和 Agents Window 對話工作臺兩種模式。

提示詞中要求先用 Firecrawl 搜尋 Cursor 3 的產品設計，再用 Context7 查詢 VS Code 擴充套件 API 文件：

![](https://pic.yupi.icu/1/1784212308866-3738611f-e9c5-4546-a161-d96611a13d68-20260717144631641.png)

這個任務跑了半個多小時。K3 先克隆了 VS Code 原始碼作為參考，透過 Firecrawl 搜尋了 Cursor 官方部落格和第三方指南瞭解產品設計，然後一步步構建了完整的 Web IDE，每完成一步都透過瀏覽器截圖來驗證效果：

![](https://pic.yupi.icu/1/1784190241907-868bceef-a1b5-4fe6-80b9-536ffc0d0738-20260717144632037.png)

來看成品。

預設開啟的是 Editor Window，也就是程式碼編輯器介面。有檔案樹、多標籤頁和語法高亮，可以正常瀏覽和編輯程式碼：

![](https://pic.yupi.icu/1/1784190810038-c3d24d7d-f500-46ff-bb62-b2c9205005f2-20260717144633410.png)

切換到 Agents Window，這就是我們非常熟悉的 AI 對話工作臺了。

我讓它開發一個貪吃蛇遊戲，可以看到 AI 呼叫了 `RUN_COMMAND` 工具，先執行 `ls -la` 來了解當前專案結構：

![](https://pic.yupi.icu/1/1784190877508-637d8580-e58d-4810-b54a-d740da2b6be6-20260717144634958.png)

接下來 AI 會執行更多命令，分析當前專案的檔案結構，然後在當前工作空間基礎上完成開發任務：

![](https://pic.yupi.icu/1/1784190957997-f207d1e5-3b65-4005-9a6e-392ecd25f328-20260717144635325.png)

雖然跟 Cursor 這種成熟產品比還有很大差距，但核心的 Editor + Agent 雙視窗能力是跑通的。

這個專案是 7 個 Case 裡最複雜的長程任務，K3 能夠理解 VS Code 這麼龐大的程式碼庫，從聯網搜尋產品設計、查閱 API 文件到獨立完成開發，半個多小時一路跑下來沒有卡死或跑偏，這對模型的長上下文穩定性和自主規劃能力要求很高。



## 寫在最後

7 個專案全部跑完了，聊聊我的真實感受。

首先，**K3 最讓我驚喜的地方是穩定性**。7 個專案全部直接跑起來就能用，前後端啟動沒有報錯、核心功能都是通的。

之前我測其他國產模型的時候，經常會遇到依賴裝不上、服務啟動報錯、還得再讓 AI 修一輪才能跑的情況。

K3 在這方面明顯更穩了，讓我想到了 Claude Opus 剛出的時候，「能用」這一關穩穩過了。

模型的執行速度也還不錯，簡單專案基本都在幾分鐘內搞定，最複雜的 AI IDE 專案用了半個多小時。

**前端能力是 K3 最能打的方向。** 從 Arena 前端競技場的資料來看，K3 確實在前端領域超越了 Fable 5 和 Sol。我自己實測下來也有同感，動畫網站的審美和準確度比我之前用 Claude 做的還好，PPT 的排版和配色也很有設計感。

**但是，整體工作完成度跟海外頂尖模型還是有差距的。**

比如讓它做個遊戲，雖然能玩，但跟能釋出的成品有距離。想做出 Kimi 官方演示的這些遊戲大作，還需要再進行多輪迭代最佳化。

![](https://pic.yupi.icu/1/image-20260717111152646.png)

再看看大家最關心的成本。[K3 官方部落格](https://www.kimi.com/zh-cn/blog/kimi-k3) 公佈的 API 定價：

| 模型           | 輸入（快取命中） | 輸入（快取未命中） | 輸出              |
| -------------- | ---------------- | ------------------ | ----------------- |
| Kimi K3        | $0.30/百萬 token | $3.00/百萬 token   | $15.00/百萬 token |
| Claude Fable 5 | $2.50/百萬 token | $10.00/百萬 token  | $50.00/百萬 token |

由於 Kimi 的 Mooncake 分離式推理架構在程式設計場景下快取命中率超過 90%，相當於絕大多數輸入只按 $0.30 計費，這個價格比 Fable 5 便宜了一個數量級。

我自己是 Kimi Code 的滿配套餐（Vivace），跑完這 7 個專案，包括半小時的 AI IDE 開發、17 分鐘的足球遊戲、各種前端動畫和全棧應用，本週用量才花了 **2%**。以後真的是隨便 Vibe Coding 了，百萬上下文隨便造。

![](https://pic.yupi.icu/1/image-20260717141420121-20260717144636656.png)

對於國內開發者來說，不用折騰海外支付、不用擔心封號，直接訂閱就能用上百萬級上下文的程式設計模型。而且大多數日常開發任務根本用不到 Claude Fable 5 這種模型，寫個工具、做個網站、搭個原型、辦公自動化，K3 的能力完全夠用。

順便提一下，K3 除了在 Kimi Code 中使用，也可以在 VS Code 外掛中使用，或者透過 CC Switch 接入 Claude Code 和 Codex 等工具。

![](https://pic.yupi.icu/1/image-20260717102305034-20260717144636779.png)

最後說點心裡話。

我測過很多國產模型，大部分時候的感受是湊合能用、還差點意思。但這次測 K3，是我第一次覺得一個國產程式設計模型真的能讓我在日常工作中用起來，而且用得挺舒服的。

穩定性足夠、前端能力甚至超越了海外頂尖模型、成本只有 Claude 的幾分之一，還支援百萬上下文和多模態能力。

雖然在複雜任務的精細度上跟 Fable 5 和 Sol 還有差距，但 K3 的釋出，給了我們信心：**國產模型在程式設計領域終於站起來了！**

如果你也對 AI 程式設計感興趣，不妨親自動手試試不同的模型和工具，用實際專案來感受它們的能力差異。AI 程式設計的世界變化很快，保持好奇心，多動手實踐，你一定能找到最適合自己的程式設計搭檔！
