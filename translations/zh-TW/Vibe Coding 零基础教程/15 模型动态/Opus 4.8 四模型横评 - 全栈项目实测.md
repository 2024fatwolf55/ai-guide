# Opus 4.8 四模型橫評 - 全棧專案實測

剛剛 Anthropic 又釋出了新模型 Claude Opus 4.8，從 2 月的 Opus 4.6 到 4 月的 Opus 4.7，短短 3 個月就迭代了 3 版！

![](https://pic.yupi.icu/1/image-20260529132455116.png)

每次大模型一更新，全網都在搬官方的跑分資料、翻譯一下更新日誌就完事了。

但跑分高不代表實際好用，我還是更想親自測一測，哪怕已經發如雨下……

![](https://pic.yupi.icu/1/%25E5%25A4%25B4%25E7%25A7%25833%25E6%25A0%25B9.jpeg)

正好最新的 Claude Opus 4.8 已經能在 Cursor 裡用了，我乾脆把 Opus 最近三代（4.6、4.7、4.8）和當紅的 GPT-5.5 放到一起，用同一個提示詞開發同一個全棧專案，看看到底誰最能打。

開始之前，先介紹一下本次 Opus 4.8 的更新，也請大家預測一下最終的測試結果~



## Opus 4.8 更新了什麼？

Opus 4.8 的定價和 Opus 4.7 一樣，每百萬 token 輸入 5 美元、輸出 25 美元，上下文依然是 100 萬 tokens。

跑分這塊本來我都懶得看了，反正 Opus 每次更新都是往上漲。不過和 GPT-5.5 的對比還是值得關注的，程式設計能力方面，SWE-bench Pro（Agent 程式設計能力）從 4.7 的 64.3% 提升到 69.2%，大幅領先 GPT-5.5 的 58.6%。不過在 Terminal-Bench 2.1（終端程式設計能力）上，GPT-5.5 以 78.2% 仍然領先 Opus 4.8 的 74.6%。

![](https://pic.yupi.icu/1/image-20260529130434887.png)

這次更新我覺得最值得關注的有 3 點：

1）動態工作流：Claude Code 裡可以一次性派出幾百個並行子 Agent，最多 16 個同時跑、單次上限 1000 個 Agent。適合大規模程式碼遷移這種硬骨頭活兒。

不過大多數使用者應該用不上這個功能，就好比你開了個公司，也沒必要一次性僱幾百個人，日常開發哪來這麼大的遷移需求。

2）程式碼自查能力暴漲：官方說 Opus 4.8 漏檢程式碼缺陷的機率比 4.7 降低了 4 倍。也就是說 AI 寫完程式碼之後，自己就能發現更多 Bug，一把梭跑通的成功率更高了。

3）Fast Mode 大降價：Fast 模式可以讓同樣的模型處理速度翻倍，而且比之前的 Fast Mode 便宜 3 倍。

看資料是一方面，AI 程式設計模型好不好用，還是得拿真實專案來檢驗。

不過正式開測之前，先說個最近跟 Claude 有關的樂子。

有人發現用 Anthropic 官方 API（注意是 **官方 API**，不是中轉站）直接調 Claude，中文問它「你是什麼模型？」，它竟然一本正經地回答「我是通義千問」。據說換個問法，它還會說自己是 DeepSeek。

![](https://pic.yupi.icu/1/HJbHfIubYAAPU8F-20260529140327405.jpeg)

我盲猜一個原因，API 呼叫沒有像網頁端那樣的系統提示詞來錨定身份，而中文網際網路上「我是通義千問 / DeepSeek」的訓練資料遠比「我是 Claude」多得多。模型在沒有身份提示的情況下，自然就輸出了機率最高的那個回答。

不過也有可能，Claude 就是蒸餾了國產模型，好一個迴旋鏢~

![](https://pic.yupi.icu/1/HJbtnTCaMAEBJpr-20260529140327435.jpeg)

好了說回正題，這些頂級模型在實際程式設計中表現到底如何呢？



## 讓 Cursor 自動並行測試

如果讓你來做 4 個模型的程式設計能力對比，你會怎麼做呢？手動一個一個跑麼？

那也太累了，我選擇直接讓 AI 幫我測。

現在 Cursor 這類 AI 程式設計工具已經內建了「子 Agent」能力，可以並行啟動多個獨立的 AI 任務，而且每個任務可以指定用不同的模型。

相當於 Cursor 是一個包工頭，我下一個指令，它就幫我同時排程 4 個不同的「工人」幹活。

我只需要發一段提示詞，Cursor 就自動幫我同時啟動 4 個子 Agent，分別用 Opus 4.6、4.7、4.8 和 GPT-5.5，全部開到 High thinking 檔位，用同一段提示詞在各自的目錄裡開發同一個專案。

我讓 AI 開發的專案是一個「TaskFlow 任務管理看板」全棧應用，類似簡化版飛書看板，包含 7 個功能需求：使用者註冊登入、三列看板拖拽、任務增刪改查、資料圖表面板、搜尋篩選、暗色 / 亮色主題切換、響應式設計。技術棧是 React + TypeScript 前端 + Python FastAPI 後端 + SQLite 資料庫，前後端分離。

![](https://pic.yupi.icu/1/1780023443848-2d39ddfb-8739-4e80-a723-514b71c3bda9-20260529140327470.png)

再次強調，4 個模型用的是完全一樣的提示詞，而且全程不做任何人工干預。我主要關注這幾個指標：UI 設計水平、功能完成度、程式碼質量和架構合理性。

## 功能實現對比

功能方面就不一一展示了，4 個模型全部實現了 7 個功能需求：註冊登入、看板拖拽、任務管理、圖表、搜尋、主題切換、響應式，都能正常使用。

畢竟主流模型一把梭全棧專案已經不是什麼新鮮事了，這些功能都不復雜，很難拉開區分度。



## 程式碼質量對比

既然功能都一樣、UI 差異也是見仁見智，那真正能拉開差距的就是程式碼質量了。

我讓 AI 幫我分析了 4 個專案的程式碼結構，還是能發現明顯的區別的。

首先，4 個模型的專案結構出奇地一致，甚至連檔名都幾乎一模一樣。一方面應該是我提示詞限定技術框架的原因，另一方面看來這些頂級模型的程式設計思路已經高度趨同了，大家都在往同一套最佳實踐上靠攏。

![](https://pic.yupi.icu/1/1780029867213-f06ef0ec-8f8e-4287-b94c-5932dca00be6.png)

看看生成的程式碼規模：

| 模型     | 原始碼檔案數 | 程式碼行數 |
| -------- | ---------- | -------- |
| Opus 4.6 | 25         | 1,865    |
| Opus 4.7 | 32         | 2,259    |
| Opus 4.8 | 33         | 2,701    |
| GPT-5.5  | 13         | 1,221    |

顯然，Opus 4.8 程式碼量最大，GPT-5.5 最精簡。

但程式碼多不一定是好事，少也不代表差。關鍵還是看架構是否清晰、有沒有明顯的 Bug。下面逐個來看。

1）**Opus 4.7 的架構是最清晰的** 

後端拆了 3 個 router（auth、tasks、stats），前端狀態管理用獨立的 store 檔案，註冊和登入分頁面，有專門的 AppLayout 佈局元件，axios 請求也做了集中封裝。分層非常規整，拿去做團隊專案也沒問題。

2）**Opus 4.8 拆得最細**

有獨立的 context 目錄、FilterBar 元件、工具模組，程式碼量最大。另外 CORS 跨域配置直接配了 `allow_origins=["*"]`，安全意識差了點。

3）**GPT-5.5 走的是極簡路線**

只用了 Opus 4.8 一半行數的程式碼就搞定了全部功能，但缺點是後端所有路由都寫在 `main.py` 一個檔案裡，300 多行擠在一起。能跑是能跑，就是後面要改的話會比較頭疼。

4）**Opus 4.6 功能完整，但有 2 個 Bug**

一個是缺少 React import 導致白屏，另一個是 Tailwind v4 的 CSS 層級衝突，說明 4.6 對最新框架版本的適配還不夠。



## 綜合排名

最終，這次測試下來 4 個模型的排名如下：

| 排名 | 模型         | 一句話評價                                  |
| ---- | ------------ | ------------------------------------------- |
| 🏅 1  | **Opus 4.7** | 架構最清晰，UI 最精緻，程式碼零缺陷，開箱即用 |
| 🥈 2  | **Opus 4.8** | 程式碼量最大最詳盡，但有檔案遺漏和 CORS 問題  |
| 🥉 3  | **GPT-5.5**  | 1221 行極簡通關，但後端單檔案堆砌不利於維護 |
| 4    | **Opus 4.6** | 功能完整但有 2 個白屏 Bug，對新框架適配不足 |

看到這個結果，是不是有點意外？

最新的 Opus 4.8 竟然沒拿第一，怕不是更新了個寂寞嘛？

![](https://pic.yupi.icu/1/image-20260529135020413.png)

我的理解是，4.8 這次更新的重心不在「寫更美觀的程式碼」，而在 Agent 可靠性和長時間無人監督的任務執行上。動態工作流、程式碼自查能力這些特性，在大型專案和企業級場景裡可能更有價值，但在「一把梭做個全棧專案」這種場景下，4.7 反而表現更穩。

**所以大家不要盲目追新，還是按自己的實際需求來選模型。**

時間有限，就先給大家分享這次測試。結合我自己的使用體感，我的建議是：

- 日常開發、一把梭小專案：選擇 Opus 4.7 或 4.8 都行，4.7 的 UI 更好看，4.8 更省心（自查能力強）
- 終端操作、命令列自動化：選擇 GPT-5.5，之前我做 Codex 教程的時候拿 GPT-5.5 用作辦公 AI 還是很香的
- 大規模程式碼遷移重構：選擇 Opus 4.8，它的動態工作流是殺手鐧

而且我發現一個趨勢，Opus 4.8 越來越像 GPT-5.5 了，都在朝著「用最務實的方式把活幹完」的方向走，對 UI 美感之類的「額外加分項」反而不太上心。

不過我是真的不希望 Claude 繼續朝著這個方向發展下去，大模型之間多搞些差異化，往不同的方向去強化各自的優勢，給使用者更多選擇，我覺得才更好。



## 寫在最後

透過這次橫評可以看到，不同模型在 AI 程式設計方面各有優劣，不能盲目追新，要根據實際需求來選擇。

學會了這些內容，你就能在實際專案中更合理地選擇和搭配 AI 模型，提升開發效率。
