## 一、什麼是 Loop Engineering

Loop Engineering 這個詞翻譯過來就是「迴圈工程」。簡單來說，就是你設計一套自動運轉的系統，讓它代替你去給 AI 下達指令、檢查 AI 的輸出、記錄完成進度、決定下一步該做什麼，然後不斷迴圈執行，直到達成你預設的目標。

![](https://pic.yupi.icu/1/01_Loop_Engineering%E6%A0%B8%E5%BF%83%E6%A6%82%E5%BF%B5%EF%BC%9A%E4%BD%A0%E8%AE%BE%E8%AE%A1%E7%B3%BB%E7%BB%9F%E8%AE%A9%E5%AE%83%E4%BB%A3%E6%9B%BF%E4%BD%A0%E7%BB%99AI%E4%B8%8B%E6%8C%87%E4%BB%A4_compressed_v1.png)

以前的 AI 程式設計模式，就像開手動擋的車。踩油門、換擋、轉彎，每一步都靠你自己操作。你給 AI 一句提示詞，AI 回你一段程式碼，然後停下來等你下一條指令。**你不說話，它就不工作。**

Loop Engineering 的模式，更像是自動駕駛。你提前設定好目的地和安全規則，車會自己開，遇到紅燈自己停、路況變了自己繞、到了目的地自動停車。你只需要偶爾看一眼儀表盤，確認方向沒問題就行。

也就是說，你從「一句一句手動提示 AI」的操作者，變成了「設計迴圈規則」的管理者。

![](https://pic.yupi.icu/1/02_%E6%89%8B%E5%8A%A8%E6%8F%90%E7%A4%BAAI_vs_%E8%AE%BE%E8%AE%A1%E5%BE%AA%E7%8E%AF%E8%A7%84%E5%88%99%E7%9A%84%E5%AF%B9%E6%AF%94_compressed_v1.png)



### Loop 的 3 大核心

可能有人會問：Loop 不就是個定時任務嗎？讓模型反覆執行同一個操作就行了吧？

當然不是！

沒有判斷能力的迴圈，AI 可能會把錯誤當成正確答案繼續往下跑，越跑越偏。那跟 cron 定時指令碼沒區別，算不上 Loop Engineering。

一個真正靠譜的 Loop 需要 3 樣核心的東西：

1）明確的目標和停止條件

你得告訴 Loop 什麼時候算完成，而且這個完成標準必須是 **可驗證的**。比如所有測試透過、lint 零報錯、所有檔案都處理完，這些都是好的停止條件。而「把程式碼最佳化一下」就不行，因為沒人知道什麼叫最佳化好了。

2）反饋閉環

每輪迴圈結束後，Loop 得檢查這一輪的結果，判斷是繼續跑下一輪還是停下來。最常見的做法是跑完程式碼後自動執行測試，測試沒過就繼續修，測試過了就停止。

3）狀態記憶

AI 的對話視窗是有限的，關掉就沒了。Loop 需要一個外部檔案來記錄當前進度，比如哪些任務做完了、哪些還沒做、上一輪迴圈的結論是什麼。這樣即使中間斷了重啟，也不會從零開始。

![](https://pic.yupi.icu/1/03_Loop%E7%9A%843%E5%A4%A7%E6%A0%B8%E5%BF%83%E8%A6%81%E7%B4%A0%EF%BC%9A%E7%9B%AE%E6%A0%87%E5%81%9C%E6%AD%A2%E6%9D%A1%E4%BB%B6%E3%80%81%E5%8F%8D%E9%A6%88%E9%97%AD%E7%8E%AF%E3%80%81%E7%8A%B6%E6%80%81%E8%AE%B0%E5%BF%86_compressed_v2.png)

後面的實戰部分你會反覆看到這 3 樣東西，先有個印象就行。



## 二、AI 程式設計的發展過程

Loop 不是憑空冒出來的概念，它是從前幾代 AI 程式設計方法論一步步進化來的。瞭解 AI 程式設計的發展過程，你才能知道 Loop 到底解決了什麼問題、為什麼需要它。

下面簡單梳理一下這條進化路徑：

![](https://pic.yupi.icu/1/04_AI%E7%BC%96%E7%A8%8B%E8%BF%9B%E5%8C%964%E9%98%B6%E6%AE%B5%EF%BC%9APrompt%E2%86%92Context%E2%86%92Harness%E2%86%92Loop_compressed_v3.png)



**1、提示詞工程 Prompt Engineering（2022 ~ 2024）**

關注的是怎麼透過對話讓 AI 聽懂你的需求。比如給 AI 設定角色、約束輸出格式、用思維鏈讓它一步步思考。

提示詞工程解決的核心問題是「AI 答非所問」，掌握了提示詞的寫法之後，輸出質量能提升一大截。

![](https://pic.yupi.icu/1/4_prompt_engineer.png)



**2、上下文工程 Context Engineering（2025）**

光寫好提示詞還不夠，AI 還得了解你的專案背景才能給出靠譜的回答。

上下文工程關注的就是怎麼 **在對的時候把對的資訊餵給 AI**。

比如寫 AGENTS.md 規則檔案讓 AI 瞭解專案背景，用 RAG 讓 AI 能檢索到相關資料，給 AI 建立跨對話的記憶機制。

上下文工程解決的核心問題是「AI 給出的回答脫離實際」，做好了上下文管理，AI 的輸出才能貼合你的專案實際情況。

![](https://pic.yupi.icu/1/5_context_engineering.png)



**3、Harness Engineering 駕馭工程（2026 年初）**

有了上下文，AI 能理解你的專案了，但要讓它真正幹好活，還得給它搭建一整套靠譜的工作環境。

除了給 AI 提供合適的上下文資訊外，還要給它配備工具、拆解任務、搭建測試、防止程式碼腐爛。

把 Harness 搭好之後，AI 才能在一個有工具、有測試、有約束的環境裡穩定可靠地產出。

![](https://pic.yupi.icu/1/6_harness_engineering.png)



**4、Loop Engineering 迴圈工程（2026 年中）**

關注的是怎麼讓 AI 自己形成工作迴圈。

前面三步都做好了，AI 已經能在靠譜的環境裡幹活了，但你還是得一步步推著它走。Loop 要解決的就是這個問題，你把「提示、檢查、決定下一步」這些事情交給一套系統去迴圈執行，自己只需要設定好目標和停止條件，AI 就能自己跑起來直到達成目標。

這四者是層層包含的關係。提示詞技巧、上下文管理、Harness 搭建，這些能力在 Loop 裡面全都要用上。Loop 只是在這些基礎上，多加了一層「自動迴圈 + 反饋閉環」的機制。

![](https://pic.yupi.icu/1/05_Loop%E5%9C%A8%E5%89%8D%E4%B8%89%E8%80%85%E5%9F%BA%E7%A1%80%E4%B8%8A%E5%8A%A0%E4%BA%86%E8%87%AA%E5%8A%A8%E5%BE%AA%E7%8E%AF+%E5%8F%8D%E9%A6%88%E9%97%AD%E7%8E%AF_compressed_v3.png)

很多同學容易把 Harness 和 Loop 搞混。

如果把 AI 比作一匹馬，Harness 就是你給馬裝上的韁繩、馬鞍和圍欄，然後你騎在馬上手動駕馭它。而 Loop 呢，是你設定好一條巡邏路線後，不用上馬，讓馬自己按路線一圈一圈地跑。每跑完一圈它會自動檢查有沒有異常，發現問題就處理，處理完繼續跑下一圈。你從騎馬的人變成了設計路線的人。

![](https://pic.yupi.icu/1/07_Harness_vs_Loop%E5%AF%B9%E6%AF%94%EF%BC%9A%E9%AA%91%E9%A9%AC_vs_%E8%AE%BE%E8%AE%A1%E5%B7%A1%E9%80%BB%E8%B7%AF%E7%BA%BF_compressed_v2.png)

不過 Loop Engineering 目前還是一個很早期的概念，業界還沒有統一的標準和最佳實踐。建議先把 Harness 那套基礎打紮實，Loop 學起來就容易多了。



## 三、Loop 實戰體驗

瞭解完基本概念，接下來我們直接上手實戰，同時用 3 種 AI 工具，感受一下 Loop 在實際開發中是什麼體驗。

目前 Claude Code 和 Codex 都已經內建了 Loop 相關的命令，可以直接用。Cursor 雖然還沒有原生的 Loop 命令，但可以透過提示詞設計來實現同樣的思想。下面分別演示。



### Claude Code 的 Loop 實戰

Claude Code 提供了兩個 Loop 相關的斜槓命令 `/goal` 和 `/loop`，分別對應兩種不同的使用場景。

#### /goal 命令

`/goal` 命令的作用是讓 AI 持續工作，直到你設定的目標達成為止。

你給出一個可驗證的目標條件，AI 開始工作，每一輪結束後會有一個獨立的小模型來判斷「目標是否已經達成」。如果沒達成，AI 自動開始下一輪繼續推進；如果達成了，就停止並報告完成。

注意，這個判斷目標是否達成的模型和執行任務的模型是分開的，避免了單個模型的偏差。

比如我想讓 Claude Code 修復整個專案的程式碼，可以這樣寫：

```bash
/goal 修復整個專案的程式碼，直到全部測試透過且沒有報錯
```

![](https://pic.yupi.icu/1/image-20260519191842661.png)

執行後 Claude 會立刻開始工作，直到所有測試透過且沒有報錯為止，整個過程你完全不用幹預。

還有個小技巧，你可以在條件後面加上熔斷限制，比如「20 輪還沒搞定就停下來」，防止 AI 陷入死迴圈狂燒 token。

`/goal` 適合那些有明確終止條件、且手動盯著比較費時的場景，比如模組遷移、批次重構、修復某個測試用例直到它透過、處理一批標了特定標籤的 Issue 等等。

如果你想中途看看進度，直接輸入 `/goal` 不帶任何引數就行，能看到當前任務跑了多久、花了多少 token。

![](https://pic.yupi.icu/1/image-20260519192117090.png)


想提前停止的話，用 `/goal clear` 即可：

![](https://pic.yupi.icu/1/image-20260519192203259.png)



#### /loop 命令

`/loop` 命令的作用是讓 AI 按固定的時間間隔定時迴圈執行某個操作。

比如每 5 分鐘檢查一下部署是否完成：

```bash
/loop 5m 檢查專案前後端的部署狀態
```

![](https://pic.yupi.icu/1/image-20260519184353594.png)

`/loop` 適合那些需要定期盯著的事情，比如等部署完成後自動通知你、每隔一段時間檢查線上服務有沒有報錯、定時掃描程式碼庫裡新增的安全漏洞。任務完成後記得停掉 Loop，否則它會一直在後臺迴圈執行消耗資源。

總結一下這兩個命令的區別，`/goal` 是「跑到完成為止」，適合有明確終點的一次性任務；`/loop` 是「定時反覆跑」，適合沒有明確終點的持續監控。兩者都是 Loop Engineering 的實現方式，只是適用場景不同。

![](https://pic.yupi.icu/1/08_goal_vs_loop_%E5%91%BD%E4%BB%A4%E5%AF%B9%E6%AF%94_compressed_v2.png)



#### /schedule 命令

`/loop` 有個限制 —— 它跑在你本地電腦上，電腦關了它就停了。

如果你希望迴圈在雲端持續執行，不依賴本地環境，可以用 `/schedule` 建立一個雲端的 Routine 定時任務（目前是 Research Preview 研究預覽階段）。

比如你想讓 Claude 每小時檢查一次 Bug 反饋：

```plaintext
/schedule 每小時檢查一次 #project-feedback 頻道的 Bug 反饋。
```

`/schedule` 和 `/loop` 的區別是：前者在雲端執行，不依賴你的電腦；後者在本地執行，合上筆記本就斷了。如果是需要 7×24 小時持續執行的監控任務，用 `/schedule` 更合適。



### Codex 的 Loop 實戰

Codex 桌面 APP 也有類似的 Loop 能力，主要透過兩種方式實現。



#### 設定目標

在 Codex APP 的對話方塊裡，你可以透過輸入 `/目標` 來設定一個持續執行的目標，效果和 Claude Code 的 `/goal` 類似，AI 會持續工作直到目標達成。

比如我想讓 AI 把我的「程式設計師人格測試專案」做一次完整的國際化改造，把所有中文介面翻譯成英文版：

```
/目標 將 cbti-test 專案完整國際化為英文版。逐個檔案替換所有中文文案為英文，每處理完一個檔案就執行構建驗證，直到專案能正常編譯執行且介面無中文殘留。
```

經過 15 分鐘後，AI 完成了目標，並且輸出了 token 使用量。相比直接讓 AI 一把梭完成所有事情，設定目標後讓它一步步開發、每步都自動校驗，最終產出的質量會穩定得多。

![](https://pic.yupi.icu/1/image-20260616135706979.png)

Codex 桌面 APP 裡還有一個「自動化」面板，類似於 Claude Code 的 `/loop`，你可以配置定時執行的自動化任務。

進入左側的自動化面板，能看到 Codex 已經內建了一些模板，比如定時總結程式碼變更、檢查程式碼問題之類的。

建立成功後，時間一到 Codex 就會自動開啟一個對話來執行任務。你也可以手動執行一次先看看效果：

### Cursor 自主實現 Loop 思想

Cursor 目前還沒有原生的 `/goal` 或 `/loop` 命令。但只要在提示詞裡設計好迴圈機制，讓 AI 自主執行命令，一樣能跑出 Loop 的效果。

比如我要用 Cursor 從零開發一個叫「裝了嗎」的桌面 APP，幫學程式設計的同學一鍵安裝各種開發環境。這個專案包含 Electron 桌面應用、Python 服務端、Web 管理後臺三個模組，還是挺複雜的。

![](https://pic.yupi.icu/1/01_%E8%A3%85%E4%BA%86%E5%90%97%E4%BA%A7%E5%93%81%E6%A6%82%E5%BF%B5%E5%9B%BE%EF%BC%9A%E7%94%A8%E6%88%B7%E8%BE%93%E5%85%A5%E8%BD%AF%E4%BB%B6%E5%90%8D%E2%86%92AI%E7%94%9F%E6%88%90%E5%AE%89%E8%A3%85%E8%84%9A%E6%9C%AC%E2%86%92%E4%B8%80%E9%94%AE%E6%89%A7%E8%A1%8C_compressed_v1.png)

我特意在提示詞裡設計了一套自主開發迴圈，讓 AI 不要停下來等我確認，自己跑起來直到整個系統能用為止。

![](https://pic.yupi.icu/1/image-20260611162938865.png)

提示詞的關鍵部分是這樣的：

```markdown
## 自主開發迴圈

全程自主開發，不要停下來等我確認，除非遇到無法自行解決的阻塞問題。遵循以下迴圈機制：

1. 狀態追蹤：在專案根目錄維護 PROGRESS.md，記錄當前階段、已完成事項、進行中事項、問題及解決方案。每完成一個模組就更新
2. 開發-驗證閉環：每完成一個模組，立即編譯執行驗證，有報錯就修復，透過後再推進下一個模組
3. 端到端驗證：全部功能完成後，以使用者視角做一次完整的端到端測試
4. 防死迴圈：同一個問題修復超過 5 次仍未解決，記錄到 PROGRESS.md 後跳過，繼續推進其他任務
```

你會發現，這幾條規則恰好對應了前面講的 Loop 三個核心要素：

- 目標和停止條件 → 「端到端測試透過」就是停止條件
- 反饋閉環 → 「開發-驗證閉環」讓 AI 每做完一步都自動檢查
- 狀態記憶 → PROGRESS.md 檔案持久化記錄進度

執行之後，AI 就開始了它的自主迴圈。它先配置好環境，然後按順序開發服務端、桌面端、管理後臺。整個過程我基本沒有干預，AI 自己維護著 PROGRESS.md 記錄進度，開發完一個模組就自動跑測試，遇到報錯就自己修復，修完繼續推進。

![](https://pic.yupi.icu/1/image-20260611160046322.png)

最終 AI 花了將近 50 分鐘，獨立完成了整個系統的開發和驗證，不需要我中間插手。三個服務全部能正常啟動，核心功能都能跑通。

![](https://pic.yupi.icu/1/1781159120778-312597e0-112b-432a-9973-cc829fcbe013.png)

開啟桌面 APP 看看效果。主介面有一個 AI 對話方塊，下面預置了常見開發環境的快捷入口：

![](https://pic.yupi.icu/1/1781154426901-1d864350-c541-4d80-8b0b-f52265aeddb9.png)

選擇想安裝的軟體和版本後，AI 會自動生成完整的安裝指令碼和方案，包含中文註釋、環境檢測、驗證命令，可以直接複製執行或者點選一鍵安裝：

![](https://pic.yupi.icu/1/1781155941607-2cdae4aa-c738-4f9d-976b-fe4572b6ecc5.png)

Web 管理後臺也能正常執行，可以檢視安裝資料統計、管理所有已經生成的安裝方案、檢視使用者反饋資料：

這就是在沒有內建 Loop 命令的工具裡，透過提示詞設計來實現 Loop Engineering 思想的方法。核心就是把 **狀態記憶 + 反饋閉環 + 防死迴圈** 這三個要素寫進提示詞裡，讓 AI 自己形成迴圈。

## 四、官方的 4 種迴圈分類

前面實戰了 `/goal`、`/loop`、`/schedule` 這些命令，你可能會想：這些東西之間到底是什麼關係？

Claude Code 官方團隊在部落格 [Getting started with loops](https://claude.com/blog/getting-started-with-loops) 中給出了一個很清晰的分類框架，把迴圈按自動化程度從低到高分成了 4 種型別：

| 迴圈型別 | 你交出了什麼 | 適合什麼場景 | 用什麼工具 |
|---------|-----------|------------|----------|
| 手動迴圈 | 驗證環節 | 較短的、非固定流程的任務 | 自定義 Skills |
| 目標迴圈 | 停止條件 | 有明確完成標準的任務 | /goal |
| 定時迴圈 | 觸發時機 | 週期性的、依賴外部系統的任務 | /loop、/schedule |
| 主動迴圈 | 整個提示詞 | 持續性的、流程化的工作 | 以上全部 + Dynamic Workflows |

從上到下，你管的事情越來越少，交給 AI 的越來越多。

![](https://pic.yupi.icu/1/05_4%E7%A7%8D%E5%BE%AA%E7%8E%AF%E9%80%92%E8%BF%9B%E5%85%B3%E7%B3%BB%E5%8F%AF%E8%A7%86%E5%8C%96%E6%80%BB%E8%A7%88%E5%9B%BE_compressed_v1.png)

最高階的「主動迴圈」是把前面所有能力組合起來，搭建一套完全自動化的流水線。比如處理使用者反饋這個場景，你可以這樣設計：

```plaintext
/schedule 每小時檢查一次 #project-feedback 頻道的 Bug 反饋。
/goal 這一輪發現的每條反饋都要分類、處理、回覆，全部搞定才能停。
修復 Bug 時，用 workflow 在並行工作樹中探索三種方案，
再讓一個評審 Agent 對每個方案做對抗性審查。
```

這條提示詞把所有能力串在一起 —— 新反饋來了自動分類、自動修復 Bug、修完還有另一個 Agent 做程式碼審查，審過了還會自動回覆使用者。

其中提到的 Dynamic Workflows 動態工作流，是 Claude Code 的一個高階功能，能讓 AI 自己編寫編排指令碼、把大任務拆給數十到數百個並行子 Agent 執行。關於動態工作流的完整介紹和技術原理，可以閱讀本教程 AI 程式設計概念大全板塊中的《AI 動態工作流詳解》。

目前 `/schedule` 和 Dynamic Workflows 還在 Research Preview 階段。但從這個方向能看出來，Claude Code 團隊在做的事情就是讓 AI 能承擔越來越完整的工程流程。

不過這不意味著你要一步跳到主動迴圈。先從最簡單的 `/goal` 開始，按需選擇合適的層級就好。



## 五、深入理解 Loop 的核心模組

透過前面的實戰你會發現，其實上手 Loop 並不難，設定好目標、輸入一條命令就能跑起來。

但如果你想設計一個更復雜、更可靠的迴圈系統，比如多個 Agent 並行協作、自動連線外部工具、跨會話持續執行，那就需要了解 Loop Engineering 更完整的方法論框架了。

目前業界對 Loop Engineering 比較主流的一種拆解方式，是把它分成 5 個核心模組，外加一個貫穿全程的狀態記憶。

![](https://pic.yupi.icu/1/09_Loop%E6%A0%B8%E5%BF%83%E6%A8%A1%E5%9D%97%E6%9E%B6%E6%9E%84%E5%9B%BE%EF%BC%9A5%E6%A8%A1%E5%9D%97+%E7%8A%B6%E6%80%81%E8%AE%B0%E5%BF%86_compressed_v2.png)



### 1、自動排程

這是 Loop 的心跳，沒有它 Loop 就跑不起來。

你設定好觸發條件和執行頻率，Loop 就會按照節奏自動執行。

舉個例子，你可以設一個 `/goal` 讓 AI 把專案裡所有的報錯修完，也可以設一個 `/loop` 讓 AI 每小時檢查一次程式碼倉庫有沒有新的 Issue 需要處理。前者是一次性任務，後者是持續性任務，但底層都是自動排程在驅動，不需要人工干預。

![](https://pic.yupi.icu/1/10_%E8%87%AA%E5%8A%A8%E8%B0%83%E5%BA%A6%EF%BC%9ALoop%E7%9A%84%E5%BF%83%E8%B7%B3%EF%BC%8C%E5%AE%9A%E6%97%B6%E6%88%96%E7%9B%AE%E6%A0%87%E9%A9%B1%E5%8A%A8_compressed_v3.png)



### 2、工作隔離

當你想讓多個 AI 同時在一個專案幹活的時候，可能會遇到問題。

比如你讓一個 Agent 開發搜尋模組，另一個 Agent 開發商品列表模組，但它倆同時修改了主頁檔案，程式碼就會互相沖突，亂成一團。

解決辦法是用 Git WorkTree，給每個 Agent 分配一個獨立的工作目錄，各自在自己的分支上開發，互不干擾，最後再合併回主幹。

![](https://pic.yupi.icu/1/11_%E5%B7%A5%E4%BD%9C%E9%9A%94%E7%A6%BB%EF%BC%9AGit_WorkTree%E8%AE%A9%E5%A4%9A%E4%B8%AAAgent%E4%BA%92%E4%B8%8D%E5%B9%B2%E6%89%B0_compressed_v2.png)

像 Claude Code 可以透過 `--worktree` 引數啟動獨立工作樹，Cursor 和 Codex 的 Agent 面板也都內建了 WorkTree 的支援，可以自動建立和管理工作樹，讓多個 AI 同時幹活。

![](https://pic.yupi.icu/1/image-20260410150251832.png)



### 3、技能沉澱

如果每次新開一個 Loop，AI 都要從頭瞭解你的專案背景、編碼規範、構建流程，那太浪費時間了。

Skills 就是把這些專案知識和工作流程寫成可複用的 `SKILL.md` 文件，Loop 每次啟動時自動載入。AI 不用每次都重新學習，直接根據文件快速上手幹活。

![](https://pic.yupi.icu/1/12_%E6%8A%80%E8%83%BD%E6%B2%89%E6%B7%80%EF%BC%9ASKILL.md%E8%AE%A9AI%E5%BF%AB%E9%80%9F%E4%B8%8A%E6%89%8B_compressed_v2.png)

這跟你在公司維護一份《專案開發文件》是一個道理，新來的人看完就能幹活，只不過現在看文件的不是人，是 AI。



### 4、工具連線

AI 大模型只是大腦，能思考、能規劃，但如果不給它接上手腳和工具，很多事情它幹不了。

透過 MCP 協議和各種聯結器，Loop 可以跟你的 Issue 跟蹤器、資料庫、Slack、CI/CD 系統打通。這樣 CI 掛了它能自己去看報錯日誌，Issue 來了它能自己分類處理，修完之後還能自動開 PR 併發訊息通知你。

有了工具連線，Loop 才能從「只會改程式碼」變成「能發現問題、解決問題、通知你結果」的完整閉環。

![](https://pic.yupi.icu/1/13_%E5%B7%A5%E5%85%B7%E8%BF%9E%E6%8E%A5%EF%BC%9A%E9%80%9A%E8%BF%87MCP%E8%AE%A9Loop%E8%BF%9E%E6%8E%A5%E5%A4%96%E9%83%A8%E5%B7%A5%E5%85%B7%E5%BD%A2%E6%88%90%E5%AE%8C%E6%95%B4%E9%97%AD%E7%8E%AF_compressed_v2.png)



### 5、子代理互審

如果你讓一個模型生成程式碼，再讓同一個模型檢查這段程式碼好不好，它大機率會覺得沒問題。就像學生自己批改自己的考卷，肯定手下留情。

所以在 Loop 裡，一般會安排至少兩個角色。一個 Agent 負責寫程式碼，另一個 Agent 專門負責跑測試和程式碼審查。第二個 Agent 用的上下文和指令跟第一個完全不同，它只關心這段程式碼有沒有 Bug、邏輯對不對，不會受到第一個 Agent 思路的影響。

![](https://pic.yupi.icu/1/14_%E5%AD%90%E4%BB%A3%E7%90%86%E4%BA%92%E5%AE%A1%EF%BC%9A%E5%86%99%E4%BB%A3%E7%A0%81%E7%9A%84%E5%92%8C%E6%A3%80%E6%9F%A5%E4%BB%A3%E7%A0%81%E7%9A%84%E5%88%86%E5%BC%80_compressed_v1.png)



### 狀態記憶

Loop 在執行過程中會產生大量中間狀態，比如哪些檔案處理過了、上一輪的結論是什麼、當前進度到哪一步了。

這些資訊不能只存在 AI 的對話視窗裡，因為對話視窗空間有限，關掉就沒了。

可以把進度記錄在外部檔案裡（比如 PROGRESS.md），Agent 每次新開一輪迴圈時先讀取進度瞭解當前狀態，幹完活再更新它。中間斷了重啟也不會從零開始。

![](https://pic.yupi.icu/1/15_%E7%8A%B6%E6%80%81%E8%AE%B0%E5%BF%86%EF%BC%9APROGRESS.md%E6%8C%81%E4%B9%85%E5%8C%96%E8%AE%B0%E5%BD%95%E8%BF%9B%E5%BA%A6_compressed_v3.png)

這 5 個模組裡，**自動排程** 和 **狀態記憶** 是最核心的，也是我們實戰中已經接觸過的東西。其他幾個模組（工作隔離、技能沉澱、工具連線、子代理互審）更多是在基礎迴圈跑起來之後的進階最佳化，按需使用就好，不需要一上來就全部配齊。



## 六、注意事項和學習建議

每次新技術一出來，你總會聽到「XX 已死」這種說法。這次也不例外，不少人在喊：提示詞工程已死，Loop Engineering 才是未來！

但其實 Loop 不是取代提示詞的，它是建立在提示詞、上下文、Harness 這些基礎之上的。

如果基礎都沒打好，跑 Loop 只會放大問題。

下面聊幾個實際使用 Loop 時需要注意的事情。



### Token 消耗較多

每一次 Loop 迭代都是一次完整的提示詞執行。如果你設定 1 分鐘執行一次、連續跑 24 小時，那就是 1440 次 AI 呼叫。

你想想強烈推薦 Loop Engineering 的 2 位大佬，一個是 Anthropic 的工程師，一個背後有 OpenAI 的資源，人家用自家的模型做實驗，公司報銷 token 費用，成本幾乎為零。但對於大多數普通開發者來說，一個月 20 刀的訂閱套餐很難撐住高頻迴圈。

**跑的不是迴圈，是你的錢包啊！**

有人在評論區質問 Peter：你們有無限 token 供應，我沒有啊！

Peter 回答：沒錯，可你的時間真不值錢嗎？

這句話是在提醒我們思考 **價效比**。如果一個 `/goal` 任務花了 30 塊錢的 token，但幫你省了 3 小時的手動操作，應該還挺值的。但如果跑了 100 塊錢，最後還是搞砸了，需要人工返工，那就是純浪費錢了。

所以啟動 Loop 之前先想清楚，目標能不能量化？值不值得跑？別讓你的 AI 員工白忙活。

Claude Code 官方也給了一些很實用的省錢方法：

1. **選對工具和模型**：簡單任務不需要多 Agent 或複雜迴圈，有些任務用更便宜更快的模型就夠了。日常執行的 Routine 可以路由到更小更快的模型上跑，把最強的模型留給需要判斷力的關鍵環節。
2. **把停止條件寫具體**：條件越清晰，AI 越能快速收斂到正確結果，少走彎路就是省錢。
3. **先小範圍試跑再全量鋪開**：Dynamic Workflows 可以同時啟動幾百個 Agent，但如果直接全量跑，token 消耗想都不敢想。先拿一小部分任務試試水。
4. **能用指令碼搞定的事情就別用 AI 推理**：批次重新命名檔案、格式化 JSON、跑資料遷移這些確定性的操作，寫個指令碼讓 AI 直接執行就行，不用它每次都從頭推理一遍。
5. **迴圈頻率別設太高**：你監控的東西多久變化一次，迴圈就設多長間隔。沒必要每分鐘檢查一個一天才更新一次的東西。
6. **用 `/usage` 命令看看錢花哪了**：這個命令能按 Skills、Subagents、MCPs 拆解最近的用量，發現哪個 Agent 燒錢太猛還能隨時停掉它。



### 除錯比提示詞難 10 倍

有開發者說：所有人都在衝向 loops，但除錯一個已經跑了 47 輪的狀態機，比修好一個 prompt 難 10 倍！

的確，當 Loop 跑偏了，你很難定位到底是第幾輪出了問題。所以一開始一定要從簡單的 Loop 做起，目標設小一點、停止條件寫明確一點。每輪 Loop 都讓 AI 寫清楚這一輪做了什麼、結果如何，方便你事後追溯。



### Overbaking 過度烘焙

如果 Loop 跑得太久、目標約束又不夠緊，AI 可能會開始「加戲」。比如給你的專案加上沒人需要的加密功能、過度拆分檔案結構、甚至為了透過測試而刪除測試用例。

這個現象最早在 Ralph Wiggum Loop 的實踐中就被社群發現了。Ralph 是 Loop Engineering 的前身，有人用它讓 AI 在迴圈裡不斷重構程式碼庫，結果跑太久之後 AI 開始亂加功能、亂刪測試。社群形象地把這種情況叫做 Overbaking 過度烘焙。

更穩的做法是，寫好清晰的需求文件，明確列出 Loop 要做什麼、不做什麼。還要設定合理的迴圈次數上限，跑完後人工審查結果，不要無腦合併。



### 保持程式碼質量

迴圈跑得再溜，如果每輪產出的程式碼質量拉胯，那也是白費 token。Claude Code 官方團隊總結了幾個實操要點：

1）**保持程式碼庫本身乾淨整潔**。AI 會模仿你程式碼庫裡已有的模式和規範，你的程式碼庫本身就亂七八糟的話，它寫出來的也好不到哪去。

2）**用 Skills 給 AI 配一個驗證自己工作的方法**。檢查標準越量化越好，最好讓它能執行指令碼、檢視截圖、測試效能，而不是靠它自己感覺程式碼沒問題。AI 的感覺可不靠譜。

3）**把框架和庫的文件放在 AI 能找到的地方**。最新的最佳實踐它不一定知道，但如果你提供了文件，它就能參考著寫。這也是為什麼聯網搜尋能力和 Context7 這類能自動拉取最新文件的 MCP 外掛越來越重要了。

4）**用第二個 Agent 做程式碼審查**。讓不同的 Agent 來寫程式碼和審查程式碼，審查者有了全新的上下文，不會受寫程式碼 Agent 的思路影響。Claude Code 內建了 `/code-review` 技能可以直接用，如果你的程式碼託管在 GitHub 上，還可以配合 GitHub 自帶的 Code Review 功能做雙重把關。

還有個很重要的原則：當某次迴圈的結果不達標時，不要只修這次的問題就完事了，要把這次踩的坑編碼到系統裡，比如更新 Skill 或規則檔案，讓以後每一輪迴圈都不再犯同樣的錯。長期下來質量會越來越穩。

![](https://pic.yupi.icu/1/10_AI%E7%BA%A0%E9%94%99%E6%B2%89%E6%B7%80%E6%AD%A3%E5%90%91%E5%BE%AA%E7%8E%AF_compressed_v2.png)



### 學習路徑

如果你剛接觸 AI 程式設計，還在用 Vibe Coding 的方式跟 AI 對話寫程式碼，那先不用急著搞 Loop。把提示詞技巧練好，學會用 AGENTS.md 給 AI 提供充足的上下文，這是最基礎也最重要的一步。

等你能用 AI 做完整功能、但經常需要手動糾偏的時候，就該學 Harness Engineering 了。給 AI 配好工具、寫好測試、搭好架構約束，讓它在一個靠譜的環境裡幹活。

這些基礎打好之後，真要上手 Loop，先從 `/goal` 這種輕量方式開始就夠了。給 AI 一個小目標，讓它自己跑一輪，感受一下效果和 token 消耗。確認符合預期之後，再逐步加入定時迴圈、防死迴圈機制、工具連線這些進階能力，一步步搭建更完整的迴圈系統。

如果你想系統學習前面幾個階段的知識，可以閱讀本教程經驗技巧板塊中的《Harness Engineering 保姆級教程》，裡面從概念到實戰都有完整的講解。



## 寫在最後

Loop 是放大器，能放大你的能力，也能放大你的懶惰。
