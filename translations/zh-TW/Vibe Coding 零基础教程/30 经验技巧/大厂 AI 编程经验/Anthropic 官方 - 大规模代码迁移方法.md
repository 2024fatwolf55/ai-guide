# Anthropic 官方 - 大規模程式碼遷移方法

> 學習 Anthropic 官方的六步遷移法，用 AI 高效完成大規模程式碼遷移



大家好，我是程式設計師魚皮。

前幾天 Anthropic 官方發了 [一篇博文](https://claude.com/blog/ai-code-migration)，講的是他們內部如何用 Claude Code 跑大規模程式碼遷移。

這篇文章的含金量非常高，因為裡面的兩個案例實在太炸裂了！

![](https://pic.yupi.icu/1/image-20260720133130758.png)

第一個案例，前端圈很火的工具 Bun 的創始人 Jarred Sumner（目前也是 Anthropic 的技術員工），用 Claude Code 把 Bun 從 Zig 語言重寫到 Rust。整整 53 萬行程式碼，只用 11 天就完成了，而且 100% 測試透過後合併上線。

第二個案例，Anthropic Labs 的聯合負責人 Mike Krieger 只用了一個週末，把一個 Python 專案遷移成了 16.5 萬行 TypeScript，全平臺構建時間從 30 分鐘降到了約 2 秒。

**一個週末，重構 16.5 萬行程式碼，什麼概念？**

以前這種量級的工程，再牛的團隊也得幹上一兩年，還不一定能做到 100% 相容。現在一個人加一個 AI，幾天就搞定了。

大家肯定很好奇，他們是怎麼做到的，這背後有什麼方法和技巧嗎？

下面我會結合官方博文的內容，加上 Bun 官方的技術部落格、以及我自己使用 AI 程式設計的經驗，給大家做一個完整的中文深度解讀。

學會這套方法之後，幾萬行程式碼的專案重構、技術棧升級、老專案翻新，你都可以用同樣的思路高效完成。



## AI 遷移程式碼的核心思路

用 AI 遷移程式碼時，你的工作不是修改程式碼，是在設定「產出程式碼的流程」。

傳統的程式碼遷移思路是一個檔案一個檔案地翻譯，翻譯完了逐個檢查，發現問題逐個修復。

這種方式在幾十個檔案的規模還可行，但如果檔案數量成百上千，基本就不可能了。

正確的思路是 **把注意力放在流程上**。

當你發現 AI 在某類翻譯上反覆犯同樣的錯，不要一個一個去修那些錯誤的程式碼，而是去修復規則手冊，讓所有後續翻譯都不再犯這個錯。隨著規則越來越完善，你需要人工干預的次數會越來越少。

![](https://pic.yupi.icu/1/01_%E4%BF%AE%E6%B5%81%E7%A8%8B%E4%B8%8D%E4%BF%AE%E4%BB%A3%E7%A0%81%EF%BC%9A%E6%A0%B8%E5%BF%83%E6%80%9D%E8%B7%AF%E5%AF%B9%E6%AF%94_compressed_v1.png)

我剛開始用 AI 程式設計的時候，經常是一個個修復 Bug。AI 犯了一個錯，我糾正一次，下次又犯同樣的錯，我再糾正一次。反反覆覆，非常低效。

後來我開始把踩過的坑寫進 CLAUDE.md / AGENTS.md 或者 Rules 檔案裡，每次糾正 AI 的錯誤都順手沉澱成規則。

隨便舉個例子，比如我發現 AI 生成 Spring Boot 介面時總是忘記加引數校驗註解，我就加了一條規則：

```markdown
所有 Controller 層的請求引數必須使用 @Valid + DTO 校驗，禁止在 Service 層手動 if 判空
```

從此再也沒出現過這個問題。

所以無論是百萬行程式碼遷移，還是你平時 Vibe Coding 專案，都應該有這個意識：**出了問題不要只盯著問題本身，要修復產出問題的源頭**。



## 六步遷移法

Anthropic 總結了一套完整的大規模程式碼遷移流程，總共六步。

開局一張圖，你就知道這套方法論大概有多 NB 了。

![六步遷移流程總覽](https://pic.yupi.icu/1/07_%E5%85%AD%E6%AD%A5%E8%BF%81%E7%A7%BB%E6%B5%81%E7%A8%8B%E6%80%BB%E8%A7%88%EF%BC%88%E4%B8%AD%E6%96%87%E7%89%88%EF%BC%89_compressed_v1.png)



### 0、搞定驗證機制

在動手遷移之前，你必須有一個可靠的驗證機制。沒有驗證機制，你都不知道什麼時候可以收工。

最理想的情況是像 Bun 一樣，已經有一套完整的測試套件，而且測試是用第三方語言寫的（Bun 的測試用的是 TypeScript），不依賴被遷移的語言本身。

但如果你的測試跟原始碼是同一種語言寫的呢？

建議是先把測試分類。哪些測試是透過外部介面驗證行為的？哪些是依賴內部實現細節的？

外部介面的測試可以直接複用，內部實現的測試需要重寫成跟語言無關的形式。

開頭提到的例子中，Mike 的專案沒有現成的測試套件，他的做法是讓 Claude 建立了一個 **對比指令碼**，跑 7 個真實場景，把 Python 版本和 TypeScript 版本的輸出做 diff，任何行為差異都算 Bug。

這個思路對小專案也完全適用。哪怕你只是把一個 Python 指令碼遷移到 TypeScript，也可以讓 AI 幫你準備幾組真實的輸入輸出樣本，遷移完了跑一遍，看看結果一不一樣。



### 1、制定規則手冊和依賴圖

這一步是整個流程里人工投入最多的階段。

![](https://pic.yupi.icu/1/08_%E7%AC%AC1%E6%AD%A5%EF%BC%9A%E5%88%B6%E5%AE%9A%E8%A7%84%E5%88%99%E6%89%8B%E5%86%8C%E5%92%8C%E4%BE%9D%E8%B5%96%E5%9B%BE%EF%BC%88%E4%B8%AD%E6%96%87%E7%89%88%EF%BC%89_compressed_v2.png)

Bun 創始人 Jarred 光是跟 Claude 討論怎麼把 Zig 的模式對映到 Rust 就花了 3 個小時，最終產出了一份 576 行的規則手冊，裡面詳細規定了每種型別怎麼對映、每種慣用法怎麼轉換。

規則手冊的內容取決於一個關鍵策略：**新程式碼是保持原有架構逐行翻譯，還是完全重新設計？**

Jarred 選擇的是保持架構不變的機械翻譯，所以他的規則手冊主要是一個對照表。他還讓 Claude 跑了一個工作流，分析程式碼庫裡每個 struct 欄位的生命週期，輸出成一個 `LIFETIMES.tsv` 檔案給後續翻譯參考。

![](https://pic.yupi.icu/1/image-20260720171445547.png)

而 Mike 選擇的是重新設計架構，所以他的規則手冊更像是一份設計文件，描述新系統應該長什麼樣。

除了規則手冊，依賴圖也很重要。你得知道哪些檔案依賴哪些檔案，這樣才能決定遷移的順序、哪些檔案可以放在同一批處理。

對於像 Python 這種依賴關係不顯式宣告的語言，可以讓 Claude 寫一個指令碼去分析和生成依賴圖。Anthropic 還開源了一個 [程式碼遷移工具包](https://github.com/anthropics/code-migration-kit-with-claude-code)，裡面就包含了現成的依賴分析指令碼，拿來直接用就行。

![](https://pic.yupi.icu/1/image-20260720171538243.png)

此外，還要做一份「差異清單」，列出源語言和目標語言之間那些不能簡單翻譯的地方。

比如 Zig 到 Rust 的核心差異是手動記憶體管理變成了所有權系統，Python 到 TypeScript 的核心差異是動態型別變成了需要顯式宣告介面。這些差異點是 AI 最容易犯錯的地方，必須在規則手冊裡重點標註。



### 2、小範圍試跑

規則手冊寫好之後，不要急著全量執行，先拿 3 個檔案試試水。

![](https://pic.yupi.icu/1/09_%E7%AC%AC2%E6%AD%A5%EF%BC%9A%E5%8E%8B%E5%8A%9B%E6%B5%8B%E8%AF%95%E8%A7%84%E5%88%99%EF%BC%88%E4%B8%AD%E6%96%87%E7%89%88%EF%BC%89_compressed_v1.png)

我覺得 Bun 創始人 Jarred 的做法很機智。他讓一個 Claude 例項按照規則手冊翻譯 3 個檔案，同時讓另一個 Claude 例項以「高階 Rust 工程師」的身份翻譯同樣的 3 個檔案。然後再開一個全新的 Claude 對話，專門用來對比兩個版本的差異，從差異中提取新的翻譯規則。

這一步他發現了 2 個關鍵問題，如果直接鋪開到全部 1448 個檔案，後果不堪設想。

對於重新設計架構的專案，做法不太一樣。Mike 是讓多個 Claude 例項從不同角度挑設計文件的毛病，看有沒有邏輯漏洞或考慮不周的地方。然後跑一次完整的端到端翻譯，看看設計在實際執行中有沒有問題，發現了問題就改規則、重跑。

有趣的是，他實際上跑了三次完整遷移，**前兩次都丟棄產出，只保留對規則的改進，直到第三次才正式保留結果。**

![](https://pic.yupi.icu/1/02_%E8%AF%95%E8%B7%91%E5%93%B2%E5%AD%A6%EF%BC%9A%E5%89%8D%E4%B8%A4%E6%AC%A1%E4%B8%A2%E5%BC%83%E5%8F%AA%E4%BF%9D%E7%95%99%E8%A7%84%E5%88%99%E6%94%B9%E8%BF%9B_compressed_v1.png)

我看到這裡，第一反應是：前兩次直接丟棄，這不是浪費 Tokens 麼？

但其實，對於複雜的專案來說，這麼做是合理的。試跑階段的目標就是打磨規則，試跑出來的程式碼未必正確可用，如果直接應用這些程式碼，搞不好會影響整個專案遷移。

這點對普通開發者也很有啟發。很多人用 AI 做專案的時候，總想著一步到位。其實不妨先讓 AI 做一個粗糙的版本，看看哪裡不對，完善好提示詞和規則之後再正式開始，磨刀不誤砍柴工。



### 3、全量翻譯

規則經過試跑驗證之後，就可以全量執行了。

這一步的核心架構可以理解為一個流水線，分為 3 個角色：負責翻譯的 Agent、負責找茬的 Agent、負責修復的 Agent。

![](https://pic.yupi.icu/1/10_%E7%AC%AC3%E6%AD%A5%EF%BC%9A%E5%85%A8%E9%87%8F%E7%BF%BB%E8%AF%91%EF%BC%88%E4%B8%AD%E6%96%87%E7%89%88%EF%BC%89_compressed_v1.png)

每個翻譯好的檔案由 2 個獨立的「找茬 Agent」來檢查，它們的唯一任務就是挑毛病。發現問題後交給「修復 Agent」來處理。

![三角色 Agent 流水線](https://pic.yupi.icu/1/03_%E4%B8%89%E8%A7%92%E8%89%B2Agent%E6%B5%81%E6%B0%B4%E7%BA%BF%EF%BC%9A%E7%BF%BB%E8%AF%91%E3%80%81%E6%89%BE%E8%8C%AC%E3%80%81%E4%BF%AE%E5%A4%8D_compressed_v2.png)

這裡的找茬 Agent 就是前面提到的「對抗性審查」。

為什麼叫對抗性呢？

因為審查者被明確要求「假設這段程式碼是有 Bug 的，你的任務是找出 Bug 在哪」。

這種心態跟人做程式碼審查是一個道理，審查者不能先入為主覺得「他寫的應該沒問題吧」？而是要帶著懷疑的態度去看，才能發現問題。

![對抗性審查](https://pic.yupi.icu/1/04_%E5%AF%B9%E6%8A%97%E6%80%A7%E5%AE%A1%E6%9F%A5%EF%BC%9A%E6%80%80%E7%96%91%E5%BF%83%E6%80%81_vs_%E4%BF%A1%E4%BB%BB%E5%BF%83%E6%80%81_compressed_v3.png)

聽起來很簡單，但是要注意幾個實操細節。

1）工作佇列要機械化。比如什麼檔案翻譯了、什麼檔案沒翻譯，可以透過檢查磁碟上有沒有目標檔案來判斷。這樣整個流程天然可恢復，中斷了重啟就行，不需要維護什麼狀態。

2）翻譯 Agent 和審查 Agent 的對話必須隔離。寫程式碼的 AI 總是傾向於認為自己的程式碼沒問題，所以審查者必須在一個全新的獨立對話裡工作，只看翻譯結果，不看翻譯過程中的推理。

3）模型要分層使用，不需要所有步驟都用最強的。實現翻譯這種高併發的工作可以用相對便宜的模型（比如 Claude Sonnet），而審查和規則制定用最強的模型（比如 Claude Fable、Claude Opus）。Mike 在全量翻譯階段就是用 12 個 Sonnet 子代理並行工作的。

翻譯時如果有拿不準的地方，直接標上 `// TODO(port): <原因>`，不要在這一步糾結，後面編譯器和測試會告訴你到底對不對。



### 4 ~ 6、編譯 + 執行 + 對齊行為

接下來的 3 步套路都一樣：先跑一遍得到錯誤列表，然後讓一批修復 Agent 並行處理這些錯誤，修完了再跑一遍，迴圈往復直到沒有錯誤為止。人工介入的程度越來越低。

![錯誤驅動修復迴圈](https://pic.yupi.icu/1/05_%E9%94%99%E8%AF%AF%E9%A9%B1%E5%8A%A8%E4%BF%AE%E5%A4%8D%E5%BE%AA%E7%8E%AF_compressed_v3.png)

1）編譯階段，把編譯器報出的所有錯誤整理成一份待修復清單，然後讓 AI 按照這份清單逐個修復。

Jarred 的做法是讓編排指令碼對整個工作區跑一次編譯器，把錯誤按模組分組輸出到檔案，然後 64 個「修復 Agent」並行處理錯誤列表。每個修復 Agent 有 2 個對抗性審查者盯著。修復完再編譯，反覆迴圈。

這一步他遇到了一個大問題。

原來的 Zig 程式碼是一整坨放在一起編譯的，他想把 Rust 程式碼拆成 100 個獨立模組來加快編譯速度，但這引入了大量迴圈依賴問題。

於是，他跑了一個專門的工作流來分類哪些程式碼該挪到哪裡，修復迴圈依賴之後暴露出約 16000 個編譯錯誤。16000 個錯誤對人來說是天文數字，但對 64 個並行的 Claude 來說，也就是幾個小時的事。

2）冒煙測試階段，把所有崩潰資訊整理成待修復清單。

編譯透過之後，先讓各個子命令跑起來，把每個崩潰的報錯資訊和對應的子命令儲存到檔案，用同樣的「修復 + 審查」迴圈處理。

3）行為對齊階段，把所有失敗的測試整理成待修復清單。

把測試套件分片跑，每個失敗的測試交給一個修復 Agent，修復之後由對抗性審查者檢查。

![](https://pic.yupi.icu/1/11_%E7%AC%AC4-6%E6%AD%A5%EF%BC%9A%E7%BC%96%E8%AF%91%E3%80%81%E8%BF%90%E8%A1%8C%E3%80%81%E8%A1%8C%E4%B8%BA%E5%AF%B9%E9%BD%90%EF%BC%88%E4%B8%AD%E6%96%87%E7%89%88%EF%BC%89_compressed_v1.png)

Jarred 還有一個巧妙的設計，只允許一個專門的構建守護程序來編譯整個專案。修復 Agent 只提交程式碼，守護程序定期把所有補丁批次編譯、跑受影響的測試、把結果反饋回去。這樣避免了多個 Agent 各自觸發編譯導致的資源衝突和重複工作。

整個過程中，Bun 的 CI 從 972 個測試檔案失敗到全部透過，花了大約 4 天。Linux 最先變綠，Windows 是最後一個。合併之後一共出現了 19 個迴歸 Bug，全部已修復。

![](https://pic.yupi.icu/1/image-20260720165511010.png)

其實 Airbnb 之前也做過類似的事情。他們用 AI 把 3500 個 React 元件測試從 Enzyme 遷移到 React Testing Library，原本估計要一年半，最終 6 周就完成了，用的也是類似的方法。



## 我的感受

看完 Anthropic 這套六步遷移法，說幾個我自己比較有感觸的點。

首先是對抗性審查這件事，大家日常用 AI 程式設計時完全可以做。比如讓一個 Agent 寫完程式碼之後，開一個新的對話讓另一個 Agent 做 code review。在 Claude Code 裡面可以直接用內建的 `/code-review` 命令，或者用 Subagent 來做審查。哪怕不做程式碼遷移，這個習慣也值得養成。

然後是 AI 的成本問題。你敢信？Bun 的遷移花了 **16.5 萬美元**的 API 費用！

![](https://pic.yupi.icu/1/image-20260720182903395.png)

這個數字乍一聽很嚇人，但對比 3 個高階工程師幹一年的薪資加機會成本，便宜太多了。

對於個人開發者來說，一個幾萬行的專案遷移用 Pro 或者 Max 的訂閱額度基本就夠了。至於這個錢花的值不值，自己用人力成本算一筆賬就好。

不過不要盲目跟風遷移。如果現有程式碼跑得好好的、也不難維護，就沒必要折騰了。

**遷移的前提是你確實有一個持續的痛點需要解決。**

像我之前在 Claude Fable 5 限時可用的那幾天裡，瘋狂最佳化自己的工作流，結果純粹是為了最佳化而最佳化，也沒什麼效果，主要是之前 Opus 做的已經很好了。

還有很關鍵的一點，**人的判斷力仍然不可替代**。

Jarred 在整個遷移過程中，每天都在監控工作流的輸出、手動檢查 AI 的行為、發現系統性問題後調整流程。

雖然 AI 執行力很強，但決策權還是在人這邊。

AI 能節省成本，但不代表完全不需要人。



## 寫在最後

幫大家總結一下本文提到的方法，你立刻就能用起來：

1）做任何稍大的重構或遷移之前，先跟 AI 聊出一份規則文件，把「什麼該怎麼改」定義清楚，別上來就動手。

2）先拿 3 個檔案試跑一輪，看看 AI 會犯什麼錯。發現的問題不要逐個修程式碼，而是補到規則文件裡，然後重新生成。

3）寫程式碼的 AI 和審查程式碼的 AI 一定要分開。可以用 Claude Code 的 `/code-review` 命令，或者開一個新對話做獨立審查。

4）善用「錯誤即清單」的思路。編譯報錯、測試失敗、Lint 警告，這些都是天然的任務列表，讓 AI 按清單逐個修復就好。

想想看，連幾十萬行、上百萬行程式碼都能用 AI 完成遷移了，我們平時幾千行、幾萬行的專案重構，還有什麼不敢動的呢？

關鍵不在於 AI 有多聰明，現在模型的能力已經足夠了，更多的要看你給 AI 設計的流程夠不夠好。
