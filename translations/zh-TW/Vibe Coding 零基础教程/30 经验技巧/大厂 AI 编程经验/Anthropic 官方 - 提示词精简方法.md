# Anthropic 官方 - 提示詞精簡方法

> 官方砍掉了 Claude Code 80% 的系統提示詞，跑分居然沒降

大家好，我是程式設計師魚皮。

前段時間 Anthropic 在官方部落格發了一篇文章，說他們針對 Claude Opus 5 和 Fable 5 這兩個新模型，刪掉了 Claude Code **超過 80%** 的系統提示詞，但在編碼評測上的表現居然沒有下降。

![](https://pic.yupi.icu/1/1785753504253-ca87d006-a35e-475f-bdb4-7a4b241e3856.png)

我當時的第一反應是：之前我花大力氣寫的那些提示詞，都白寫了？

但仔細想想，又覺得很合理。之前寫的很多規則，本質上是在彌補舊模型判斷力的不足。當模型能力跟上來之後，這些規則反而成了束縛。

這就好比你教一個新手司機開車，需要告訴他紅燈停綠燈行、轉彎前先打轉向燈。但你不會對一個十年駕齡的老司機重複這些話，因為他早就內化了這些規則，你多說一遍反而會讓他分心。

這篇文章我就帶你看看官方到底是怎麼砍的、背後的原理是什麼，再透過一組實戰對比感受一下短提示詞的效果，最後聊聊我們自己寫提示詞該怎麼做減法。



## 為什麼提示詞要做減法

Anthropic 在他們關於上下文工程的系列部落格中提出了 2 個概念，可以很好地解釋這件事。

第一個叫 **注意力預算（Attention Budget）**。AI 模型和人一樣，工作記憶是有限的。你給它的上下文規則越多，它花在權衡這些規則上的注意力就越多，留給真正幹活的注意力就越少。

第二個是 **上下文的邊際遞減效應**。上下文中的 Token 數量越多，模型精確召回資訊的能力就越差。就像你一次性塞給一個人 100 頁文件，讓他同時記住每一頁的細節，根本不現實。

![](https://pic.yupi.icu/1/01_%E6%B3%A8%E6%84%8F%E5%8A%9B%E9%A2%84%E7%AE%97%E4%B8%8E%E8%BE%B9%E9%99%85%E9%80%92%E5%87%8F%E6%95%88%E5%BA%94_compressed_v2.png)

現在你應該明白 Anthropic 為什麼要砍這麼多系統提示詞了吧。

那具體是怎麼砍的呢？



## Anthropic 具體改了什麼

官方部落格中總結了好幾個關鍵轉變，我挑幾個最有價值的來聊聊。



### 1、從定死規則到讓模型自己判斷

早期為了防止 Claude 誤刪程式碼或亂寫註釋，團隊透過系統提示詞把規則寫得很死，比如下面這段：

```markdown
預設不寫註釋。永遠不要寫多行文件字串或多行註釋塊，最多一行簡短註釋。除非使用者要求，否則不要建立規劃、決策或分析文件。
```

這種「一刀切」的規則肯定不夠靈活。比如有些複雜程式碼確實需要多行註釋，有些使用者也有自己的文件偏好。

但沒辦法，舊模型的判斷力不夠，不這麼約束它就容易亂來，團隊只能接受這個折中方案。

到了新模型時代，這條長長的規則被精簡成了一句話：

```markdown
寫出來的程式碼要像周圍的程式碼，匹配它的註釋密度、命名方式和慣用法。
```

這樣一來，模型就會根據專案現有的程式碼風格來自動適配，而不是被前置規則限制住選擇。

![](https://pic.yupi.icu/1/02_%E4%BB%8E%E5%AE%9A%E6%AD%BB%E8%A7%84%E5%88%99%E5%88%B0%E8%AE%A9%E6%A8%A1%E5%9E%8B%E8%87%AA%E5%B7%B1%E5%88%A4%E6%96%AD_compressed_v1.png)



### 2、從給示例到設計好介面

以前有個經典的提示詞技巧叫 Few-shot，就是給 AI 舉例子。比如 AI 不知道怎麼呼叫某個工具，你就寫 3 個示例給它看。

但 Anthropic 發現，在新模型上面，示例反而會限制模型的探索空間，因為新模型的理解能力比你給的示例更強，示例反而把它框住了。

他們的建議是，與其寫一堆示例教 AI 怎麼用工具，不如把工具本身的用法設計得更清晰。

他們拿 Claude Code 裡管理待辦任務的 Todo 工具來舉例，這個工具有待辦、進行中、已完成三種狀態，引數名分別叫 `pending`、`in_progress`、`completed`，AI 一看就知道什麼意思，根本不需要你再寫示例教它。

設計好的介面自己就能說明用法，只有設計得糟糕的介面才需要一堆說明書。



### 3、從一股腦全塞進去到按需載入

以前 Claude Code 的系統提示詞裡包含了大量關於程式碼審查、驗證等方面的詳細指引。這些內容不是每次都用得到，但萬一需要的時候又很關鍵，所以只能全塞進去。

現在 Anthropic 把這些內容拆成了獨立的 Skills 技能包，模型在需要的時候才去載入。甚至連一些工具定義也做成了「延遲載入」模式，模型要用的時候才會透過 ToolSearch 去獲取完整的工具描述，平時不佔用上下文。

這種策略叫做 **漸進式披露（Progressive Disclosure）**，如果你讀過本教程程式設計工具板塊「工具實戰」目錄中的《Agent Skills：通用 AI 技能庫》，對這個術語應該不陌生了。

![](https://pic.yupi.icu/1/03_%E6%B8%90%E8%BF%9B%E5%BC%8F%E6%8A%AB%E9%9C%B2%E6%8C%89%E9%9C%80%E5%8A%A0%E8%BD%BD_compressed_v3.png)

這個思路也適用於我們自己寫的 CLAUDE.md 和 Skills 檔案。很多人喜歡把 CLAUDE.md 寫成一個事無鉅細的百科全書，覺得如果不寫全，模型就找不到。

但 Anthropic 建議把內容拆成多個檔案，形成一個樹狀結構。就像你整理電腦檔案一樣，不會把所有文件都堆在桌面上，而是按類別分到不同的資料夾裡，需要什麼就開啟什麼。



### 4、從手動記憶到自動記憶

以前使用者需要手動按 `#` 快捷鍵把重要資訊儲存到 CLAUDE.md，現在 Claude 會自動儲存和你工作相關的記憶。

CLAUDE.md 的定位也因此發生了變化，Anthropic 建議把它保持輕量，重點寫專案中的「坑」和那些模型看程式碼看不出來的特殊約定。像目錄結構、依賴列表這種模型自己就能讀到的資訊，就不需要再手動寫進去了。

![](https://pic.yupi.icu/1/04_%E4%BB%8E%E6%89%8B%E5%8A%A8%E8%AE%B0%E5%BF%86%E5%88%B0%E8%87%AA%E5%8A%A8%E8%AE%B0%E5%BF%86_compressed_v2.png)



### 5、減少矛盾指令

Anthropic 在審查自己團隊使用 Claude Code 的對話記錄時，還發現了一個有意思的問題。

同一個請求裡，系統提示詞說的是「適當新增文件」，但 Skills 裡又寫了「不要新增註釋」，兩條指令是矛盾的。

雖然模型大部分時候能根據上下文猜到使用者的真實意圖，但它得額外花精力去處理這些衝突，白白浪費了注意力預算。

於是他們砍掉了冗餘的規則，這類矛盾自然就少了很多。

![](https://pic.yupi.icu/1/05_%E7%9F%9B%E7%9B%BE%E6%8C%87%E4%BB%A4%E8%AE%A9%E6%A8%A1%E5%9E%8B%E5%9B%B0%E6%83%91_compressed_v3.png)



## 長短提示詞實戰對比

原理講得差不多了，為了直觀地感受新模型在短提示詞下的表現，我做了一組實戰對比測試。

我用的是 Cursor + Claude Opus 5，任務是讓 AI 復刻一個 Cursor 網頁版，分別用風格完全不同的兩種提示詞來跑。

第一種是規則堆砌型的長提示詞，包含一堆具體的技術要求和開發步驟：

![](https://pic.yupi.icu/1/1785921294571-9f9acde0-232f-4571-8f39-8f8c8f1a464f.png)

第二種是短提示詞，就 5 行話，只說了要做什麼和用什麼方式調研：

```plain
基於 VS Code 開源生態做一個類似 Cursor 的 Web AI 程式設計工具，
支援 Editor Window 和 Agents Window。
先用 Firecrawl 搜 Cursor 3 的產品設計，
再用 Context7 查 monaco-vscode-api 的 Web 整合方案，
調研完先出技術方案，確認後再寫程式碼。
```

有趣的是，兩種提示詞在正式寫程式碼之前就表現得不一樣了。

在前期調研規劃階段，短提示詞那邊主動進入了 Plan 模式，先規劃好完整的 Todo 列表才開始動手；長提示詞那邊反而沒有進入 Plan 模式，收到指令就直接開寫了。

![短提示詞規劃後的 Todo 列表](https://pic.yupi.icu/1/1785908352580-d2cafcaf-d694-40a9-98e7-3ea556571265.png)

從程式碼量來看，短提示詞版本一共跑出了 12984 行程式碼，長提示詞版本只有 8384 行，少了將近三分之一。

我們正常的直覺可能是，提示詞越長、資訊量越大、生成的程式碼量就應該越多。但結果恰恰相反，說明短提示詞下 AI 反而更能放開手腳地探索和生成。

從成品效果上來看，短提示詞生成的程式碼一次跑通，而且功能相當齊全。

可以正常切換 Edit 和 Agent 模式視窗，目錄樹載入正常，檔案的增刪改查都沒問題，程式碼語法高亮和自動補全也有，甚至連 git 功能都做了。除此之外還支援切換主題、終端可以正常使用、搜尋和快捷鍵也都到位了。最關鍵的是，Agent 模式可以正常接入模型來生成程式碼。

![短提示詞版本](https://pic.yupi.icu/1/1785913712132-b278c6d8-521a-4d60-9a64-5cb90fef59a0.png)

長提示詞生成的效果就有點兒翻車了，放張圖大家自己感受一下差距。

![長提示詞版本](https://pic.yupi.icu/1/1785942480484-bdb66780-bc13-4d2c-8da3-dc88a18aaa55.png)

得益於 Opus 5 的智慧，兩種提示詞生成的 Cursor 網頁版都能正常呼叫 AI Agent 來生成程式碼。我把它們都接入了 DeepSeek API，讓它們各自寫一個貪吃蛇小遊戲，用的模型是 DeepSeek V4 Flash，生成過程很絲滑。

短提示詞做的 Cursor 在生成程式碼前會顯示思維鏈和呼叫了什麼工具，整個互動體驗更完整。

![](https://pic.yupi.icu/1/1785981173449-df6ee5ce-64aa-456c-87cf-dea06f4dac33.png)

長提示詞做的 Cursor 則是直接開寫，沒有思維鏈展示。

![](https://pic.yupi.icu/1/1785981359513-9ece52c4-c252-406f-be73-08ca1f401ec9.png)

最後兩個版本生成的貪吃蛇小遊戲都能正常執行。AI 發展成現在這樣，我居然能夠輕鬆地用 AI 程式設計工具做個 AI 程式設計工具，然後讓做出來的 AI 程式設計工具再來 AI 程式設計。

![](https://pic.yupi.icu/1/1785913338340-fa358bbe-5512-4ba6-b2b3-d6366573c3f3.png)

測試做到這裡結果已經很明顯了。短提示詞開發的 Cursor 無論是功能完善度、程式碼質量還是一次跑通的成功率，都完勝長提示詞版本。

核心原因就在於，長提示詞把模型的行為框住了，它只敢在你劃定的範圍內做事。而短提示詞給了模型足夠的探索空間，模型自己根據對 Cursor 這個產品的理解，主動補全了很多它認為應該有的功能。



## 我們該怎麼做減法

以前模型能力不夠，對很多產品和技術的認知是模糊的，你必須手把手告訴它每個細節。現在新模型的訓練資料更豐富、推理能力更強，再加上有 MCP、Skills 這些工具讓模型的探索自由度更高，那些重複的規則反而成了負擔，既浪費 Token，又搶佔模型幹活時的注意力，還容易跟其他 Skills 的規則產生衝突。

那我們該怎麼判斷一條提示詞有沒有必要寫呢？

我是這樣判斷的：**如果一件事是這個任務天然就包含的常識，就不用寫。** 比如你讓 AI 寫一個 REST API 介面，不需要告訴它要處理錯誤、要返回 JSON，這些模型已經知道了。

**如果一件事是這個任務的特殊要求，跟通常做法不一樣，才需要明確告訴模型。** 比如你的專案規定所有介面必須用 snake_case 命名、錯誤碼必須遵循某個內部標準，這些才是值得寫進規則的內容。

換個角度來說，你的程式碼倉庫本身就是很好的提示詞。專案結構、程式碼風格、測試用例，這些模型都能自己讀到並理解。你要做的是把專案架構設計好，而不是把規則寫成一篇小作文。



## 用 /doctor 命令自動最佳化

為了幫開發者跟上這個變化，Claude Code 還內建了一個 `/doctor` 命令（也可以用 `/checkup`），可以自動掃描你的 Skills、CLAUDE.md 等配置檔案，幫你檢測哪些內容是冗餘的、哪些可以精簡。

![](https://pic.yupi.icu/1/1785830100705-ba0f3f43-ba78-43e0-bf59-5dabcf2f2c61.png)

具體來說，它會做這麼幾件事：

- 檢查 CLAUDE.md 裡有沒有寫目錄結構、依賴列表這些模型自己就能從程式碼庫讀到的資訊，有就建議你刪掉
- 找出沒用到的 Skills 和 MCP 服務
- 檢測本地和倉庫裡的 CLAUDE.md 有沒有重複或矛盾
- 針對那些不需要每次都載入的內容，建議你遷移到可以按需載入的 Skills 裡

而且所有變更都會先給你看報告，等你確認後才會執行，不用擔心它亂改你的配置。

我用自己的專案實測了一下，它幫我最佳化了一部分配置內容，但沒有對 CLAUDE.md 做大的改動，說明我這個專案的規則還算健康。

![](https://pic.yupi.icu/1/1785830217113-f4cf3ca0-4d3b-42f7-9dae-a0d8f590bc5b.png)



## 寫在最後

AI 程式設計領域的變化真的太快了。前幾個月我還在研究怎麼把提示詞寫得更完美，還覺得專案規則寫得越詳細 AI 幹活的方向就越準確，結果現在官方直接宣佈，之前精心打磨的很多規則其實都是束縛。

Anthropic 在官方部落格的最後總結了一句話，我覺得特別精妙：**找到那組最小的、高訊號的 Token 集合，來最大化你想要的結果。**

以後寫提示詞，少即是多。Less is More，你的很多提示詞真的可以丟掉了。

當然，做減法不等於什麼都不寫。把需求和目標描述清楚，仍然是最重要的事，只是不用再事無鉅細地規定每一步該怎麼做了。關於怎麼把需求描述清楚，可以繼續閱讀本板塊中的《Vibe Coding 對話工程技巧》和《用 grill-me 讓 AI 拷問你的需求》。
