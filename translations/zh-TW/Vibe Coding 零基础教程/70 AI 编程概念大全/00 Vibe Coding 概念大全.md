## AI 基礎概念


### 人工智慧（AI）

人工智慧（Artificial Intelligence）是讓計算機模擬人類智慧的技術。簡單來說，就是讓機器能像人一樣思考、學習和解決問題。

在 Vibe Coding 中，AI 就是你的程式設計助手。你只管告訴它要做什麼，它就會嘎嘎幫你做方案、寫程式碼、修 Bug。就像你有一個 24 小時線上的程式設計師朋友，隨時可以幫你幹活。




### 大語言模型（LLM）

大語言模型（Large Language Model）是一種能夠理解和生成人類語言的 AI 系統。ChatGPT、Claude、Gemini、DeepSeek 都是大語言模型。

為什麼叫 “大” 模型呢？因為這些模型的 **引數量** 非常龐大，動輒幾十億甚至上萬億個引數。引數越多，模型通常越聰明，但也越消耗計算資源。

你可以把大語言模型理解成一個讀過海量書籍和程式碼的超級學霸，它見過無數的程式設計案例，所以能幫你寫程式碼、解釋程式碼、修復 Bug。

![](https://pic.yupi.icu/1/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E6%98%AF%E4%BB%80%E4%B9%88%E5%A4%A7.jpeg)

除了文字大語言模型之外，AI 領域還有專門處理圖片的視覺模型（比如 Stable Diffusion）、處理語音的音訊模型（比如 Whisper）、以及能同時處理文字、圖片、音訊的多模態模型（如 GPT-4o、Gemini）。在 AI 程式設計時，我們主要和文字大語言模型打交道。



### Token（詞元）

Token 是 AI 模型處理文字的基本單位，中文叫做 “詞元”。你可以簡單理解為 “詞塊”，是大模型把文字拆分後的最小單元。

Token 是你必須掌握的核心概念，因為 AI 服務通常按照 Token 收費。你輸入的文字和 AI 輸出的文字都會消耗 Token。Token 用得越多，花的錢就越多。

在英文中，一個 Token 大約是一個單詞或單詞的一部分。在中文中，一個漢字通常是 1 ~ 2 個 Token。不同模型使用的分詞器（Tokenizer）不同，所以同一段文字在不同模型中可能對應不同數量的 Token。

值得一提的是，國產大模型（比如通義千問、DeepSeek）針對中文做了專門最佳化，1 個 Token 大約可以表示 1.5 ~ 1.8 個漢字，比早期的英文模型效率高不少。

舉個例子來幫助大家理解：

- "Hello World" 大約是 2 個 Token
- “你好世界” 大約是 4 ~ 6 個 Token

![](https://pic.yupi.icu/1/image-20260112112612434.png)

目前很多 AI 程式設計工具（比如 Cursor、Claude Code）都自帶了 Token 消耗量的實時統計和展示，方便你隨時掌握用量和成本。



### 輸入 Token 和輸出 Token

AI 服務在計費時，一般會分別計算輸入和輸出的 Token。

- 輸入 Token：你發給 AI 的內容，比如提示詞、程式碼、檔案等
- 輸出 Token：AI 返回給你的內容，比如回答、生成的程式碼、工具呼叫指令等

一般來說，輸出 Token 比輸入 Token 更貴。以 Claude Sonnet 4 為例，輸入價格是 3 美元/百萬 Token，輸出價格是 15 美元/百萬 Token，貴了 5 倍。這是因為生成內容比理解內容更消耗算力。

最簡單的一個省 Token 小技巧是：**用心編寫簡潔清晰的提示詞**，讓 AI 一次就能理解你的需求，減少反覆對話。更多省 Token 技巧可以看看魚皮分享過的影片：[AI 程式設計省錢技巧](https://www.bilibili.com/video/BV1pAy5BXE5z)



### Token 快取

Token 快取是一個能幫你省大錢的機制。簡單來說，大模型在處理你的提示詞時，需要做大量的計算。如果你連續多次對話，很多內容（比如系統提示詞、引用的程式碼檔案）是重複的，每次都重新計算就太浪費了。快取機制會把這些中間計算結果儲存下來，下次遇到相同的字首內容就直接複用，不僅更快，還更便宜。

快取相關的 Token 分為兩種：

- 快取寫入 Token：AI 第一次處理你的上下文時，會把計算結果存起來，比普通輸入略貴一點
- 快取讀取 Token：後續再用相同的上下文時，直接複用快取，**價格甚至可以低到普通輸入的 1/10**，非常便宜

![](https://pic.yupi.icu/1/Token%E7%BC%93%E5%AD%98%E6%9C%BA%E5%88%B6%E5%A4%A7.jpeg)

所以在對話時，儘量保持上下文穩定，比如引用的檔案、規則檔案不要頻繁改動，這樣能持續享受快取優惠。有時候你會發現連續對話比開新對話更省錢，就是因為快取在起作用。



### 模型引數

引數是模型在訓練過程中學到的 “知識點”，用數字的形式儲存在模型中。

舉個好理解的例子，模型在訓練時讀到了大量 “天空是藍色的” 這類內容，它就會在引數中記住 “天空” 和 “藍色” 之間的關聯關係。引數越多，模型能記住的知識和關聯就越豐富。

引數量直接影響模型的能力和使用成本。引數越多，模型越聰明，但執行時消耗的算力（GPU 計算資源）也越多，所以價格也越貴。

目前主流大模型中，明確公開引數量的有：

- DeepSeek-V4-Pro：1.6 萬億引數（採用 MoE 混合專家架構，實際啟用 490 億）
- DeepSeek-V4-Flash：2840 億引數（啟用 130 億）
- Qwen3.8-Max：2.4 萬億引數（通義千問最新旗艦模型，同樣是 MoE 架構，實際啟用 950 億，只佔總引數的 4% 左右）
- Llama 4 Scout：1090 億引數（Meta 開源模型，啟用 170 億）

值得一提的是，即使是同一系列的大模型，廠商也會提供不同引數量的版本供你選擇。

![](https://pic.yupi.icu/1/image-20260302162302260.png)




### 模型訓練和推理

訓練（Training）是讓 AI 模型從大量資料中學習知識的過程。這個過程需要海量的計算資源和時間，一般由 AI 公司完成。絕大多數情況下，你不需要自己訓練模型，直接用訓練好的成品就行。

推理（Inference）是模型訓練完成、具備了知識之後，用學到的知識來回答問題、生成內容的過程。我們日常使用 AI 工具，比如和 ChatGPT 對話、讓 Cursor 寫程式碼，本質上都是 AI 模型在進行推理。

打個比方，訓練就像學生上學讀書，推理就像學生參加考試答題。

![](https://pic.yupi.icu/1/%E6%A8%A1%E5%9E%8B%E8%AE%AD%E7%BB%83%E5%92%8C%E6%8E%A8%E7%90%86%E5%A4%A7.jpeg)




### 模型微調（Fine-tuning）

微調是在已有模型的基礎上，用特定領域的資料繼續訓練，讓模型在某個領域表現更好。

比如，你可以用大量的醫學資料微調一個模型，讓它成為醫學專家。或者用你公司的程式碼庫微調，讓它更瞭解你的專案風格。

對於普通使用者來說，微調成本較高，一般不需要自己做，直接使用現成的模型就夠了。不過，很多大模型應用開發平臺（比如阿里雲百鍊、火山引擎等）都提供了模型微調的能力，降低了微調的門檻。

![](https://pic.yupi.icu/1/image-20260302163159965.png)



### 模型蒸餾

模型蒸餾，也叫知識蒸餾（Knowledge Distillation），是一種把大模型的知識 “壓縮” 到小模型裡的技術。

就像一個經驗豐富的高階開發帶新人，高階開發（教師模型）不只是告訴新人最終答案，還會分享自己的推理過程和思考邏輯。新人（學生模型）透過學習這些思維方式，能做出接近的決策，但成本低得多。

蒸餾的核心在於 “軟標籤”。舉個例子，讓大模型識別一張動物圖片，它不會只說 “這是狗”，而是會給出一組機率：狗 92%、貓 5%、狼 3%。那個 5% 的 “貓” 其實包含了珍貴的資訊，說明這張圖裡的動物和貓有某些相似特徵。小模型透過學習這些機率分佈，能學到類別之間的微妙關係，效果比只看 “對或錯” 的硬標籤好得多。

蒸餾的好處非常多，比如成本降低 5 ~ 30 倍、推理速度提升 4 倍、效能保留 95% 以上。典型案例就是 DeepSeek-R1 的蒸餾版本，用 671 億引數的教師模型訓練出 32 億引數的學生模型，效能依然出色。最新的 DeepSeek-V4 系列也延續了這一思路，透過 MoE 架構讓 1.6 萬億引數的模型僅啟用 490 億引數就能達到強大的推理能力。

蒸餾和微調有什麼區別呢？

微調是在已有模型基礎上用特定資料繼續訓練，讓它在某個領域更專業；蒸餾是把大模型的知識轉移到小模型裡，讓小模型更輕量、更便宜。



### 上下文視窗

上下文視窗（Context Window）是指 AI 模型一次能 “記住” 的最大內容量，用 Token 來衡量。

不同模型的上下文視窗大小不同：

- GPT-4o：128K Token（約 10 萬中文字）
- GPT-5.5：1M Token（約 75 萬中文字）
- Claude Opus 4.8：標準 200K Token，支援擴充套件到 1M Token（約 75 萬中文字）
- Gemini 3.1 Pro：1M Token（約 75 萬中文字），且支援同時處理文字、圖片、音訊、影片
- DeepSeek-V4-Pro：1M Token（約 75 萬中文字）

上下文視窗越大，AI 能處理的程式碼量就越多，能記住的對話歷史就越長。如果你的專案程式碼很多，或者你不確定 AI 能否在一次對話中完成任務，選擇上下文視窗大的模型會更合適。

但要注意，上下文視窗越大，每次請求消耗的 Token 也越多，成本也會更高。比如在 Cursor 中使用 Claude Sonnet 模型時，單次請求超過 20 萬 Token，輸入價格就會翻倍。



## 提示詞相關


### 提示詞（Prompt）

提示詞是你給 AI 的指令或問題。在 AI 程式設計中，提示詞就是你用自然語言描述的需求。

提示詞的質量直接決定了 AI 輸出的質量。一個好的提示詞應該：

- 具體明確
- 包含必要的背景資訊
- 說明期望的輸出格式

比如，“做一個網站” 是一個模糊的提示詞，而 “用 React 做一個記賬網站，包含新增支出、檢視列表、統計總額三個功能，介面用藍色調” 就是一個更好的提示詞。

在 AI 對話中，訊息一般分為 3 種角色：

- 系統提示詞（System）：設定 AI 的角色和行為規則，對使用者不可見
- 使用者提示詞（User）：你傳送給 AI 的訊息
- 助手提示詞（Assistant）：AI 回覆給你的訊息

理解這 3 種角色有助於你更好地使用 AI。比如很多 AI 程式設計工具允許你設定系統提示詞來定義 AI 的行為規則，而你在對話方塊中傳送的內容就是使用者提示詞。

![](https://pic.yupi.icu/1/1745462990451-6f2b5727-d47b-436c-9da2-50dac64fb790.png)



### 系統提示詞

系統提示詞（System Prompt）是在對話開始前給 AI 設定的指令，用來定義 AI 的角色、行為和限制。

比如，你可以設定系統提示詞：“你是一位資深的 Java 後端開發專家，請用簡潔清晰的程式碼風格回答問題。”

系統提示詞在整個對話過程中都會生效，是定製 AI 行為的重要方式。

還記得前幾年 AI 剛流行的時候，市面上冒出了一大堆 AI 助手網站麼？其實很多就是 “套殼”，底層呼叫的是同一個大模型，只不過給不同的 AI 助手設定了不同的系統提示詞，比如 “你是一個翻譯專家”、“你是一個法律顧問” 等。

![](https://pic.yupi.icu/1/%E4%B8%BB%E9%A1%B5.png)



### 提示詞工程

提示詞工程（Prompt Engineering）是設計和最佳化提示詞的技術，目的是讓 AI 更好地理解你的意圖，生成更符合預期的結果。

這是 Vibe Coding 的核心技能之一。好的提示詞工程師能用更少的對話輪次、更低的 Token 成本，讓 AI 生成更高質量的程式碼。

想學習編寫提示詞的實戰技巧，可以看看魚皮的免費《AI 程式設計教程》：[提示詞編寫技巧](https://ai.codefather.cn/library/2010974716125712386)

![](https://pic.yupi.icu/1/image-20260302164120604.png)



### 零樣本提示（Zero-shot）

零樣本提示是指在給 AI 下達任務時，不提供任何示例，直接描述你的需求讓 AI 去完成。

比如：“請把這段英文翻譯成中文。”

AI 會根據自己的訓練知識來完成任務。

對於簡單任務，零樣本提示一般就夠用了，不需要提供額外的示例內容，還能節約一些 Token 成本。



### 少樣本提示（Few-shot）

少樣本提示是指在給 AI 下達任務時，額外提供幾個輸入輸出的示例，讓 AI 透過這些示例學習你想要的格式或風格，從而更準確地完成任務。

比如：

```
請按以下格式翻譯：
英文：Hello → 中文：你好
英文：Thank you → 中文：謝謝
英文：Good morning → 中文：
```

透過提供示例，AI 能更準確地理解你的需求，輸出更一致的結果。

![](https://pic.yupi.icu/1/image-20260302164402338.png)



### 思維鏈提示（Chain-of-Thought）

思維鏈提示（Chain-of-Thought，簡稱 CoT）是一種引導 AI 展示推理過程、一步一步思考問題的提示技術，而不是讓 AI 直接給出答案。這對於複雜的推理任務特別有效，比如多步驟的數學計算、程式碼邏輯分析、系統架構設計等。

觸發思維鏈提示的方法很簡單。很多推理模型（比如 DeepSeek-R1）和 AI 程式設計工具天然內建了思維鏈能力，會自動展示推理過程。你也可以在提示詞中手動加上 “請一步一步思考”，AI 就會展示它的推理過程，一般能得到更準確的答案。

在 AI 程式設計中，涉及複雜業務邏輯、多模組互動、或者需要權衡多種技術方案的專案，特別適合利用推理模型和思維鏈提示能力，讓 AI 想清楚再動手。

![](https://pic.yupi.icu/1/chainofthought.png)



### Markdown 語言

Markdown 是一種輕量級的文字標記語言，用簡單的符號來表示格式。比如用 `#` 表示標題，用 `**文字**` 表示加粗，用 `-` 表示列表。

![](https://pic.yupi.icu/1/image-20260302164811601.png)

在 AI 程式設計中，Markdown 非常重要，因為：

- AI 生成的回答大多數都是 Markdown 格式
- 專案文件（如 README）採用 Markdown 編寫
- 定義 AI 智慧體的規則檔案也是 Markdown 格式

學會 Markdown 能讓你更好地跟 AI 交流，也能寫出更規範的專案文件。更重要的是，結構化的內容（標題層級、列表、程式碼塊等）有助於 AI 更準確地理解你的意圖，同時也能培養你自己的結構化思維能力，這對寫好提示詞非常有幫助。




## AI 程式設計模式


### Vibe Coding 氛圍程式設計

Vibe Coding 是由電腦科學家 Andrej Karpathy 在 2025 年 2 月提出的概念。它描述了一種全新的程式設計方式：透過自然語言和 AI 對話，讓 AI 幫你寫程式碼，你只需要描述需求、測試結果、指導方向。

你不需要精通程式設計語法，只需要能清楚表達你的想法，AI 負責把你的想法變成可執行的程式碼。

所以說，Vibe Coding 的重點不是寫程式碼，而是明確需求並清晰表達。你描述得越清楚，AI 給你的結果就越靠譜。

這就像點外賣一樣，你告訴外賣平臺你想吃什麼，餐廳幫你做好送到手上。你不需要會做飯，但要知道自己想吃什麼。



### Agentic Engineering 智慧體工程

Agentic Engineering（智慧體工程）是 2026 年 2 月由 Andrej Karpathy（也就是提出 Vibe Coding 的那位大佬）提出的新概念，可以理解為 Vibe Coding 的規範版。

Vibe Coding 就是跟著感覺寫程式碼：你給 AI 一句話，AI 吐出程式碼，能跑就行，跑不了就把報錯粘回去讓 AI 再改。做個小工具賊拉快，但專案一大就容易翻車。

而 Agentic Engineering 的思路是：你先想清楚要幹嘛、寫好方案、拆好任務，再把活交給 AI 去執行，它幹完了你還得驗收，質量不行再打回去重做。

打個比方，Vibe Coding 的時候你是個 DJ，放什麼歌全憑感覺；Agentic Engineering 裡你是包工頭，流程、質量、驗收都得你說了算。**一個跟著感覺走，一個按流程來。**

當然，不是說 Vibe Coding 已經過時了。Vibe Coding 負責讓你看到可能性，Agentic Engineering 負責把可能性變成真正能用的東西。二者適用於不同的場景，做小工具時可以用 Vibe Coding，做企業級專案就需要 Agentic Engineering 的思維。

![](https://pic.yupi.icu/1/agentic%20engineering.jpeg)



### Agentic Coding 智慧體程式設計

Agentic Coding 智慧體程式設計是指讓 AI 像一個自主的 “智慧體”（Agent）一樣工作，能夠自己規劃任務、執行操作、驗證結果，而不只是被動地回答問題。

它和前面提到的 Agentic Engineering 的區別在於，Agentic Coding 強調的是 AI 的自主執行能力（AI 能幹什麼），而 Agentic Engineering 強調的是人對 AI 的管理方法論（人該怎麼管）。

如今，幾乎所有主流 AI 程式設計工具都提供了智慧體程式設計的能力。比如在 Cursor 的 Agent 模式中，AI 可以：

- 自動讀取和分析多個檔案
- 規劃實現方案
- 執行程式碼修改
- 執行測試驗證
- 自動修復問題

這比傳統的問答式 AI 更強大，因為它能自主完成複雜的多步驟任務。可以說，AI 不再只是輔助程式設計的配角，而是正在成為專案開發的核心驅動力。

![](https://pic.yupi.icu/1/agent-in-cursor.png)



### Harness Engineering 駕馭工程

Harness Engineering（駕馭工程）是 2026 年興起的 AI 工程新正規化，核心理念是 **人類掌舵 + 智慧體執行**。它不是去最佳化 AI 模型本身，而是圍繞 AI 智慧體搭建一整套約束機制、反饋迴圈和工作流管理系統，讓原本不可預測的 AI 在高可靠性環境下跑得穩、跑得快。

Harness 這個詞本意是 “馬具”，就像韁繩和馬鞍用來引導強大但難以預測的馬匹一樣，Harness Engineering 就是圍繞 AI 程式設計智慧體搭建的整套 “執行環境”，確保 AI 能按照你的預期工作。

![](https://pic.yupi.icu/1/2_harness_horse.png)

為什麼這個概念越來越重要呢？

因為在 AI 程式設計時代，**模型本身已經是通用商品，真正的競爭力在於你圍繞模型搭建的工程體系**。同一個大模型，在不同的 Harness 環境下，程式碼質量可能天差地別。程式設計師的角色正在從 “自己寫程式碼” 轉變為 “設計讓 AI 可靠寫程式碼的系統”。

![](https://pic.yupi.icu/1/8_agent_queals.png)

從發展路徑來看，Harness Engineering 是在提示詞工程和上下文工程基礎上的進一步演進。提示詞工程關注「怎麼給 AI 下指令」，上下文工程關注「怎麼給 AI 提供資訊」，而 Harness Engineering 關注的是「怎麼讓 AI 持續靠譜地幹完一整件事」，三者是層層包含的關係。

![](https://pic.yupi.icu/1/7_harness_layers.png)

Harness 的核心模組包括：

- 上下文架構（讓 AI 瞭解專案背景和規矩）
- 執行能力（給 AI 裝上工具和 MCP）
- 任務編排（Plan Mode、SubAgents 並行執行等）
- 反饋機制（Linter、自動化測試、Browser Use）
- 架構護欄（防止程式碼越改越亂）

![](https://pic.yupi.icu/1/20_harness_modules.png)




### Loop Engineering 迴圈工程

Loop Engineering（迴圈工程）是 2026 年中期興起的 AI 程式設計新正規化，核心理念是 **設計自動迴圈系統，讓 AI 自主執行、自主驗證、自主修復，直到達成目標**。

以前的 AI 程式設計模式就像開手動擋的車，每一步都靠你自己操作。Loop Engineering 更像自動駕駛，你提前設定好目的地和安全規則，AI 自己執行、自己檢查、自己修復，直到任務完成。

![](https://pic.yupi.icu/1/01_Loop_Engineering%E6%A0%B8%E5%BF%83%E6%A6%82%E5%BF%B5%EF%BC%9A%E4%BD%A0%E8%AE%BE%E8%AE%A1%E7%B3%BB%E7%BB%9F%E8%AE%A9%E5%AE%83%E4%BB%A3%E6%9B%BF%E4%BD%A0%E7%BB%99AI%E4%B8%8B%E6%8C%87%E4%BB%A4_compressed_v1.png)

一個靠譜的 Loop 需要 3 樣核心的東西：

- **明確的目標和停止條件**：比如「所有測試透過」就是好的停止條件
- **反饋閉環**：每輪迴圈結束後自動檢查結果，判斷是繼續還是停止
- **狀態記憶**：用外部檔案（如 PROGRESS.md）記錄進度，斷了重啟不會從零開始

![](https://pic.yupi.icu/1/03_Loop%E7%9A%843%E5%A4%A7%E6%A0%B8%E5%BF%83%E8%A6%81%E7%B4%A0%EF%BC%9A%E7%9B%AE%E6%A0%87%E5%81%9C%E6%AD%A2%E6%9D%A1%E4%BB%B6%E3%80%81%E5%8F%8D%E9%A6%88%E9%97%AD%E7%8E%AF%E3%80%81%E7%8A%B6%E6%80%81%E8%AE%B0%E5%BF%86_compressed_v2.png)

從發展路徑來看，Loop Engineering 是在提示詞工程、上下文工程和 Harness Engineering 基礎上的進一步演進。前面幾步讓 AI 能在靠譜的環境裡幹活，Loop 則在這些基礎上多加了一層「自動迴圈 + 反饋閉環」的機制，讓你從「一句一句手動提示 AI」的操作者變成「設計迴圈規則」的管理者。

![](https://pic.yupi.icu/1/04_AI%E7%BC%96%E7%A8%8B%E8%BF%9B%E5%8C%964%E9%98%B6%E6%AE%B5%EF%BC%9APrompt%E2%86%92Context%E2%86%92Harness%E2%86%92Loop_compressed_v3.png)



### 多智慧體協作

多智慧體協作（Multi-Agent）是指多個 AI 智慧體分工合作，共同完成複雜任務。

比如，一個智慧體負責設計架構，一個負責寫前端程式碼，一個負責寫後端程式碼，一個負責程式碼審查。它們像一個軟體開發團隊一樣協作。

這兩年，多智慧體系統正在成為 AI 程式設計的重要趨勢。它的優勢不僅僅是能處理更復雜的專案，還能透過並行工作大幅提升效率，讓原本需要幾小時的任務在幾分鐘內完成。

![](https://pic.yupi.icu/1/%E5%A4%9A%E6%99%BA%E8%83%BD%E4%BD%93%E5%8D%8F%E4%BD%9C%E5%A4%A7.jpeg)



### 智慧體編排

編排（Orchestration）是指協調和管理多個 AI 智慧體或 AI 任務的過程，確保它們按正確的順序和方式工作。

如果說多智慧體協作關注的是 “有哪些角色參與”，那編排關注的是 “誰先幹、誰後幹、結果怎麼彙總”，它是多智慧體系統的指揮中樞。

就像樂隊指揮一樣，編排器決定哪個智慧體在什麼時候做什麼事情、如何傳遞資訊、如何彙總結果。

![](https://pic.yupi.icu/1/image-20260112112854174.png)



### Subagents 子代理

Subagents（子代理）是指主 AI 智慧體將部分任務分派給獨立的子智慧體來並行處理的機制。

你可以把它理解成 AI 的下屬，就像一個經理把活分給手下的幾個員工同時幹一樣。當主 AI 遇到一個大任務時，它可以把獨立的小任務分給幾個子代理同時幹，自己繼續處理其他工作。

Subagents 的好處是：

- 並行處理多個獨立任務，效率翻倍
- 主代理的上下文保持乾淨，不會被子任務的細節汙染
- 每個子代理可以專注於自己的任務，結果更準確

比如你可以讓幾個子代理同時審查程式碼庫的不同模組，速度會快很多。

![](https://pic.yupi.icu/1/%E5%AD%90%E4%BB%A3%E7%90%86%E6%BC%AB%E7%94%BB%E5%A4%A7.jpeg)

在 Claude Code 中，AI 會透過內建的 Task 工具自動生成子代理來處理子任務，你不需要做額外配置。你也可以在 `.claude/agents/` 目錄下建立自定義的子代理（用 Markdown 檔案定義），給它指定專屬的角色描述、工具許可權和行為規則。

不過子代理也有侷限，每個子代理的上下文是獨立的，它們之間無法直接共享資訊，所以不適合有強依賴關係的任務。另外，多個子代理同時執行會消耗更多 Token，成本會相應增加。就像公司招人一樣，多招幾個人確實能幹得更快，但工資支出也得跟著漲，而且人多了溝通協調的成本也會上來。



### Agent Teams 智慧體團隊

[Agent Teams](https://code.claude.com/docs/en/agent-teams)（智慧體團隊）是 2026 年興起的多智慧體程式設計新模式，由 Claude Code 率先推出。它讓 3 ~ 5 個獨立的 AI 智慧體組成團隊，在同一個專案上並行工作。

和傳統的單 AI 對話不同，Agent Teams 中有一個 Team Lead（隊長）負責拆解任務和協調工作，其他 Teammates（隊員）各自領取任務獨立執行，還能透過訊息系統互相溝通。

![](https://pic.yupi.icu/1/subagents-vs-agent-teams-light.png)

打個比方，以前用 AI 程式設計就像你一個人帶一個實習生幹活，現在 Agent Teams 相當於你直接管了一個小團隊，前端、後端、測試同時幹，效率翻了好幾倍。Anthropic 的工程團隊曾用 16 個 Agent 同時工作，產出了 10 萬行 Rust 程式碼！把原本需要數天的工作壓縮到了幾小時。

當然，代價就是花費的 Tokens 可能會更多，不是什麼時候都建議使用 Agent Teams。

在實際操作中，Agent Teams 的多個智慧體通常需要物理隔離來避免程式碼衝突。目前最主流的做法是利用 Git WorkTree 給每個智慧體分配獨立的工作目錄，各自在獨立的分支上開發。

![](https://pic.yupi.icu/1/image-20260410145744619.png)

Cursor 已經內建了這種能力，透過 Parallel Agents 模式自動建立和管理 WorkTree，讓多個 AI 並行工作後一鍵合併程式碼。

![](https://pic.yupi.icu/1/image-20260410150251832.png)



### Hermes Agent

[Hermes Agent](https://github.com/NousResearch/hermes-agent) 是 Nous Research 在 2026 年 2 月開源的自改進 AI 智慧體，最大的特點是它能從自己完成的任務中學習，越用越聰明。

一般的 AI 智慧體每次對話都是從零開始，不會從過去的經驗中學習。而 Hermes Agent 內建了一套閉環學習機制：

1. 完成任務後，自動把解決方案提煉成可複用的 Skill Document（技能文件）
2. 下次遇到類似任務時，先檢索已有的技能文件
3. 根據新的實踐不斷最佳化已有技能

官方資料顯示，使用已積累技能的 Hermes Agent 完成類似任務的速度比全新例項快 40%。

Hermes Agent 採用三層記憶系統：會話記憶（當前對話上下文）、技能文件（從任務中提煉的可複用知識）、以及使用者畫像（持久化的使用者偏好和習慣）。它支援 Telegram、Slack、Discord、微信等多個平臺接入，相容 200 多種 AI 模型，完全免費開源。



### Background Agent

後臺 Agent（Background Agent）是讓 AI 在後臺自主執行、完成任務後再通知你結果的能力。

傳統的 AI 程式設計需要你盯著螢幕等 AI 一步步做完，電腦還不能關。而後臺 Agent 允許你把任務交給 AI 後，就去做別的事情，AI 會在雲端獨立完成工作，你甚至可以關掉電腦！

比如讓 AI 在後臺修復一批 Bug、跑一輪程式碼審查、或者完成一個完整的功能模組，做完了會通知你來驗收。

目前 Claude Code、Cursor 等工具都已經支援後臺 Agent 能力。以後 AI 程式設計可能就像發微信一樣，你在手機上把需求發過去，該幹嘛幹嘛，等 AI 做完了來找你驗收就行。

![](https://pic.yupi.icu/1/cursor%20agent%E5%90%8E%E5%8F%B0%E8%83%BD%E5%8A%9B_%E5%89%AF%E6%9C%AC.jpg)



### Agent Loop 智慧體迴圈

Agent Loop（智慧體迴圈）是 AI 智慧體的核心工作機制，簡單來說就是 AI 透過不斷重複 “感知-思考-行動-觀察” 的迴圈來一步步完成任務。

一個典型的 Agent Loop 包括：

1. 感知：獲取當前環境資訊（讀取檔案、檢視錯誤等）
2. 思考：分析情況，決定下一步行動
3. 行動：執行具體操作（寫程式碼、執行命令等）
4. 觀察：檢查行動的結果
5. 迴圈：根據結果決定是否繼續

這個迴圈會一直進行，直到任務完成或達到終止條件。

理解 Agent Loop 能幫你更好地規劃任務和管理 AI 的工作過程。需要特別注意的是，AI 程式設計時 Agent Loop 的迴圈次數不要太多，很多工具都有最大迴圈次數限制，迴圈太多不僅效果不好，還會瘋狂燒 Token！有朋友一覺醒來發現額度用光了，就是因為讓 AI 陷入了無限迴圈……

Claude Code 的原始碼就是 Agent Loop 最好的工程實現案例。它的核心對話迴圈其實就是一個樸素的 while(true) 無限迴圈：每一輪迭代裡，先做上下文壓縮、再呼叫大模型拿到響應，如果模型說 “我要用某個工具” 就去執行，把結果追加到對話歷史裡，然後進入下一輪。

![](https://pic.yupi.icu/1/image-20260401140913171.png)



### Ralph Wiggum Loop

Ralph Wiggum Loop 是 2026 年比較流行的一種 AI 程式設計模式，名字來源於《辛普森一家》中那個執著不放棄的角色 Ralph Wiggum。

這個模式目前已有多個開源實現，比如 [wiggumdev/ralph](https://github.com/wiggumdev/ralph)。它的核心思路很簡單：**把 AI 放在迴圈中反覆執行，直到需求文件中的所有檢查項全部完成。**

工作流程大概是這樣的：

1. 先寫一份 PRD（產品需求文件），把要做的功能拆解成一個個清晰的檢查項
2. 讓 AI 智慧體開始執行，每次從檢查清單中取出未完成的任務
3. AI 完成一個任務後，透過 Git 提交程式碼並記錄進度
4. 以全新的上下文開始新一輪迭代，繼續處理剩餘任務
5. 不斷迴圈，直到所有檢查項完成

這種模式的巧妙之處在於，每輪迴圈都以乾淨的上下文開始（透過 Git 和檔案來持久化進度），避免了長對話中 AI 容易 “斷片兒” 的問題。而且可以無人值守地執行，你寫好 PRD 就可以去睡覺了，第二天起來檢查成果就行。

不過要注意設定好迴圈次數限制和 Token 預算，防止 AI 陷入無限迴圈瘋狂燒錢。



### ReAct 推理與行動

ReAct（Reasoning and Acting）是一種讓 AI 智慧體交替進行推理和行動的技術正規化。它的核心思想很簡單：讓 AI 先想清楚再動手，動完手再看看效果，然後繼續想下一步怎麼做。

傳統的 AI 要麼只思考不行動，要麼只行動不思考。而 ReAct 讓 AI 能夠：

1. 先推理：思考當前情況，制定計劃
2. 再行動：執行具體操作
3. 觀察結果：看看行動效果如何
4. 繼續推理：根據結果調整策略

這種 “思考 - 行動 - 觀察” 的迴圈讓 AI 能更可靠地完成複雜任務，是現代 AI 程式設計工具的核心技術之一。

![](https://pic.yupi.icu/1/ReAct%E6%8E%A8%E7%90%86%E4%B8%8E%E8%A1%8C%E5%8A%A8%E5%A4%A7.jpeg)



### 深度思考

深度思考（Deep Thinking）是讓 AI 在回答之前先進行一段內部推理的能力，也叫 “擴充套件思考” 或 “思考模式”。

它和前面提到的思維鏈提示（CoT）有什麼區別呢？

思維鏈提示是一種提示詞技巧，透過提示詞引導 AI 展示推理過程；而深度思考是模型內建的能力，AI 會在內部自動進行深度推理，不需要你在提示詞中特別要求。

普通模式下，AI 收到問題後會直接生成回答。而開啟深度思考後，AI 會先在內部進行一系列推理步驟，比如分析問題、考慮多種方案、評估利弊，然後才輸出最終答案。你有時能在 AI 的回覆中看到一個 “思考中...” 的過程，那就是深度思考在工作。

![](https://pic.yupi.icu/1/image-20260215104649777.png)

深度思考特別適合複雜的程式設計任務，比如設計系統架構、排查難以定位的 Bug、最佳化演算法等。代價是速度更慢、Token 消耗更多。

目前主流 AI 模型和 AI 程式設計工具都支援深度思考，並且你可以選擇是否開啟思考模式。




### 自適應思考

自適應思考（Adaptive Thinking）是深度思考的智慧化版本，讓 AI 自動判斷當前問題需要多深的思考程度。

以前深度推理模式只能手動開關，開了的話簡單問題也慢吞吞地想半天、還浪費錢，關了的話複雜問題又容易出錯。

AI 有了自適應思考能力後，可以做到簡單問題秒回，複雜問題會自動進入深度思考模式。這樣既保證了質量，又節省了時間和成本。

![](https://pic.yupi.icu/1/%E8%87%AA%E9%80%82%E5%BA%94%E6%80%9D%E8%80%83%E6%BC%AB%E7%94%BB%E5%A4%A7.jpeg)

Anthropic 在 Claude Opus 4.6 中率先引入了自適應思考能力，並在 Opus 4.8 中進一步最佳化。開發者可以設定不同的思考力度級別來平衡質量和成本。




### 工具呼叫

工具呼叫（Tool Use / Function Calling）是讓 AI 能夠使用外部工具和功能的技術。

AI 本身只能生成文字，但透過工具呼叫，它可以讀寫檔案、搜尋網頁、執行命令和指令碼、呼叫 API、運算元據庫等等。

![](https://pic.yupi.icu/1/1746590338968-0240c12b-2956-47f4-b8ff-5b5f831221f6.png)

工具呼叫的工作流程分為 4 步：

1. 識別需求：AI 判斷當前任務需要使用工具
2. 選擇工具：從可用工具中選擇合適的
3. 執行呼叫：用正確的引數呼叫工具
4. 整合結果：將工具返回的結果融入回答，繼續完成任務

舉個例子，使用者想要獲取 [程式設計導航網站](https://www.codefather.cn) 的熱門文章，下面這張圖清晰地展示了工具呼叫的完整流程：

![](https://pic.yupi.icu/1/%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8%E6%B5%81%E7%A8%8B.png)

需要注意的是，AI 模型本身並不直接執行工具，而是生成 “我想呼叫這個工具，引數是這些” 的指令，由外部系統執行後把結果返回給 AI。

有了工具呼叫，AI 就從 “只會說” 變成了 “能動手”。如果沒有工具呼叫，AI 只能告訴你該怎麼改程式碼，你還得自己去複製貼上；而有了工具呼叫，AI 可以直接幫你讀取檔案、修改程式碼、執行命令，一條龍搞定。比如 Cursor 的 Agent 模式就是透過工具呼叫來實現自主程式設計的。



### MCP 模型上下文協議

MCP（Model Context Protocol）是 Anthropic 在 2024 年底推出的開放標準，用於讓 AI 模型安全地連線外部資料來源和工具。

你可以把 MCP 理解成 AI 世界的 “USB 介面”。就像 USB 介面讓各種裝置（鍵盤、滑鼠、U 盤）都能用同一種方式連線電腦一樣，MCP 讓各種外部工具（檔案管理、資料庫、搜尋引擎等）都能用同一種方式連線 AI，不用為每個工具單獨寫一套對接程式碼。

![](https://pic.yupi.icu/1/1746710765234-c974bda8-666e-45b3-adc4-ace97cbb8c0a.png)

MCP 的核心價值在於 **標準化**。開發者不需要為每個 AI 工具單獨開發聯結器，只需要按照 MCP 標準開發一次，就能被所有支援 MCP 的 AI 工具使用。目前 Claude Code、Cursor、Windsurf 等主流 AI 程式設計工具，以及各種網頁 AI Agent 應用都已經支援 MCP 協議。

![](https://pic.yupi.icu/1/1746677838632-9278e62b-c850-4d3c-a835-297ccbe2061a.png)

在 Vibe Coding 中，MCP 讓 AI 能夠連線更多外部工具和資料來源，大大擴充套件了 AI 的能力邊界。比如透過 Figma MCP，AI 可以直接讀取設計稿並生成對應的網頁程式碼；透過 GitHub MCP，AI 可以直接操作程式碼倉庫、建立 PR；透過資料庫 MCP，AI 可以查詢和分析業務資料。

![](https://pic.yupi.icu/1/image-20260116123701822.png)

💡 想要發現更多好用的 MCP 服務？可以訪問 [魚皮 AI 導航 - MCP 大全](https://ai.codefather.cn/mcp)，持續更新優質 MCP，幫你重塑 AI 工作流。



### Agent Skills 智慧體技能

Agent Skills（智慧體技能）是 Anthropic 在 2025 年 10 月推出的 [一套開放標準](https://platform.claude.com/docs/zh-CN/agents-and-tools/agent-skills/overview)，目的是讓 AI 能夠學習使用各種專業技能，快速擴充套件特定領域的專業能力。

簡單來說，Agent Skills 就是給 AI 準備的 **技能包**。技能包裡有精心設計的提示詞、程式碼指令碼、還有各種資原始檔。

![](https://pic.yupi.icu/1/1769306811193-2ee3acbc-5e36-46c2-8d08-b2682494fb56.png)

把 AI 想象成一個職場小白，給他裝上 `文件處理技能`，它就立刻知道怎麼生成 PPT、處理 Excel 表格；裝上 `程式碼規範技能`，它就知道怎麼按照公司標準寫程式碼。

![](https://pic.yupi.icu/1/1769306900359-2a2b73da-a366-411d-ad3b-2ae61f6b5bc4.png)

Skill 的本質是一個包含 `SKILL.md` 檔案的資料夾，裡面可以放置指令說明、指令碼程式碼、參考資料等。當 AI 遇到相關任務時，會自動載入對應的 Skill 來增強自己的能力。

![](https://pic.yupi.icu/1/agent%2520skills.jpeg)

Skills 的核心設計是 **漸進式披露**，AI 只在需要時才載入相關內容，不會一次性把所有資訊都塞進上下文，既節省 Token 又保持靈活性。

![](https://pic.yupi.icu/1/agent%20skills%20bundling.jpeg)

💡 想要發現更多好用的 Agent Skills？可以訪問 [魚皮 AI 導航 - Skills 大全](https://ai.codefather.cn/skills)，持續更新優質技能，讓 AI 幫你幹更多活。



### Hooks 鉤子

Hooks（鉤子）是 AI 程式設計工具中的一種自動化觸發器。當 AI 完成某個動作（比如生成程式碼、提交程式碼、執行命令）時，Hook 會自動執行你預設的指令碼或檢查流程。

各種主流 AI 程式設計工具都支援 Hooks，比如在 Claude Code 中，Hooks 可以用來：

- 程式碼生成後自動執行格式化工具
- 檔案修改後自動執行測試
- 許可權請求時自動判斷是否安全並批准
- 提交程式碼前自動檢查程式碼規範

![](https://pic.yupi.icu/1/image-20260215105006734.png)

Hooks 讓你的 AI 工作流更加自動化，減少手動操作。但是要注意，Hooks 配置不當可能會阻塞 AI 的正常工作流程，建議先在小範圍測試，確認沒問題再推廣到整個專案。



### 斜槓命令

斜槓命令（Slash Commands）是在 AI 程式設計工具的對話方塊中輸入 `/` 觸發的快捷指令，可以快速執行常用操作。

你可以把斜槓命令理解成操作 AI 的快捷鍵。Cursor、Claude Code 等主流 AI 程式設計工具都支援斜槓命令，比如 Claude Code 內建了這些常用的斜槓命令：

- `/help`：檢視可用命令
- `/compact`：壓縮當前對話的上下文
- `/config`：修改配置
- `/skills`：檢視已安裝的技能

![](https://pic.yupi.icu/1/image-20260215105146492.png)

你可以自定義斜槓命令，把常用的工作流封裝起來複用。比如建立一個 `/commit-push-pr` 命令，一次性完成程式碼提交、推送和建立 PR；或者搞個 `/techdebt` 命令，每次會話結束跑一下清理重複程式碼。

自定義命令的本質其實就是一個 Markdown 檔案，在 Cursor 中，只需要在專案的 `.cursor/commands/` 目錄下建立 `.md` 檔案，裡面寫上你想要 AI 執行的指令，這個檔名就會變成一個斜槓命令。還可以用 Git 版本控制工具來管理自定義命令的檔案，跨專案複用。

![](https://pic.yupi.icu/1/image-20260302171806320.png)



### A2A（Agent-to-Agent）

A2A（Agent-to-Agent）是指 AI 智慧體之間相互通訊和協作的協議或方式，是多智慧體系統的基礎技術。

就像人和人之間需要語言來溝通，AI 智慧體之間也需要標準化的方式來交換資訊、分配任務、彙報結果。

A2A 協議讓不同的 AI 智慧體能夠組成團隊，分工合作完成複雜任務。這個協議由 Google 在 2025 年推出，目前已有超過 150 家企業加入支援。

![](https://pic.yupi.icu/1/a2a-agent.png)

不要把 A2A 和 MCP 搞混！二者是互補關係，MCP 解決的是 AI 連線工具的問題，A2A 解決的是 AI 之間溝通協作的問題。



### ACP 協議

ACP 這個縮寫在 AI 領域其實有兩個含義，容易搞混，這裡一起說清楚。

**第一個是 Agent Communication Protocol 智慧體通訊協議**，由 IBM 研究院推出。它讓不同框架、不同公司開發的 AI 智慧體能夠無縫協作，就像不同品牌的手機都能互相打電話一樣。

它基於輕量級的 HTTP REST 介面設計，支援文字、程式碼、檔案、圖片等多種內容格式，不挑程式語言，上手很簡單。

![](https://pic.yupi.icu/1/%E6%99%BA%E8%83%BD%E4%BD%93ACP%E5%8D%8F%E8%AE%AE%E5%A4%A7.jpeg)

需要注意的是，ACP 和前面提到的 A2A 是兩個獨立的協議。它們都在解決智慧體跨框架交流的問題，但具體的通訊格式和能力發現機制還是兩套不同的體系。這些協議主要面向做 AI 應用開發的程式設計師，幫助他們構建多個智慧體協作的系統。

**第二個是 Agent Client Protocol 智慧體客戶端協議**，由 JetBrains 和 Zed 聯合推出，解決的是完全不同的問題 —— 讓任何 AI 程式設計智慧體都能在任何 IDE 中執行。

你可以把它理解成 AI 程式設計工具的 “萬能介面卡”。以前每個 AI 程式設計智慧體外掛都要為 IDEA 寫一套程式碼、為 VS Code 寫一套程式碼。現在有了 ACP 協議，Claude Code 只需要實現 ACP 介面，IDEA 就能直接把它接入進來，你在 IDEA 裡也能爽用 Claude Code、在 Zed 編輯器裡也能用 Gemini CLI，不再被某個 IDE 綁死。

此外，JetBrains 還上線了 ACP Agent Registry，一鍵就能安裝各種 AI 程式設計智慧體，越來越方便了~

![](https://pic.yupi.icu/1/image-20260328131101270.png)



### BMAD 敏捷 AI 開發方法

[BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)（Breakthrough Method of Agile AI-Driven Development，突破性敏捷 AI 驅動開發方法）是一套系統化的 AI 智慧體開發框架，目標是將原本混亂的 AI 程式設計過程變得結構化、可複用。

BMAD 使用 **角色化智慧體** 的方式組織開發流程，每個智慧體扮演特定角色：

- Analyst Agent 分析師：建立專案簡報，包含市場分析和使用者畫像
- PM Agent 產品經理：將簡報轉化為詳細的產品需求文件（PRD）
- Architect Agent 架構師：設計技術實現方案和系統架構

BMAD 中的智慧體分為兩種型別：

- Simple Agents 簡單智慧體：單檔案、自包含，適合程式碼審查、文件生成等聚焦任務
- Expert Agents 專家智慧體：具有跨會話持久記憶，配有專屬資料夾存放資源，適合複雜的多步驟工作流

每個智慧體都有標準化的組成部分，包括人設（角色、身份、溝通風格、原則）、能力列表、互動選單，以及可選的關鍵行動。

![](https://pic.yupi.icu/1/BMAD%E5%BC%80%E5%8F%91%E6%B5%81%E7%A8%8B%E5%A4%A7.jpeg)

BMAD 在 GitHub 上獲得了幾萬+ Star，說明這種結構化的 AI 開發方法正在被越來越多的開發者認可。

![](https://pic.yupi.icu/1/image-20260201143945594.png)




### Browser Use 瀏覽器使用

Browser Use（瀏覽器使用）是讓 AI 智慧體能夠自主操控網頁瀏覽器的技術能力。透過 Browser Use，AI 可以像人類一樣瀏覽網頁、點選按鈕、填寫表單、提取資料。

Browser Use 的典型應用場景：

- 自動化研究：讓 AI 在多個網站上搜尋、整理資訊
- 資料採集：從網頁中提取結構化資料
- 表單填寫：自動完成繁瑣的線上表單
- 跨平臺操作：在不同網站間完成多步驟任務

比較知名的開源專案是 [Browser-Use](https://github.com/browser-use/browser-use)，支援透過 Python 呼叫多種大模型來控制瀏覽器。此外，Cursor、Claude Code 等主流 AI 程式設計工具也內建了 Browser Use 能力，可以在開發過程中自動開啟瀏覽器預覽效果、執行測試等操作。

![](https://pic.yupi.icu/1/image-20251030220841383.png)

Browser Use 的一個關鍵優勢是，AI 可以利用你現有的瀏覽器會話和登入狀態，無需為每個網站單獨開發 API 整合。也就是說，AI 能夠訪問那些沒有公開 API 的網站，大大擴充套件了自動化的應用範圍。



### Computer Use 計算機使用

Computer Use（計算機使用）是 Anthropic 公司在 2024 年推出的 AI 能力，讓 Claude 大模型能夠像人類一樣操作整個計算機桌面。

和 Browser Use 只能操作瀏覽器不同，Computer Use 可以操作任何桌面應用程式，比如：

- 檢視螢幕截圖，理解介面元素
- 移動滑鼠游標，點選按鈕
- 使用鍵盤輸入文字
- 執行命令列操作

Computer Use 的工作原理是一個持續的反饋迴圈：

1. 截圖分析：AI 捕獲並分析當前螢幕
2. 決策規劃：根據任務目標確定下一步操作
3. 執行操作：傳送滑鼠/鍵盤輸入
4. 觀察結果：檢查操作效果，調整策略

💡 為了安全起見，Computer Use 一般需要在虛擬機器或容器中執行，不會直接控制你的真實電腦。

Computer Use 代表了 AI 從 “只能生成文字” 到 “能夠操作軟體” 的重大跨越，徹底改變人機互動方式。

基於 Computer Use 技術，Anthropic 在 2026 年推出了 [Claude Cowork](https://claude.com/product/cowork)，這是一個桌面端 AI 助手，可以直接訪問你電腦上的檔案和資料夾，幫你整理下載目錄、從截圖中提取資料到表格、準備品牌報告等日常辦公任務。

## 上下文管理


### 上下文（Context）

上下文是 AI 在回答問題時能夠參考的所有資訊，包括：

- 當前對話的歷史
- 你開啟的程式碼檔案
- 專案的結構和配置
- 你提供的參考資料

上下文越豐富、越和當前任務相關，AI 生成的程式碼就越符合你的需求。這就像給一個新同事交接工作，你給的背景資訊越多，他上手就越快。

在 Cursor 中，你可以透過對話方塊附近的 Token 用量指示器來大致瞭解當前上下文的大小；在 Claude Code 中，可以使用 `/context` 命令檢視上下文佔用情況。

![](https://pic.yupi.icu/1/image-20260302172312528.png)



### 上下文工程

上下文工程（Context Engineering）是有策略地管理和最佳化提供給 AI 的上下文資訊的技術。

核心目標是 **讓 AI 擁有恰到好處的資訊**。既不能太少（導致 AI 不瞭解情況），也不能太多（導致資訊過載、成本上升）。

好的上下文工程包括：

- 選擇最相關的檔案
- 提供必要的背景說明
- 使用規則檔案定義專案規範
- 適時清理無關的對話歷史

上下文工程是目前 AI 領域非常熱門的研究方向。2026 年的趨勢正在從簡單的上下文管理，演進到更復雜的 **記憶架構** —— 讓 AI 擁有短期記憶（當前對話上下文）、長期記憶（跨會話的知識積累）和外部記憶（向量資料庫、知識圖譜等）。

比如 Claude Opus 4.5 就引入了 [Memory Tool](https://console.anthropic.com/docs/en/agents-and-tools/tool-use/memory-tool)，能讓 AI 在超出上下文視窗的情況下，透過檔案系統式的持久化儲存來記住重要資訊。根據 Anthropic 官方資料，這項技術在長時間工作流中減少了 84% 的 Token 消耗！

可以說，誰能更好地解決上下文和記憶的問題，誰就能在 AI 程式設計領域佔據優勢。

Claude Code 的三層記憶架構是上下文工程的典型實踐：
- 第一層是 MEMORY.md（熱資料），就像一本書的目錄，每次對話都會載入，但嚴格限制在 200 行、25KB 以內
- 第二層是話題檔案（溫資料），存著你的編碼偏好、專案約定等，新對話開始時 AI 只挑選最相關的 5 個檔案載入
- 第三層是歷史對話（冷資料），存成檔案，需要時用 Grep 搜尋。不同溫度的資料用不同方式管理 —— 熱的常駐、溫的按需、冷的搜尋。

![](https://pic.yupi.icu/1/image-20260401141550843.png)

一個有意思的設計是，Claude Code 的記憶不記程式碼，只記人的偏好和判斷。因為程式碼會變化但記憶不會自動更新，如果記憶裡說 “函式 X 在第 30 行”，你重構後這條記憶就變成了誤導。程式碼的事實永遠去原始碼裡實時讀取，這種設計從根源上消滅了快取和資料不一致的可能性。



### 上下文壓縮

上下文壓縮（Context Compaction）是 AI 自動壓縮和總結之前對話內容的技術，解決的是長時間執行任務中上下文溢位的問題。

以前跑長任務的時候，AI 經常會撞到上下文長度的天花板，前面聊過的內容被擠掉後 AI 就失憶了，導致生成的程式碼和之前的約定對不上。有了上下文壓縮，AI 會在上下文快要滿的時候，自動把前面的對話總結成更精簡的形式，保留關鍵資訊的同時釋放空間，這樣就能持續工作更久而不會失憶。

你可以把它想象成專案經理寫會議紀要。已經開了 3 小時的會，不可能把每句話都記下來，但關鍵決策、待辦事項、重要結論都會被記錄。AI 的上下文壓縮也是類似的思路，把冗長的對話歷史濃縮成關鍵資訊。

![](https://pic.yupi.icu/1/%25E4%25B8%258A%25E4%25B8%258B%25E6%2596%2587%25E5%258E%258B%25E7%25BC%25A9%25E6%25BC%25AB%25E7%2594%25BB%25E5%25A4%25A7.jpeg)

Claude Opus 4.8 已經內建了上下文壓縮能力，搭配它的 100 萬 token 上下文視窗，可以讓長時間執行的程式設計任務更加穩定。

Claude Code 在原始碼中實現了一套精妙的五級壓縮策略，像漏斗一樣層層過濾：

1. Snip 剪裁：最輕的一刀，把舊的工具呼叫結果只保留結構，不保留內容
2. Microcompact 微壓縮：把體積大的工具執行結果解除安裝到快取裡。注意是解除安裝到快取而不是直接丟掉，因為子智慧體後續可能還需要這些結果
3. Context Collapse 摺疊：對中間的對話做摺疊摘要，只保留關鍵資訊
4. Autocompact 自動壓縮：當上下文佔用超過閾值時，觸發全量摘要壓縮
5. Reactive Compact 應急壓縮：最後的兜底，當 API 返回 413 “提示詞太長” 錯誤時緊急觸發

這五級從輕到重依次觸發，能裁的先裁，實在不夠了再上更重的方案。

![](https://pic.yupi.icu/1/image-20260401142212163.png)




### 規則檔案

規則檔案（Rules File）是放在專案中的配置檔案，用來告訴 AI 你的專案規範、技術棧、程式碼風格等資訊。有了規則檔案，AI 每次生成程式碼時都可以參考這些規則，生成的程式碼更符合你的專案風格，省去了反覆強調的麻煩。


不同 AI 程式設計工具使用不同的規則檔案格式：

- Cursor：早期使用 `.cursorrules` 單檔案格式，現在推薦使用 `.cursor/rules/*.mdc` 多檔案格式
- Claude Code：使用 `CLAUDE.md` 檔案
- GitHub Copilot：使用 `.github/copilot-instructions.md` 檔案

以 Cursor 為例，`.mdc` 規則檔案支援 YAML 後設資料（frontmatter），可以指定規則的適用範圍。根據 Cursor 官方文件，其格式如下：

```yaml
---
description: React 元件開發規範
globs: src/components/**/*.tsx
alwaysApply: false
---
# React 規範
- 使用函式式元件
- 優先使用 hooks
```

規則檔案的啟用方式有多種，比如：

- 始終生效：設定 `alwaysApply: true`
- 模式匹配：當引用匹配 `globs` 的檔案時自動啟用
- 手動呼叫：在對話中用 `@規則名` 引用
- AI 自主決定：AI 根據任務相關性自動載入


💡 注意，隨著工具版本的更新，這些檔案的名稱和標準可能會發生改變，一切以工具官方文件為主。



### AGENTS.md

[AGENTS.md](https://agents.md/) 是一種開放的檔案格式，專門用於給 AI 程式設計智慧體提供專案指令。它本質上也是一種規則檔案，只不過是跨工具通用的開放標準。

![](https://pic.yupi.icu/1/image-20260201145003244.png)

傳統的 README.md 是寫給人看的，主要介紹專案是什麼、怎麼用。而 AGENTS.md 是寫給 AI 看的，包含 AI 工作時需要的技術細節：

- 專案的構建和啟動命令
- 測試執行方式
- 程式碼風格和規範
- 專案結構說明

一個典型的 AGENTS.md 檔案大概長這樣：

```markdown
# 專案設定
- 安裝依賴：npm install
- 啟動開發：npm run dev
- 執行測試：npm test

# 程式碼規範
- 使用 TypeScript 嚴格模式
- 元件檔案使用 PascalCase 命名
- 工具函式使用 camelCase 命名
```

AGENTS.md 的優勢在於它是一個開放標準，被數萬個開源專案採用。當你使用支援該標準的 AI 程式設計工具（比如 Claude Code、Codex、Cursor、GitHub Copilot 等）時，AI 會自動識別專案根目錄下的 AGENTS.md 檔案，並將其中的指令傳送給 AI，不需要你手動引用。



### SDD 規範驅動開發

SDD（Spec-Driven Development，規範驅動開發）是 AI 時代的一種新型開發方法論，強調在編碼之前先建立明確的、AI 能直接理解和執行的規範文件。

傳統開發流程是：想到什麼寫什麼，邊寫邊改，最後再補文件。這樣容易導致需求不清晰、程式碼和文件對不上。

而 SDD 的思路正好相反：**先把需求寫成規範文件，並且把規範文件當作程式碼的唯一真相來源**。

你可以把規範文件理解為 “專案憲法”，它包含了詳細的需求描述、系統設計和介面定義。AI 必須嚴格遵守這些條文來生成程式碼，確保產出完全符合預期。

![](https://pic.yupi.icu/1/%25E6%25BC%25AB%25E7%2594%25BB%25E5%259B%25BE4%25E5%25A4%25A7.jpeg)

為什麼 SDD 越來越受重視？

因為 AI 生成程式碼的質量直接取決於上下文的清晰度，而不僅僅是依靠提示詞技巧。一個清晰的規範文件能比任何 Prompt 黑魔法更有效地減少錯誤。

SDD 的典型工作流程如下：

1. Constitution 制定準則：定義專案的基本原則、程式碼規範、效能標準
2. Specify 編寫規範：描述要做什麼功能、為什麼做、使用者需求是什麼
3. Clarify 澄清疑問：讓 AI 提出結構化問題，明確邊界情況和錯誤處理
4. Plan 制定方案：確定技術棧、系統架構、資料模型、API 介面
5. Tasks 拆解任務：把計劃拆解成可執行的任務列表，標註依賴關係和優先順序
6. Implement 執行實現：AI 按照任務列表生成程式碼，人類驗證

其實這和程式設計師在企業中開發專案的標準流程非常相似，只不過執行者從人變成了 AI。

![](https://pic.yupi.icu/1/%2525E6%2525BC%2525AB%2525E7%252594%2525BB%2525E5%25259B%2525BE5%2525E5%2525A4%2525A7.jpeg)

2025 年 9 月，GitHub 釋出了開源的 [Spec Kit](https://github.com/github/spec-kit) 工具包，幫助開發者在 AI 程式設計中實踐 SDD 方法論。它支援 Claude Code、GitHub Copilot 等主流程式設計工具，透過一套斜槓命令引導你完成上述流程。即使你不是軟體開發專家，也能在 AI 的引導下輕鬆地走完規範的專案開發流程。

![](https://pic.yupi.icu/1/image-20260116164612533.png)



### RAG 檢索增強生成

RAG（Retrieval-Augmented Generation 檢索增強生成）是一種讓 AI 能夠先檢索外部知識庫、再基於檢索結果生成回答的技術，目標是讓 AI 的回答更準確、更有依據。

普通的 AI 只能依賴訓練時學到的知識，而這些知識可能已經過時了。RAG 能讓 AI 在回答問題時，先從你的文件、程式碼庫、知識庫中檢索相關資訊，然後基於這些資訊生成回答。

![](https://pic.yupi.icu/1/1776650476421-3bfb3c26-575d-4cc4-9538-f74a4589b42d-20260430230436685.png)

這對於企業中的 Vibe Coding 特別有用，因為 AI 可以參考你專案中的已有程式碼，生成風格一致的新程式碼。

RAG 檢索增強生成的工作流程如下圖所示，做 AI 應用開發的程式設計師朋友們可以深入瞭解一下：

![](https://pic.yupi.icu/1/1745810809620-15c36bc0-5130-47fc-aaca-7d2a6ce6e3ce.png)

在實際工程中，RAG 已經演化出了很多進階方案。

![](https://pic.yupi.icu/1/1776651602499-afc9fc4b-6105-4b96-a3cd-a6681bf69480-20260430230542027.png)

比如：

- Multi-Query RAG，用多種問法分別檢索再合併結果。
- HyDE，讓 AI 先生成一段假答案再用假答案的向量去檢索。
- Hybrid Search，混合向量搜尋和關鍵詞搜尋再融合排序。
- Reranking，在檢索後用精排模型重新打分過濾噪聲。
- GraphRAG，把文件變成知識圖譜來支援跨文件多跳推理。
- Agentic RAG，給 Agent 配備一組檢索工具，讓它來自動排程，根據問題自主決定每一步該怎麼做。

還有很多，不同的方案適用於不同場景，可以根據實際需求組合使用。

![](https://pic.yupi.icu/1/1776652755436-d1f52895-b98a-4e33-8c86-6ce0322ace05-20260430230713947.png)

對 RAG 感興趣的程式設計師朋友，可以閱讀本教程程式設計學習板塊的《AI 程式設計技術入門指南》，裡面有更詳細的 RAG 實現方案和選型建議。



### Agentic RAG 智慧體檢索增強生成

Agentic RAG（智慧體檢索增強生成）是傳統 RAG 的進化版，它把固定的 “檢索 → 生成” 流水線升級成了一個由 AI 智慧體控制的閉環系統。

傳統 RAG 就像一個只會按流程辦事的圖書管理員：你問一個問題，它去書架上找一次資料，拿回來就給你答案，不管找的對不對。

而 Agentic RAG 更像一個資深的研究員：它會先思考應該從哪裡找資訊，找到後會判斷資訊是否相關，如果不夠好就換個角度重新搜尋，甚至同時查多個資料來源，反覆驗證直到滿意為止。

![](https://pic.yupi.icu/1/1776652755436-d1f52895-b98a-4e33-8c86-6ce0322ace05.png)

Agentic RAG 的核心能力包括：

- 多輪檢索：根據需要進行多次有針對性的檢索，而不是隻查一次
- 動態查詢改寫：如果第一次沒找到好結果，AI 會自動換個提法重新搜尋
- 多資料來源協作：同時從向量資料庫、API、網頁、SQL 資料庫等多個來源獲取資訊
- 自我糾錯：評估檢索結果的質量，不滿意就重來

典型模式包括 CRAG（糾正式 RAG，新增檢索評估器）、Self-RAG（自反思 RAG，在生成過程中嵌入反思步驟）和 Adaptive RAG（自適應 RAG，根據問題型別選擇不同檢索策略）。

代價是更高的延遲和數倍的 Token 成本，所以更適合複雜的、高準確率要求的場景，比如法律、醫療、合規類的問題。簡單的單源查詢用傳統 RAG 就夠了。



### 向量資料庫

向量資料庫是專門用來儲存和查詢 “向量”（一種數字表示形式）的資料庫。在 AI 領域，它常用來儲存文字的語義表示。

什麼是向量呢？

簡單來說，向量就是一串數字組成的陣列，比如 `[0.1, 0.5, 0.3, 0.8]`。每個數字代表一個特徵維度。AI 可以把一段文字、一張圖片、一段程式碼轉換成這樣的向量，語義相似的內容轉出來的向量也會很接近。

當你把程式碼或文件存入向量資料庫後，AI 就能快速找到語義相似的內容，即使搜尋詞和原文不完全一樣。

![](https://pic.yupi.icu/1/1769047066536-0ef08cd3-b86b-4c97-9016-7add32a710b8.png)

比如，你搜 “使用者登入”，它能找到叫 "handleAuth" 的函式，因為它們在語義上是相關的。

隨著 AI 的爆發，市面上湧現了非常多支援向量儲存的資料庫：

![](https://pic.yupi.icu/1/1745813546910-9b39355a-85ab-4673-b52b-7f11349a55d7.jpeg)




### 嵌入 Embedding

嵌入是把文字、程式碼等內容轉換成數字向量的過程。這些向量能夠捕捉內容的語義資訊。

在向量空間中，語義相似的內容會靠得更近。這就是為什麼向量資料庫能進行語義搜尋的原理。

![](https://pic.yupi.icu/1/1745812543781-8ef377d0-2dac-4d17-a504-35de13fbaad0.png)

你不需要深入理解嵌入的技術細節，只需要知道它是 RAG 和程式碼語義搜尋的基礎技術就好。




## AI 輸出相關


### AI 幻覺

AI 幻覺（Hallucination）是指 AI 輸出了不符合事實的內容，可能是編造了不存在的 API、給出了錯誤的函式用法、推薦了根本不存在的庫，甚至胡編亂造一些看起來很合理但完全錯誤的資訊。

比如下面這段對話，我讓 AI 介紹一下程式設計師魚皮，結果它一本正經地胡說八道，我的本名可不是這個……

![](https://pic.yupi.icu/1/image-20260104184328898.png)

這是大語言模型的固有問題，因為它們是基於機率生成內容的，有時會 “腦補” 不存在的東西。

在 AI 程式設計時，我們可以透過以下方法儘量減少幻覺帶來的影響：

- 要求 AI 提供文件連結驗證
- 自己查官方文件確認
- 換個模型試試
- 開新對話重新描述問題
- 利用 Context7 等獲取到最新技術文件的 MCP 擴充套件

對於做 AI 應用開發的程式設計師來說，如何消除幻覺是一個需要重點攻克的挑戰。前面提到的 RAG（檢索增強生成）技術就是目前最主流的解決方案之一，透過讓 AI 先檢索真實資料再回答，大幅降低幻覺的機率。




### 溫度

溫度（Temperature）是控制 AI 輸出隨機性的引數，取值一般在 0 ~ 2 之間（不同大模型和 AI 程式設計工具的設定範圍可能會有區別）。

- 溫度低（如 0.1）：輸出更確定、更保守，適合寫程式碼
- 溫度高（如 1.0）：輸出更隨機、更有創意，適合頭腦風暴

在程式設計場景中，一般使用較低的溫度，讓 AI 生成更穩定、更可預測的程式碼。而在需要 AI 發揮創意的場景（比如起名字、寫文案、頭腦風暴產品方案），可以適當調高溫度，讓 AI 給出更多樣化的建議。

比如下圖，我把溫度調高，輸出的結構可能完全不同：

![](https://pic.yupi.icu/1/image-20260302173616073.png)



### 流式輸出

流式輸出（Streaming）是指 AI 一邊生成內容，一邊實時顯示給使用者，而不是等全部生成完再顯示。

這就像看直播而不是看錄播，你能實時看到 AI 的輸出過程和生成的內容，如果發現方向不對，可以及時中斷，避免浪費 Token。

大多數 AI 程式設計工具都支援流式輸出，讓互動體驗更流暢。

在技術實現上，流式輸出一般基於 SSE（Server-Sent Events，伺服器推送事件）技術，服務端透過持續推送資料片段給客戶端，做到實時展示。

## 開發工具概念


### IDE 整合開發環境

IDE（Integrated Development Environment 整合開發環境）是程式設計師用來寫程式碼的綜合軟體，一般包含程式碼編輯器、偵錯程式、終端、外掛擴充套件市場等。

VS Code 是目前最流行的輕量級 IDE，由微軟開發並開源。Cursor 和 Windsurf 都是基於 VS Code 開發的 AI 程式碼編輯器，繼承了 VS Code 的介面風格和功能，同時大幅擴充套件了 AI 能力。

![](https://pic.yupi.icu/1/image-20260112113710320.png)




### 程式碼編輯器

程式碼編輯器是用來編寫和修改程式碼的工具，提供語法高亮、程式碼補全、錯誤提示等功能，幫助你更高效地寫程式碼。

常見的程式碼編輯器有 Sublime Text、Vim 等。區別於 IDE 整合開發環境，它們相對輕量、啟動快速，適合快速編輯單個檔案；而 IDE 的功能更全面，整合了偵錯程式、終端、版本控制等工具，適合專業開發者和大型專案開發。

![](https://pic.yupi.icu/1/image-20260302174013740.png)

在 Vibe Coding 時代，程式碼編輯器整合了 AI 能力，可以根據你的提示詞自動生成程式碼、解釋程式碼、修復錯誤。比如早期的 Cursor 雖然功能強大，但它的核心還是一個 AI 增強的程式碼編輯器。



### CLI 命令列介面

CLI（Command Line Interface）全稱命令列介面，就是你在一個小黑框裡敲文字命令來操作電腦。和它對應的是 GUI（Graphical User Interface 圖形介面），也就是我們日常看到的圖示、按鈕和視窗。

![](https://pic.yupi.icu/1/image-20260407150349886.png)

在 AI 時代，CLI 正在迎來一波復興，它不再只是程式設計師的專屬技能，而是 AI 與工具互動的天然介面。

為什麼 CLI 會突然火起來呢？

因為 AI 大模型從誕生那天起，就在學習海量的程式碼和命令列操作，讓它讀一行命令、執行一個操作，跟喝水一樣自然。反過來，讓 AI 去操作圖形介面就難多了，要截圖分析、找元素、模擬點選，整個過程又慢又容易出錯。有人測試過，AI 透過瀏覽器完成任務的成功率只有 35.8%，換成 CLI 就接近 100%。

![](https://pic.yupi.icu/1/image-20260407123223554.png)

所以現在大廠們紛紛開源自己產品的 CLI 工具（Google、飛書、釘釘、企業微信等），本質上就是在給 AI 提供操作自己產品的介面。

以前做產品只考慮人類使用者怎麼用，現在還得想想 AI 怎麼用。所以未來的產品可能會有兩套前端：一套給人類看的 GUI，一套給 AI 用的 CLI。

想深入瞭解 CLI 工具的使用和開發，可以閱讀本教程程式設計工具板塊的《AI 命令列程式設計工具》。



### 零程式碼平臺

零程式碼平臺（No-Code Platform）是不需要寫程式碼就能建立應用的平臺。與之相近的還有低程式碼平臺（Low-Code Platform），它允許透過少量程式碼加上視覺化拖拽來構建應用，自由度更高一些。

在 AI 時代，像 Bolt.new、Lovable、v0.dev、百度秒噠這樣的平臺結合了零程式碼和 AI，你可以用自然語言描述需求，平臺自動生成完整可線上訪問的應用。

零程式碼平臺特別適合完全沒有程式設計經驗的新手，或者想快速做原型的場景。不過缺點也很明顯，出了問題不好除錯，也很難深度定製，專案做大了容易遇到瓶頸。

![](https://pic.yupi.icu/1/image-20260104141512389.png)




### 程式碼補全

程式碼補全（Code Completion）是指 AI 根據你當前的程式碼上下文，自動預測你接下來要寫的內容並提供建議。

當你寫程式碼時，AI 會根據上下文推測你的意圖，提供程式碼片段供你選擇。按下 Tab 鍵就能接受建議，大大提高編碼速度。

![](https://pic.yupi.icu/1/image-20260302174238835.png)

早在 2021 年，GitHub 就推出了 Copilot，開創了 AI 程式碼補全的先河。但誰也沒想到，短短几年後 AI 已經從 “補全幾行程式碼” 進化到了 “自主開發整個專案”。如今各大 AI 程式設計工具都支援程式碼補全，但越來越多的開發者已經不滿足於逐行補全了，而是直接用 Agent 模式讓 AI 一口氣寫完整個功能。



### 程式碼審查

程式碼審查（Code Review）是檢查程式碼質量、發現問題、提出改進建議的過程。

沒有程式碼審查的專案，Bug 往往要等到上線之後才被發現，修復成本很高。而有了程式碼審查，很多問題在程式碼合併之前就能被提前發現和修復。

在傳統開發中，程式碼審查一般由同事或上級來做。在 Vibe Coding 中，你可以讓 AI 幫你審查程式碼，它會指出潛在的 bug、安全問題、效能問題，並提供修改建議。

![](https://pic.yupi.icu/1/image-20260112114023226.png)

但要注意，AI 的審查不能完全替代人工審查！特別是對於重要的生產程式碼。




### Linter 程式碼檢查器

Linter 是自動檢查程式碼問題的工具，能發現語法錯誤、風格問題、潛在 bug 等。

常見的 Linter 有前端的 ESLint、Python 的 Pylint、Go 的 golint 等，它們像一個嚴格的語法老師，幫你保持程式碼規範。

在 Vibe Coding 中，Linter 能幫你快速發現 AI 生成程式碼中的問題。而且很多時候，AI 在幫你建立前端專案時會自動整合 ESLint 等 Linter 工具，省去了你手動配置的麻煩。

![](https://pic.yupi.icu/1/image-20260116131356553.png)




### Debug 除錯

除錯（Debug）是找到並修復程式碼中錯誤的過程。當程式碼執行結果不符合預期時，你需要除錯來定位問題。

除錯的常用方法包括：

- 設定斷點，逐步執行程式碼
- 檢視變數的值
- 閱讀錯誤資訊和堆疊跟蹤
- 新增日誌輸出

![](https://pic.yupi.icu/1/image-20251027214825243.png)

在 AI 程式設計時，你可以直接把錯誤資訊發給 AI，讓它幫你分析原因並提供修復方案，甚至是自主修復。



### OpenClaw 開源 AI 助手

[OpenClaw](https://github.com/openclaw/openclaw) 是 2026 年最現象級的開源 AI 專案，僅用 100 多天就登頂 GitHub 星標歷史第一，斬獲 30 萬+ Star。

你可以把它理解為一個能操控你電腦的 AI 數字員工。它不只是一個聊天機器人，而是真的能幫你開啟軟體、操作瀏覽器、處理檔案、執行程式碼的全能助手。更關鍵的是，你可以透過手機聊天軟體（比如飛書、QQ、微信）隨時隨地給它下達任務，AI 會在你的電腦上自動完成。

![](https://pic.yupi.icu/1/1773231001520-f08121d8-de2c-4586-9af2-42cb0c728961-20260311204057246.png)

OpenClaw 的特點包括：

- 真正執行任務：能操作瀏覽器、處理檔案、寫程式碼、管理日程等
- 多渠道接入：支援微信、QQ、飛書、Telegram、Discord 等
- 技能生態系統：透過安裝不同的技能包擴充套件 AI 能力
- 多模型支援：支援 Anthropic、OpenAI、國產大模型等
- 完全開源：MIT 許可證，支援本地部署，資料掌握在自己手裡

不過 OpenClaw 的許可權很大，使用時一定要注意安全。想深入瞭解 OpenClaw 的安裝、使用和注意事項，可以閱讀本教程程式設計工具板塊的《OpenClaw 保姆級安裝教程》，或者魚皮 AI 知識庫的《完整 OpenClaw 保姆級教程》。



## 專案管理概念


### MVP 最小可行產品

MVP（Minimum Viable Product 最小可行產品）是指用最少的功能滿足核心需求的產品版本，簡單來說就是一個 “能跑起來、核心功能能用” 的最簡版本。

很多同學剛開始做產品的時候會有各種奇思妙想，恨不得一口氣把所有功能都做出來，結果花了大量時間在不必要的功能上，越做越複雜，最後覺得太難就直接放棄了，屬於是自己把自己嚇跑了。而做 MVP 的思路正好相反，先用最少的功能把核心價值跑通，快速驗證想法是否可行，拿到使用者反饋後再逐步迭代。

比如做一個記賬 APP，MVP 版本可能只有記錄支出、檢視列表兩個功能，其他高階功能以後再加。



### 迭代開發

迭代開發是把大專案分成多個小週期，每個週期完成一部分功能的開發方法。

每個迭代週期包括：計劃 => 開發 => 測試 => 釋出 => 反饋 => 改進。

這種方法特別適合 Vibe Coding，因為你可以讓 AI 先實現核心功能，測試沒問題後再逐步新增新功能。

順便提一下，迭代開發是敏捷開發（Agile Development）方法論的核心實踐之一。敏捷開發強調小步快跑、快速反饋、擁抱變化，非常適合 AI 程式設計的工作節奏。

![](https://pic.yupi.icu/1/%E8%BF%AD%E4%BB%A3%E5%BC%80%E5%8F%91%E5%A4%A7.jpeg)



### 重構

重構（Refactoring）是在不改變功能的前提下，改進程式碼結構和質量的過程。

重構的目的是讓程式碼更清晰、更易維護、更高效。常見的重構包括：

- 提取重複程式碼為函式
- 改進變數和函式命名
- 簡化複雜的邏輯
- 拆分過長的檔案

在 Vibe Coding 中，你可以讓 AI 幫你重構程式碼，但要小步進行，每次重構後都要測試。

注意，如果你只是用 AI 快速做個小工具，程式碼能跑就行，沒必要花時間重構。但如果是長期維護的企業級專案，程式碼質量直接決定了後續迭代的效率和穩定性，定期重構就非常有必要了。



### 技術債

技術債（Technical Debt）是為了快速完成功能而採用的臨時方案，這些方案在未來需要花時間修復和改進。

就像信用卡欠款一樣，雖然現在透支方便，但遲早要還，還要加利息。

在 Vibe Coding 中，AI 生成的程式碼可能不是最優方案，積累太多技術債會讓專案越來越難維護。定期重構是償還技術債的有效方法，防止出現屎山程式碼。

![](https://pic.yupi.icu/1/v2-806707f0f72072f1db481c237fc035ea_1440w-20260112114757928.png)



### 版本控制

版本控制是記錄程式碼變更歷史的系統，讓你能追蹤每次修改、對比不同版本、回退到之前的狀態。

Git 是最流行的版本控制工具，注意別把它和 GitHub 搞混了，Git 是在你電腦上執行的工具，GitHub 是線上的程式碼託管平臺，用來存放和分享你用 Git 管理的程式碼。

在 Vibe Coding 中，版本控制特別重要。因為 AI 可能會生成有問題的程式碼，有了版本控制，你隨時可以回退到之前正常的版本。

![](https://pic.yupi.icu/1/image-20260112114940228.png)



### Git WorkTree 工作樹

Git WorkTree（工作樹）是 Git 的一個隱藏技能，它可以讓一個倉庫同時擁有多個獨立的工作目錄，每個目錄對應不同的分支。

正常情況下，一個 Git 倉庫只有一個工作目錄，你同一時間只能在一個分支上幹活。想切換分支，就得先儲存手頭的程式碼，來回折騰。但用了 WorkTree，你可以開啟分身術，同時在不同的分支上幹活，互不干擾。

![](https://pic.yupi.icu/1/image-20260410143507942.png)

和手動複製專案資料夾的區別在於：手動複製會複製完整的 .git 目錄和歷史記錄，佔用空間大而且合併程式碼很麻煩。而 WorkTree 建立的工作目錄只是連結到同一個 .git 目錄，共享同一套提交歷史，省空間、合併也方便。

![](https://pic.yupi.icu/1/image-20260410143527245.png)

在 AI 程式設計時代，WorkTree 最香的用法就是讓多個 AI 並行開發。比如你有首頁、搜尋、個人中心三個功能要做，就建立三個工作樹，每個分配給一個 AI，各幹各的互不打擾，開發完再用 Git 合併程式碼。

![三個 AI 同時幹活](https://pic.yupi.icu/1/vscode%E4%B8%89%E4%B8%AA%E5%90%8C%E6%97%B6%E5%B9%B2%E6%B4%BB.png)

像 Cursor 這樣的 AI 程式設計工具已經內建了 WorkTree 支援，可以直接開啟 Parallel Agents 模式，自動建立和管理工作樹。

不過要注意，分配任務時要儘量讓不同的 AI 改不同的檔案，如果兩個 AI 改了同一個檔案，合併時就會產生衝突，需要手動解決。



### 部署

部署（Deployment）是指把開發好的應用釋出到伺服器上，讓使用者能夠訪問並使用。

最原始的部署方式是自己登入伺服器，把程式碼檔案打包上傳後手動執行，又麻煩又容易出錯。好在現在有很多自動化的部署平臺，傻瓜式操作，點幾下就能部署專案，常用的有：

- Vercel：適合前端和全棧應用
- Netlify：適合靜態網站和前端應用
- Railway、Render：適合後端服務

![](https://pic.yupi.icu/1/image-20260302175217005.png)

很多零程式碼平臺（如 Bolt.new）都支援一鍵部署，點個按鈕就能上線。

此外，還可以利用 MCP 來實現更智慧的部署。比如透過 EdgeOne Pages MCP，你只需要跟 AI 對話，AI 就能幫你自動完成網站的打包和部署，連部署平臺都不用自己登入~

![](https://pic.yupi.icu/1/1752212029384-16cfba8f-babb-49c0-9d41-3b76ee78eecf.png)



### GEO 生成式引擎最佳化

GEO 全稱為 Generative Engine Optimization 生成式引擎最佳化，你可以把它理解為 AI 時代的 SEO。

傳統的 SEO 關注的是 “怎麼讓網頁在百度、Google 搜尋結果中排名靠前”，而 GEO 關注的是 “怎麼讓你的內容被 ChatGPT、DeepSeek、豆包這些 AI 大模型引用和推薦”。

![](https://pic.yupi.icu/1/image-20260327155157265-20260328131543764.png)

打個比方，SEO 像是在超市貨架上搶黃金位置，GEO 像是讓導購員在顧客詢問時主動把你的產品推薦出去。

![](https://pic.yupi.icu/1/image-20260327163145093.png)

隨著越來越多人用 AI 搜尋代替傳統搜尋引擎，GEO 正在變得越來越重要。有資料顯示，AI 搜尋帶來的流量轉化率可以達到傳統搜尋的 5 倍以上！

GEO 的核心策略包括：

- 先給結論：文章開頭直接回答核心問題，AI 更喜歡提取開頭就給答案的內容
- 結構化寫作：使用清晰的標題層級、問答格式、對比表格，方便 AI 解析和引用
- 打造權威內容：用具體資料、權威引用代替模糊描述，AI 更信任有據可查的內容
- 在權威平臺多發內容：知乎、公眾號、GitHub 等高權重平臺釋出的內容更容易被 AI 抓取
- 技術最佳化：確保 robots.txt 允許 AI 爬蟲訪問，使用 SSR / SSG 確保頁面可爬取

需要注意，GEO 技術本身是中立的，和 SEO 一樣只是內容最佳化手段。而且做好 SEO 也有利於 GEO，兩者並不衝突。

對於想讓自己的產品被更多人發現的開發者來說，SEO 和 GEO 都是值得學習的推廣技能。可以閱讀本教程產品變現板塊的《SEO 搜尋引擎最佳化實戰》和《GEO 生成式引擎最佳化實戰》來深入瞭解。



## 前後端概念


### 前端

前端（Frontend）是使用者能直接看到和互動的部分，包括網頁介面、按鈕、表單、動畫等。說得粗暴一點，你在瀏覽器裡看到的一切，都是前端！

前端技術棧通常包括：

- HTML：頁面結構
- CSS：樣式和佈局
- JavaScript：互動邏輯
- React/Vue/Next.js：現代前端框架

在 Vibe Coding 中，前端是 AI 最擅長生成的部分，因為效果可以直接看到，方便驗證和調整。你還可以利用 Agent Skills 和精心編寫的提示詞來美化 AI 生成的前端頁面，去掉那股子 AI 味兒。具體技巧可以看魚皮的影片：[如何去除網站的 AI 味兒](https://www.bilibili.com/video/BV1QF6EBiErM/)




### 後端

後端（Backend）是使用者看不到的部分，負責處理業務邏輯、資料儲存、使用者認證等。

比如你在電商網站上點選 “下單” 按鈕，前端把你的訂單資訊發給後端，後端負責校驗庫存、計算價格、扣款、生成訂單，然後把結果返回給前端展示。

後端技術棧通常包括：

- Node.js/Python/Java：程式語言
- Express/FastAPI/Spring：Web 框架
- MySQL/PostgreSQL/MongoDB：資料庫

後端比前端更復雜，需要考慮安全性、效能、資料一致性等問題。因此 AI 生成的後端程式碼需要更仔細地審查。

![](https://pic.yupi.icu/1/%E5%89%8D%E7%AB%AF%E5%92%8C%E5%90%8E%E7%AB%AF%E4%BA%A4%E4%BA%92%E5%A4%A7.jpeg)




### 全棧

全棧（Full-stack）是指同時包含前端和後端的完整應用。全棧開發者是能同時處理前端和後端工作的程式設計師。

在 Vibe Coding 中，像 Cursor、Bolt.new 這樣的 AI 程式設計工具可以一次性生成全棧應用，前後端程式碼都幫你寫好。

想進一步瞭解全棧程式設計師是什麼、怎麼成為全棧程式設計師？可以看魚皮的這篇文章：[全棧程式設計師是什麼？](https://www.bilibili.com/opus/534338036646820466)




### API

API（Application Programming Interface）是不同程式之間通訊的介面。

你可以把 API 理解成餐廳的選單。選單告訴你有什麼菜可以點，怎麼點，點了之後會得到什麼。你不需要知道廚房怎麼做菜，只需要按選單點餐。

在 Web 開發中，前端透過 API 和後端通訊，獲取資料或提交操作。

![](https://pic.yupi.icu/1/1766718929375-35cd24d6-077e-4a5e-8cbb-7725edf8098f-20260112120508019.png)

想進一步瞭解 API 介面和標準的 API 介面設計規範，可以觀看 [魚皮的 API 動畫科普影片](https://www.bilibili.com/video/BV1WFBXBmExs)。




### 資料庫

資料庫是儲存和管理資料的系統。應用中的使用者資訊、內容、設定等都存在資料庫裡。

常見的資料庫型別有：

- 關係型資料庫（MySQL、PostgreSQL）：資料以表格形式儲存
- 文件資料庫（MongoDB）：資料以 JSON 文件形式儲存
- 鍵值資料庫（Redis）：適合快取和快速查詢

![](https://pic.yupi.icu/1/1764309581505-2ff17977-695f-4d7c-a779-b5d35ad99d6b.png)

![](https://pic.yupi.icu/1/1764309606178-1af81d82-b320-4bed-9c97-5dfe3847d8d3.png)

在 Vibe Coding 中，你可以用 Supabase、Firebase 等現成的雲資料庫服務，不用自己搭建和管理資料庫。

如果你想系統學習資料庫知識，可以看魚皮的資料庫入門教程：[資料庫入門教程](https://www.bilibili.com/video/BV1iJSLBbEyD/)



### BaaS 後端即服務

BaaS（Backend as a Service 後端即服務）是提供現成後端功能的雲服務，包括資料庫、使用者認證、檔案儲存等。

以前沒有 BaaS 的時候，你得自己買伺服器、裝資料庫、寫後端介面、處理各種運維問題，光是搭環境就得折騰好久。而現在使用 BaaS，這些都是現成的，你不需要自己寫後端程式碼和管理伺服器，註冊個賬號就能直接用，能大大加快開發速度，特別適合 Vibe Coding 的場景。

常用的 BaaS 服務有：

- Supabase：開源的 Firebase 替代品
- Firebase：Google 的 BaaS 平臺
- PlanetScale：託管的 MySQL 服務

![](https://pic.yupi.icu/1/image-20260302175641346.png)
