## 動態工作流是什麼？

動態工作流是讓 AI 自己編寫編排指令碼，把一個大任務拆成若干子任務，分發給數十到數百個並行子 Agent 執行，最後彙總驗證結果的能力。

![](https://pic.yupi.icu/1/01_%E5%8A%A8%E6%80%81%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%A6%82%E5%BF%B5%E5%9B%BE-AI%E8%87%AA%E5%B7%B1%E7%BC%96%E6%8E%92%E5%AD%90Agent_compressed_v3.png)

注意，這裡的關鍵詞是 **讓 AI 自己編寫**。

以往我們做多 Agent 協作，不管是用 LangGraph 這種框架、還是自己寫編排程式碼，任務怎麼拆分、子 Agent 之間怎麼協調、結果怎麼合併，這些邏輯都是開發者手動定義的。你得提前想好有幾個 Agent、每個 Agent 負責什麼、上下游怎麼串聯。

而動態工作流不一樣。你只需要告訴 AI 自己想做什麼，比如「幫我把這個專案從 Python 2 遷移到 Python 3」，它會自己分析程式碼庫的結構，決定需要幾個子 Agent、每個子 Agent 負責遷移哪些檔案、怎麼並行執行、怎麼驗證遷移後的程式碼是否正確。

整個編排方案是 AI 根據你的具體任務實時生成的，不是預定義好的模板。

打個比方，傳統的多 Agent 編排就像你當專案經理，需要自己畫甘特圖、分配任務、開站會跟進度。

動態工作流更像是你把需求丟給一個靠譜的技術總監，他自己去搖人、分活、盯進度、驗收，最後給你交付結果。

![](https://pic.yupi.icu/1/02_%E4%BC%A0%E7%BB%9F%E7%BC%96%E6%8E%92vs%E5%8A%A8%E6%80%81%E5%B7%A5%E4%BD%9C%E6%B5%81%E5%AF%B9%E6%AF%94-%E9%A1%B9%E7%9B%AE%E7%BB%8F%E7%90%86vs%E6%8A%80%E6%9C%AF%E6%80%BB%E7%9B%91_compressed_v1.png)



## Agent 系統的分類

要理解動態工作流的技術定位，得先看看 Anthropic 官方是怎麼給 Agent 系統分類的。

早在 2024 年 12 月，Anthropic 就釋出了一篇非常經典的工程部落格，叫 Building Effective Agents。

![](https://pic.yupi.icu/1/image-20260706185611910.png)

這篇文章把所有的 Agentic 系統分成了兩大類。

第一類是 Workflow 工作流，特點是 LLM 和工具的協作路徑是透過預定義的程式碼來編排的。你寫好了流程，AI 按照流程走。

第二類是 Agent 智慧體，特點是 LLM 自己動態決定接下來幹什麼、用什麼工具、怎麼推進任務。控制權在模型手裡。

在 Workflow 這個大類下面，Anthropic 又細分了 5 種具體的模式。

1、Prompt Chaining 提示鏈

任務被拆成一連串固定步驟，前一步的輸出是後一步的輸入。比如先生成文案、再翻譯成英文，兩步是固定順序。

2、Routing 路由

根據輸入的型別把請求分發到不同的處理流程。比如客服系統裡，退款問題走退款流程，技術問題走技術支援流程。

3、Parallelization 並行化

同一個任務拆成多個獨立子任務並行執行，最後把結果彙總。比如讓多個 Agent 分別從不同角度審查一段程式碼。

4、Orchestrator-Workers 編排者-工人

一箇中心 LLM 作為編排者，動態地把任務分解，分配給多個工人 LLM 執行，然後綜合它們的結果。這裡的重點是「動態」，編排者不是按預定義的規則分配任務，而是根據具體輸入來判斷需要幾個工人、每個工人幹什麼。

5、Evaluator-Optimizer 評估者-最佳化器

一個 LLM 生成結果，另一個 LLM 負責評估和提供反饋，迴圈迭代直到質量達標。

![](https://pic.yupi.icu/1/03_Anthropic%E4%BA%94%E7%A7%8DAgent%E7%B3%BB%E7%BB%9F%E6%A8%A1%E5%BC%8F%E6%A6%82%E8%A7%88-%E5%90%AB%E4%B8%AD%E6%96%87%E5%90%8D_compressed_v3.png)

你發現了嗎？動態工作流本質上就是第 4 種模式 Orchestrator-Workers 的產品化實現。

注意，這不是一種新模式，而是同一個模式的不同實現方式。區別在於 **誰來搭建這個編排系統**。

傳統做法是你自己用程式碼實現 Orchestrator-Workers。比如你要做一次全程式碼庫的安全審計，你得用 LangGraph 或者自己寫 Python 來搭這套編排邏輯：

```python
# 這是開發者自己寫的編排器
files = scan_all_files(project_path)
risk_groups = classify_by_risk(files)
agents = []
for group in risk_groups.high:
    agents.append(Agent(task="deep_audit", targets=group))
for group in risk_groups.low:
    agents.append(Agent(task="quick_scan", targets=group))
results = run_parallel(agents)
report = merge_results(results)
```

這段程式碼執行起來確實是「動態」的，能根據實際檔案情況做分配。但問題是，這個編排器本身是你寫的。怎麼掃描檔案、怎麼分級風險、起幾個 Agent、每個 Agent 用什麼策略，所有這些決策規則都得你自己設計。

而 Dynamic Workflows 的特點是 Claude Code 把這件事全包了。你只需要說一句「幫我審計這個專案的安全漏洞」，Claude 自己就會生成類似上面那段編排邏輯並執行。掃描檔案、評估風險、分配任務、彙總結果，全部由模型在執行時自主完成。

一句話總結，**傳統方式你是 Orchestrator-Workers 模式的開發者，Dynamic Workflows 裡你是這個模式的使用者。**



## 動態工作流的運作機制

動態工作流的執行過程大致分為幾個階段。

1）首先是接收任務、制定計劃。

Claude 會分析你的輸入，理解任務的規模和複雜度，然後動態生成一份編排方案，決定需要啟動多少個子 Agent、每個子 Agent 的職責是什麼。這一步就像接到一個大專案後，技術負責人先評估工作量，再寫一份招人計劃和分工表。

2）計劃確定後就進入分發執行階段。

子 Agent 並行啟動，各自處理分配到的子任務。目前系統最多支援同時執行 16 個併發子 Agent，總計上限 1000 個！

3）然後是交叉驗證，這是動態工作流的一個亮點。

它不只是把子任務的結果簡單拼起來，還會安排獨立的驗證 Agent 去檢查其他 Agent 的輸出。對於高風險任務，甚至會啟動「對抗性 Agent」，專門嘗試找茬、攻破前面 Agent 產出的結果。

如果驗證不透過，相關的子 Agent 會被要求修正。**這個迴圈會持續進行，直到所有結果達到一致性標準。**

是不是很眼熟？

沒錯，又是 Loop Engineering 的思想。關於 Claude Code 官方的迴圈工程設計理念，可以閱讀本教程經驗技巧板塊中的《Loop Engineering 保姆級教程》瞭解更多。核心就是讓 AI 反覆跑、反覆改、直到完成目標為止。動態工作流把這個思路用到了極致，不僅僅是讓一個 Agent 自己迴圈，而是一群 Agent 互相驗證、互相糾錯地迴圈。

4）最終把驗證透過的結果彙總成一份完整的交付物，返回給使用者。

整個過程中的進度是持續儲存的，如果任務中途被打斷，恢復後可以從斷點繼續，不需要從頭開始。

![](https://pic.yupi.icu/1/04_%E5%8A%A8%E6%80%81%E5%B7%A5%E4%BD%9C%E6%B5%81%E8%BF%90%E4%BD%9C%E6%9C%BA%E5%88%B6%E5%9B%9B%E9%98%B6%E6%AE%B5%E6%B5%81%E7%A8%8B_compressed_v3.png)

此外還有一個關鍵設計，這個 **編排的執行發生在對話上下文之外**。

你可以這麼理解，主對話視窗是你和技術總監溝通的會議室，而那些子 Agent 各自在獨立的工位上幹活。不管外面有多少人在並行工作，都不會擠佔你會議室的空間。所以不管任務多大、涉及多少個子 Agent，都不會撐爆 Claude 的上下文視窗。這是它能處理跨越數百個檔案的大規模任務的關鍵。

![](https://pic.yupi.icu/1/05_%E4%B8%8A%E4%B8%8B%E6%96%87%E9%9A%94%E7%A6%BB-%E4%BC%9A%E8%AE%AE%E5%AE%A4vs%E7%8B%AC%E7%AB%8B%E5%B7%A5%E4%BD%8D%E6%AF%94%E5%96%BB_compressed_v1.png)



## 動態工作流實戰案例

動態工作流最震撼的案例來自 JavaScript 執行時 Bun 的開發者 Jarred Sumner。

他用動態工作流把 Bun 從 Zig 語言移植到了 Rust，整個過程 11 天完成，產出了大約 75 萬行 Rust 程式碼，原有測試套件的透過率達到 99.8%。

這個遷移是怎麼用動態工作流完成的呢？

Anthropic 官方部落格透露了大致的過程。

首先，一個工作流負責遍歷整個 Zig 程式碼庫，為每一個結構體的每個欄位對映出對應的 Rust 生命週期標註。這一步需要分析大量的型別關係和所有權語義。

然後，另一個工作流把數百個 .zig 檔案分配給並行的 Agent，每個 Agent 把分配到的 .zig 檔案翻譯成行為等價的 .rs 檔案。而且每個檔案會安排兩個審查 Agent 來檢查翻譯結果。

接下來是修復迴圈。一個工作流反覆執行構建和測試，把編譯錯誤和測試失敗分發給對應的 Agent 去修復，直到整個專案能夠正常編譯並透過測試套件。

最後，一個通宵執行的工作流負責消除不必要的資料複製，併為每處最佳化單獨建立一個 Pull Request 供人工審查。

整個過程中，人類開發者做的事情就是定義目標、確認方案、最後審查 PR。中間的具體實施全部由動態工作流自主完成。

![](https://pic.yupi.icu/1/07_Bun%E8%AF%AD%E8%A8%80%E8%BF%81%E7%A7%BB%E5%AE%9E%E6%88%98%E6%A1%88%E4%BE%8B%E6%B5%81%E7%A8%8B_compressed_v3.png)



## 動態工作流是模型能力還是工具能力？

這是一道很尖銳的面試題：動態工作流是模型自身具備的能力，還是平臺工具提供的？

答案是 **兩者缺一不可，但職責不同**。

**模型層面提供的是「智慧」。**

比如：

- 任務規劃能力，能把一個模糊的大目標拆解成具體的、可執行的子任務
- 上下文理解能力，能分析程式碼庫結構、理解各檔案之間的依賴關係
- 工具呼叫能力，能正確生成和執行編排指令碼
- 還有自我糾錯能力，能判斷子任務的輸出是否正確，以及如何修復

這就是為什麼動態工作流是跟 Opus 4.8 一起釋出的。Opus 4.8 在任務規劃和判斷力上有明顯提升，它對自己程式碼中的缺陷的檢出率是前代模型的 4 倍。這種自我檢驗的能力是動態工作流能做到「交叉驗證」和「對抗性檢查」的基礎。

**平臺層面提供的是「基礎設施」。**

比如：

- 子 Agent 的生命週期管理，負責建立、排程、銷燬
- 併發控制，限制最多 16 個同時執行
- 進度持久化，中斷後可以恢復
- 上下文隔離，讓編排邏輯不佔用主對話的上下文視窗
- 以及最終的結果聚合和交付

用一個類比來理解，模型能力就像一個優秀的技術總監的大腦，他知道怎麼拆任務、怎麼分配人、怎麼驗收。

平臺能力就像公司的專案管理系統和基礎設施，提供了會議室、協作工具、版本控制、持續整合等等。

光有聰明的大腦但沒有執行體系不行，光有系統但沒人會規劃也不行。

所以如果面試官問你這個問題，最準確的回答是，動態工作流是一種 **建立在強模型能力基礎上的平臺產品特性**。模型提供規劃和決策的智慧，平臺提供並行執行和生命週期管理的基礎設施，兩者結合才構成完整的動態工作流。

## 和多 Agent 框架的區別

理解了上面的架構分層之後，再來看看動態工作流跟 LangGraph、CrewAI 這些多 Agent 框架的區別就很清晰了。

傳統多 Agent 框架的思路是，開發者自己定義 Agent 的角色和能力，自己編寫編排邏輯決定誰先執行、誰後執行、結果怎麼傳遞，異常情況也要自己處理。框架給你提供了一堆現成的模組和連線方式，但具體怎麼組裝是你的事。

動態工作流的思路完全相反，開發者只需要描述最終目標，模型自動完成角色定義、任務拆解、編排邏輯生成、異常處理和結果驗證。你連編排程式碼都不用寫，因為 Claude 自己會寫。

**這兩種方式沒有絕對的好壞之分，適用場景不同。**

如果你的任務是高度標準化的、流程固定的，比如每天定時跑一輪資料分析報告，用傳統框架把流程寫死會更穩定、更可控、成本更低。

如果你的任務是一次性的、規模大的、子任務不可預測的，比如程式碼庫遷移、安全審計、大規模重構，動態工作流的優勢就很明顯了，因為你根本沒法提前定義好所有的子任務和執行路徑。



## 怎麼用起來？

動態工作流目前在 Claude Code 的 CLI、桌面端和 VS Code 擴充套件中都可以使用，也可以透過 API 呼叫。

其他 AI 程式設計工具也在探索類似的多 Agent 並行模式，比如 Cursor 推出了 Cloud Agents 和後臺 Agent 並行能力。不過目前「由模型自己編寫編排指令碼」這種玩法，Claude Code 的動態工作流是做得最完整、產品化程度最高的。

啟動動態工作流的方法非常簡單，有 2 種方法。

第一種是直接告訴 Claude 建立一個工作流，比如：

```markdown
建立一個工作流，幫我審計整個程式碼庫的安全漏洞
```

第二種是在 Claude Code 的 effort 選單裡開啟 `ultracode` 設定。這個設定會把推理力度調到最高，同時讓 Claude 自動判斷當前任務是否適合用工作流來處理。如果適合，它會自動切換到工作流模式。

第一次觸發工作流時，Claude Code 會顯示即將執行的計劃並要求你確認，不會直接就跑起來。

有一點需要注意，動態工作流的 Token 消耗量遠超普通的 Claude Code 會話。道理很簡單，你同時僱了幾十上百號人幫你幹活，工資當然比只請一個人貴得多。

所以建議按需使用，先從一個小範圍的任務開始試，感受一下消耗量級，再逐步擴大規模，別上來就對著整個程式碼庫一把梭。



## 寫在最後

看完這篇文章，你會發現 AI 應用開發正在從「開發者編排 Agent」向「Agent 編排 Agent」演進。開發者的角色在往上移，從寫編排程式碼的執行者，變成定義目標和審查結果的管理者。

這個趨勢意味著，以後做 AI 應用開發，光會用框架寫 Agent 可能不夠了，還需要對整個 Agent 架構體系有深入的理解。Anthropic 那篇 Building Effective Agents 提出的 5 種模式，基本就是這個領域的必備知識點，建議反覆讀。

希望這篇文章能幫你真正搞懂動態工作流，不管是面試還是實際使用，都能心裡有底。AI 程式設計的世界變化很快，保持學習，你一定能跟上節奏！
